## 0. 総評 — 3 つの根本原因

個別の「余白が足りない」「線がない」は症状で、原因はこの 3 つに集約される。ここを直さずに
個別値だけ触ると、また同じ状態に戻る。

### 0-1. デザイントークンが存在しない

余白・角丸・行高・フォントサイズがすべて各ファイルにベタ書きされた即値で、共有の定義が一つも
ない。実際に散らばっている値:

| 種類 | 現状の値 | 出現箇所 |
|---|---|---|
| 行高 | 24 / 24（実効 **50**）/ 28 / 32 | `QuickAccessSection.qml:83`, `FolderTreePanel.qml:88`, `FileTableView.qml:556`, `FileTableView.qml:391` |
| 内側マージン | 2 / 4 / 4 / 6 / 8 | `FileTableView.qml:618,588,405`, `FileGridView.qml:349`, `QuickAccessSection.qml:49` |
| 角丸 | 4 のみ（3 箇所で個別に） | `FileGridView.qml:266,337`, `DragProxy.qml:62` |
| ハードコード色 | `"crimson"`, `"#c42b1c"`, `"#e81123"`, `"white"` | `LoginView.qml:85,123`, `CaptionBar.qml:106,110` |

`FolderTreePanel.qml:88` の 24 は **書いてあるだけで効いていない**（3-2 参照）。ベタ書きの即値が
散らばっているだけでなく、そのうち 1 つは意図した効果を持っていない、というのが現状。
→ S0 でこの無効な即値と、それを説明していた誤ったコメントは削除済み（行高 50px 自体は S5 まで
そのまま）。

**修正案 → S1 で実装済み（2026-08-03）**: `qml/Theme.qml`（`pragma Singleton` + `QML_FILES` に

実装で確定した事実:

- ライト/ダーク判定は `Application.styleHints.colorScheme === Qt.Light`。**FluentWinUI3 自身が

  （`pragma Singleton` + 入れ子 `readonly property QtObject`）も Qt 本体の
  `FluentWinUI3/Config.qml` に倣った。
- `font.body: 14` は当て推量ではなく **FluentWinUI3 の既定値そのもの**
  （`Config.qml` の `fontFamily: "Segoe UI"` / `fontSize: 14`）。3-2 の「ink 高 11px」と整合する。
- CMake 側は `set_source_files_properties(qml/Theme.qml PROPERTIES QT_QML_SINGLETON_TYPE TRUE)` が
  必須で、**`qt_add_qml_module` より前**に置く必要がある。これが無いと生成 qmldir の行が
  `Theme 254.0 …`（singleton 無し）になる。
- **消費側に `import MegaExplorer` は不要**だった（実機で確認）。同一モジュール内なので
  `Theme.spacing.md` がそのまま解決する。S2 以降で import 行を足す必要はない。
- ~~**`strokeSubtle` は D3 が決めていない**ので暫定値（ライト `#ebebeb` / ダーク `#2d2d2d`）を
  置いてある。**S3 の実機確認で確定させ、D3 に追記すること。**~~
  → **S3 で削除した（2026-08-03）**。唯一の消費予定地だった 3-7 の区切り線に当ててみたところ、
  背景 `surfaceAlt` との差が **ダーク 6/255（`#2d2d2d` vs `#272727`）/ ライト 8/255** しかなく、
  3-7 が「ほぼ不可視」と切り捨てた `SystemPalette.mid` と同程度に見えなかった。
  `stroke`（ダーク 9/255 / ライト 14/255）に一本化して解消。3-10 のインデントガイド線が
  本当に弱い線を要るなら **S5 でその用途に合わせて値ごと再導入する** —— 消費者ゼロの状態で
  推測値を置いておくのが誤りだった、というのが今回の教訓。
- `color.text` は `SystemPalette.text` にしたが、既存コードは 2 箇所で `palette.buttonText` を
  使っている（`CaptionBar.qml:119`, `FolderTreePanel.qml:139`）。差し替える S3/S5 で見え方を
  確認し、必要ならトークン側を直す。

### 0-2. すべての面（サーフェス）が同一色で、境界線が 1 本もない

実測（1200x800、ダーク）:

- キャプションバー背景 = ツールバー背景 = サイドパネル背景 = コンテンツ背景 = **すべて
  `#202020`**
- y=36（キャプション下端）、y≈80（ツールバー下端）、y≈752（フッター上端）に境界線 **なし**
- SplitView のハンドルだけ x=202–203 に 2px の `#1c1c1c` があるが、`#202020` との差が 4/255
  しかなく事実上見えない

つまり「どこからどこまでが何の領域か」を示す視覚情報がゼロ。ユーザー指摘の「各境界に境界線が
ない」はこれ。

~~**修正案**~~ → **修正済（S3 / 2026-08-03）**。3 点とも実施した。

1. **面の色を分ける**（**D3 で確定**） — サイドパネル・キャプション行・**フッター**を
   `surfaceAlt`、ツールバー行とファイル一覧側を `surface`。
   **鍵は「ウィンドウ自体の `color` を `surface` にする」こと**: 一覧側の 5 領域
   （`TabContentPane` / `FileTableView` / `FileGridView` / `Breadcrumb` / `LoginView`）は
   どれも背景を描いておらずウィンドウ色に落ちていたので、`Main.qml` の
   `ApplicationWindow.color` 1 行で全部片付いた。各ビューに背景 `Rectangle` を足す必要はない。
   逆に、そこから外れる 2 領域（サイドパネル・フッター）だけが自前で塗る。
2. **1px の区切り線を入れる** — 4 箇所すべて `Theme.color.stroke` で実施。実測 y=39 / y=87 /
   y=752 / x=225。
   **キャプション下の線は S2 との噛み合わせがある**: アクティブタブの角丸背景は不透明な
   `surface` でキャプション下辺と面一（§1-1/§1-2）なので、線を**背景 `Rectangle` の内側**
   （= `TabStrip` より下の z）に描くと、アクティブタブがその上を塗って**線が自動的に途切れる**。
   Chrome / Explorer 11 と同じ見え方で、「アクティブタブだけコンテンツと地続き」という S2 の
   意匠が壊れない。実測でも線は x=0–3 と x=196– にのみ出て、タブ範囲 x=4–195 では消えている。
   追加の重ね描きやマスクは不要だった。
3. SplitView のハンドルは **`handle:` デリゲート自体が存在しなかった**（Fluent 既定の 2px）。
   当たり判定と見た目を分離し、`implicitWidth: 6` の掴み代の中に 1px のラインを置いた。
   ホバー/ドラッグ中は `border.drop`(2px) + `accent` に太る。
   **ラインは中央ではなく右端に置く**: ハンドルを透明にすると線の両側が同じ `surface` になり、
   線が面の境界から 2px コンテンツ側にずれて見えた（実測: パネル終端 x=219 / 線 x=222）。
   ハンドルを `surfaceAlt` で塗ってパネルの延長にし、線をその右端に置くことで境界と一致する。
   自前デリゲートにするとスタイル既定のリサイズカーソルが失われるので
   `HoverHandler { cursorShape: Qt.SplitHCursor }` を付けている。

### 0-3. Fluent 標準コントロールの一部だけを上書きしていて、寸法体系が混在している

`FileTableView` のセル、`FolderTreePanel` の背景、`FileGridView` のタイルは背景を自前の
`Rectangle` に差し替えているが、パディング・ホバー表現・背景の伸び方は Fluent 既定のまま。
結果、同じ「行」でもコンポーネントごとに高さ（ピン **24** / ツリー **50** / テーブル 28）も
内側パディング（4/6）も背景の横幅の決まり方（3-3）も揃っていない。

しかも `FolderTreePanel.qml` の 50px は**意図した値ですらない** — スタイル既定の indicator が
そのまま行高になっている（3-2）。上書きの仕方が中途半端だと、既定値がどこから来ているのか
書いた本人にも見えなくなる、という典型例。

なお **フォントサイズ自体は揃っている**（3 回目の調査でも再確認: 文字の ink 高がツリー行 /
ピン行とも 11px で一致）。バラついているのは行高・パディング・背景の描画範囲であって、
文字サイズではない。

**修正案**: 「行」の見た目を担う共通コンポーネント（例 `qml/components/RowSurface.qml`）を
1 つ作り、選択/ホバー/ドロップ受け入れの 3 状態と行高・角丸・パディングをそこに集約する。
ツリー行・ピン行・テーブル行・グリッドタイルはそれを使う。今バラバラに書かれている
`Qt.rgba(highlight, 0.35)` の選択色（4 箇所で個別に同じ式を書いている）もここに寄せられる。

## 1. キャプションバー / タブ（`CaptionBar.qml`, `TabStrip.qml`）

### 1-1. アクティブタブのインジケータがキャプション行の外にはみ出している ★重大

実測: キャプションバーの高さは 36px（`CaptionBar.qml:32`）だが、アクティブタブの下線
インジケータ（ティール色のダッシュ）は **y≈41–45** に描画されている。つまりキャプション行の
下、ツールバー（パンくず）行の領域に重なって浮いている。

原因: `TabStrip` は `RowLayout` で、`TabBar` に `Layout.fillHeight` が指定されていない
（`TabStrip.qml:57-59`）。`CaptionBar` 側は `anchors.top/bottom` で 36px に固定している
（`CaptionBar.qml:49-51`）が、内側の `TabBar` は自分の implicitHeight（Fluent 既定で 36 より
大きい）のまま配置され、`clip` もされていないので下にはみ出す。

**修正済（S0 / 2026-08-03）**: `TabBar` に `Layout.fillHeight: true` を付け、キャプション高を
36→**48px** にした。実測でインジケータは y=41–43、ツールバー行は y=48 から始まる。

当初案の「Explorer 11 に合わせて 40px 程度」は**採らなかった**。Fluent の実寸を測ったところ、
`TabButton` は label 20px + 上下 padding 10px = **40px 固定**、`TabBar` はさらに上下 4px の
padding を持つので、タブ列の自然高は **48px** だった（`FluentWinUI3/Config.qml` の
`controls.tabbutton` / `controls.tabbar`）。40px に収めるには `TabBar.topPadding/bottomPadding`
を 0 に潰し `TabButton.height` を明示する必要があり、これは §0-3 が根本原因として挙げている
「標準コントロールの寸法の一部だけを上書きする」パターンそのものになる。

~~**40px 化は S2 に送った**~~ → **S2 で実施済み（2026-08-03）**。読みどおり `TabButton.background`
の差し替えと同時に padding を定義する形になった。内訳は
**`TabBar.topPadding` 4 + `TabButton` 36 + `TabBar.bottomPadding` 0 = 40**。

下 padding を 0 にしたのは高さ合わせのためだけではなく、これが §1-2 の「アクティブタブの下辺は
コンテンツと地続き」の実装そのものだから — 下に余白があるとタブがキャプション行の中に浮き、
角丸タブがツールバー行へ繋がらない。`TabButton` 側は Fluent の 12/12/10/10 に対し
**上下 8 / 左 12 / 右 4**（右だけ詰めるのは閉じるボタンの置き場）。実測でキャプションは
y=0–39、ツールバー行は y=40 開始、アクティブタブは y=4–39 で下辺が面一。

### 1-2. インジケータの位置とラベルの位置が噛み合っていない

実測: タブ幅 200px に対し、ラベル "Cloud Drive" は x≈16 から左寄せ、インジケータは x≈92–108
（タブの中央）。左寄せテキストの下に短い中央寄せの下線があるので、どのタブが選択中なのか
視線で結び付かない。

~~**修正案**~~ → **修正済（S2 / 2026-08-03）**: Explorer 11 / Chrome 方式を採り、アクティブタブを
**背景を `Theme.color.surface` で塗った角丸タブ**（上 2 角だけ角丸、下辺はコンテンツと地続き）に
した。下線方式の代案は採っていない。

実装上の発見が 2 つある。

1. **Fluent のインジケータは `background` の中に住んでいる**。`TabButton.qml` の
   `background: Impl.StyleImage { ... property Rectangle selector: Rectangle { ... } }` がそれで、
   16x3px・`radius 1.5`・`palette.accent`・下端中央・`visible: control.checked`、さらに 83ms の
   opacity と 167ms の scale アニメまで付いている。つまり **`background` を差し替えれば下線は
   自動的に消える** — 別途消す処理は要らなかった。実測でもアクセント色のピクセルは
   キャプション行に 1 つも残っていない。
2. `StyleImage` 自体は **何も描いていない**（`filePath` が全 8 状態で空、対応する PNG も無い）。
   にもかかわらず implicit 77x40 の下駄を履かせていて、これが `TabButton` の最小幅・最小高を
   決めていた。差し替えでこの下駄も外れる。`TabBar` 側の `background` も同様に空の
   `StyleImage`（implicit 470x48）なので `background: null` にして外した。

角丸は Qt 6.7+ の `bottomLeftRadius`/`bottomRightRadius` を 0 にするだけで済み、従来よくやる
「下辺を四角い矩形で塗り潰して隠す」重ね描きは不要だった。

なお Fluent の `TabButton` は**ホバー時の背景を持たない**（`contentItem` の文字色 alpha だけで
表現している）。背景を自前化するとその表現ごと失われるので、`Theme.color.subtleHover` /
`subtlePressed` を新設して塗りで置き換えている（§0-1 の追加トークン表を参照）。

### 1-3. タブの閉じる「×」が描画されていない ★重大

実測: タブ幅 200px の範囲（x=0–200）を拡大しても × が一切見当たらない。`TabStrip.qml:109-115`
で 22x22 の `ToolButton` を `contentItem` の `RowLayout` に入れているのに出ていない。~~1-1 の
レイアウト崩れと同根の可能性が高い。~~

**原因（S0 で確定）— 1-1 とは別物だった。** Fluent の `ToolButton` は左右 padding が 11px ずつ
（`Config.qml` の `controls.toolbutton`）ある。そこに `implicitWidth: 22` を強制していたため
`availableWidth = 22 - 22 = 0` となり、「×」が幅ゼロに潰れて省略されていた。これも §0-3 の
「Fluent の寸法の一部だけを上書きする」パターンの一例で、B1 のレイアウト崩れとは無関係。

**修正済（S0 / 2026-08-03）**: 強制サイズをやめ、Fluent の自然サイズに戻した。ただし
`contentItem` の中に置いたままだと**別の副作用が出る**: `TabButton.implicitHeight` は
`implicitContentHeight` から導かれ、Fluent は content 行をラベルだけの 20px に合わせているので、
32px の `ToolButton` を入れるとタブ自体が 52px に膨らみ、今度は B1 のインジケータが再びクリップ
される。そのため**閉じるボタンは `contentItem` の兄弟**（`TabButton` 直下の子）として
`anchors.right` + `verticalCenter` で置き、ラベル側は `rightPadding` でその分を空ける形にした。
実測で × は x=165–171、インジケータは y=41–43 に共存する。

~~「ホバー中またはアクティブなタブのみ × を表示」（Explorer と同じ）は意匠なので S2 で。~~
→ **S2 で実施済み（2026-08-03）**。`visible: tabButton.checked || tabButton.hovered`。
`hovered` は閉じるボタン上も含むので、カーソルを乗せた瞬間にボタンが自分で消える事故は起きない。

**S2 で B2 を一度再発させている**（実測して気付いた）。ボタンを 38x32 から 20x20 に縮めるとき
`padding: 2` と書いたが、Fluent の `ToolButton.qml` は
`leftPadding: __config.leftPadding || 0` のように **4 辺を個別に束縛している**ため、まとめ書きの
`padding` は個別束縛に負けて 11 のまま残り、`availableWidth` が 0 になって「×」がまた消えた。
`topPadding`/`bottomPadding`/`leftPadding`/`rightPadding` を個別に書いて解消。
**B2 の教訓は「implicitWidth を強制するな」ではなく「Fluent が個別に束縛している値は個別に
上書きしろ」だった**、というのがこの再発で分かったこと。

あわせて `background` も自前の `Rectangle` に差し替える必要がある。Fluent の `ButtonBackground` は
implicit 32x32 を持つので、padding を詰めるだけでは 32px を下回れない。

### 1-4. その他

- タブ 1 枚のときも 200px 幅を占有し、しかも 1 枚しかないのに閉じるボタン等の余地だけがある。

## 2. ツールバー行（`Main.qml:152-214` / `Breadcrumb.qml`）

### 2-1. 行全体に左右マージンがない

`RowLayout` が `anchors.fill: parent`、`spacing`/`margins` 未指定（`Main.qml:153-154`）。
`ToolBar` 自体の既定パディングに委ねているため、「← Back」の左端が x≈18、検索欄の右端が

ツールバー行の高さも 44px → 40px に詰めてよい（キャプション 40 と揃う）。

### 2-2. ナビゲーションボタンが「← Back」というテキストボタン

実測: `text: qsTr("← Back")`（`Main.qml:157`）。矢印が文字で、ラベルが英語のまま横に付いて
いるので幅を食い、アイコンボタンが並ぶ Explorer 風の見た目にならない。前へ/上へも無い。

**修正案（D4 = 「上へ」のみ追加で確定）**: Segoe Fluent Icons（`CaptionBar.qml:127` で既に
採用済み）でアイコン化し、**戻る / 上へ の 2 ボタン**を 32x32 の正方アイコンボタンとして
並べる。ツールチップでテキストを補う。

「上へ」は現在パスの親へ遷移するだけで履歴スタックの分岐を作らないため、
`FolderNavigationController` への追加は小さく、パンくずが既に親パスを保持しているので
遷移先の解決も済んでいる。**「進む」は見送り** — `canGoForward`/`goForward` に加えて

スコープを超えるため。やるなら別フェーズ。

### 2-3. パンくずの余白と区切りが不揃い

実測/コード: セグメントのラベルは `leftPadding: 4` / `rightPadding: 2`（`Breadcrumb.qml:92-93`）
で左右非対称。区切りの「>」は独立 Label でパディング 0（`Breadcrumb.qml:185-189`）。オーバー
フロー表示の «  も 4/2（`Breadcrumb.qml:73-74`）。結果、"Cloud Drive" と ">" の間だけ詰まり、
">" と次のセグメントの間だけ空く。

**修正案**:

- セグメントのパディングを左右対称（`leftPadding = rightPadding = Theme.spacing.sm`）に。
- 区切りは文字「>」ではなく Segoe Fluent Icons のシェブロン（``）にし、上下中央・
  左右 2px のパディングを明示。文字サイズも本文より 1–2px 小さく。
- 先頭に「クラウドドライブ」アイコンを置く（Explorer の PC アイコン相当）。
- セグメントにホバー時の背景（角丸 4px の subtle fill）を入れる。現在はクリックできることが
  見た目からわからない。
- ドロップ受け入れ枠が `border.width: 2` の矩形（`Breadcrumb.qml:106`）で、他所（グリッド
  タイル/ツリー行）と角丸の有無が揃っていない。→ 0-3 の共通コンポーネントに寄せる。

### 2-4. 検索欄

- 幅がツールバーの 3/10 固定比（`Main.qml:192`）。1200px 時 320px は妥当だが、800px 時は
  200px まで縮み、プレースホルダ "Search in this folder" が入りきらない（実測で末尾が切れる
  寸前）。→ `Layout.minimumWidth: 160` と、狭いときはプレースホルダを短縮するか虫眼鏡
  アイコンボタンに畳む。
- 検索アイコンがない。→ 先頭に虫眼鏡、入力中はクリア（×）を出す。

### 2-5. 「≡」（サインアウト）ボタン

テキストの ≡ でフォントサイズ既定（`Main.qml:201`）。アイコンフォント化し、Explorer の
「…（もっと見る）」に相当する位置づけであることが分かる見た目にする。

## 3. サイドパネル（`SidePanel.qml`, `QuickAccessSection.qml`, `FolderTreePanel.qml`）

### 3-1. パネル全体に外周マージンがない

実測: 「Quick access」ラベルの左端 x=8、ツリー行の文字左端 x=28、パネル右端は SplitView
ハンドル（x=202）まで詰まっている。上端も y=88 のツールバー直下から即コンテンツ。

**修正案**: パネル上下に 4–8px、行の左右に 4px のインセットを入れ、行の背景（選択/ホバー）を
角丸 4px の「浮いたピル」にする（Windows 11 のナビゲーションペインの表現）。

### 3-2. ツリー行が 50px と高すぎる ★ユーザー指摘（原因を式レベルで特定）

この節は 2 度訂正している。経緯は以下のとおり。

- **初報**: 「ツリーの文字がピン行より 1〜2px 大きい」と書いた → **誤り**。拡大画像で別々の
  文字列（"Test Folder" と "Cloud Drive"）を見比べた際の錯覚だった。
- **2 回目**: 「フォントサイズは同一で、原因は行高 24px という密度」と書いた → フォントの
  結論は正しいが、**行高 24px という前提が誤り**。古いバイナリを測っていた。
- **3 回目（現行）**: リビルド後に実測し直し、**行高は 50px**、原因はスタイル既定の
  indicator であることを式レベルで特定した。

#### 実測値（1200x800、DPI 100%、リビルド後）

| 項目 | ツリー | クイックアクセス |
|---|---|---|
| **行高** | **50px** | **24px** |
| ラベル左端 | x=28 | x=20（**8px ずれ** → 3-4） |
| 文字の ink 高 | 11px | 11px（**同一**） |
| シェブロンの ink | **10 × 16px** | — |
| 選択ハイライトの幅 | 123px（`contentWidth` 追随 → 3-3） | 行幅いっぱい |

**フォントサイズの不統一は存在しない**（ink 高が両方 11px）。一方で **行高は 2 倍以上**、
**シェブロンは文字の 1.45 倍**ある。ユーザーが「文字が大きい」と感じたのは、文字ではなく
**行とアイコンが大きい**ことの裏返しだった。

#### 原因: `background` の `implicitHeight` は効いていない

`FolderTreePanel.qml` の `TreeViewDelegate` は、FluentWinUI3 ではなく **Basic スタイル**の実装に
解決されている（FluentWinUI3 は `TreeViewDelegate.qml` を持たないため）。実測値が Basic の式と
完全に一致することで確認した:

```qml
// QtQuick/Controls/Basic/TreeViewDelegate.qml
implicitHeight: Math.max(indicator ? indicator.height : 0, implicitContentHeight) * 1.25
indentation: indicator ? indicator.width : 12
leftPadding: leftMargin + __contentIndent        // = 4 + depth*20 + 20 + 4
indicator: Item { implicitWidth: 20; implicitHeight: 40 }   // ← 行高の支配項
```

| 式 | 計算 | 実測 |
|---|---|---|
| `implicitHeight` | `max(40, 19) * 1.25` = **50** | 50 ✓ |
| `indentation` | `indicator.width` = **20** | 20 ✓ |
| `leftPadding`（depth 0） | `4 + 0 + 20 + 4` = **28** | 28 ✓ |

決定的なのは、**Basic の `implicitHeight` の式に `implicitBackgroundHeight` が入っていない**こと。
つまり `FolderTreePanel.qml:87-88` の

```qml
background: Rectangle { implicitHeight: 24 }
```

は **一切効いていない**。同ファイル 84-86 行の「implicitHeight restates what the style's
background supplies」というコメントは**誤り**で、削除するか正しい説明に置き換えること。
→ **S0 で対応済み**（無効な `implicitHeight: 24` を削除し、コメントを「Basic の式に background
の項がないので、ここに書いた implicitHeight は無視される」という正しい説明に差し替えた）。
（ピン行の `QuickAccessSection.qml:83` は `ItemDelegate` **自身**に `implicitHeight: 24` を
書いているので、こちらは意図どおり効いている。この非対称が「揃っていない」の正体。）

もう一点、`indicator` の 40px は**見えているシェブロンの大きさではない**。Basic のコメントが
"Create an area that is big enough for the user to click on, since the image is a bit small" と
明記しているとおり、**クリック領域を確保するための透明な `Item`** であり、シェブロン画像は
その中央に置かれた小さい子要素。だから「アイコンを小さくすれば行が縮む」というより、
**当たり判定の `Item` が行高を決めている**。

#### 修正方針（D1a / D1b で確定）

1. **行高を 28px に統一**（ツリー 50→28、ピン 24→28）。`background` ではなく
   **デリゲート自身の `implicitHeight`** に書く。Basic の式は `max(...) * 1.25` なので、
   indicator を縮めるだけでは狙った値に着地しない — 明示指定が必須。
2. **シェブロンはグリフだけ縮小**し、ink 高を文字と同等（10〜11px）にする。
   **当たり判定の `Item` は幅 20px を維持**する（グリフごと縮めるとクリックしづらくなる）。
3. ツリー行とピン行の両方に**明示的にフォントを指定**して、スタイル既定への暗黙依存をやめる
   （現状は偶然一致しているだけで、スタイル更新で崩れうる）。
4. 行頭に 16px のフォルダーアイコンを追加（3-5）、インデントを 16px に（3-9）。

> **実装上の注意**: `indicator` を差し替えるとき、`FolderTreePanel.qml` 冒頭のコメントが
> 警告しているのは `pointerNavigationEnabled: false` + 自前 `TapHandler` の話であって、
> `indicator:` を別 `Item` に差し替えること自体ではない。stock のポインタ処理は indicator の
> 矩形を見て展開/折りたたみを判定するので生き残るはずだが、**S5 の着手時に実機で要確認**。
> また `indentation: indicator.width` なので、D1b で `indicator.width` を 20px のまま残すなら
> **`indentation` を明示的に 16 と書かないとインデントは 20px のまま**になる。

### 3-3. 行の背景幅がビュー幅ではなくコンテンツ幅に追随する ★重大（初報から詳細化）

初報では「ハイライトが行幅いっぱいでない」と書いたが、階層を深くしたツリーで再実測した結果、
より正確には **行の背景幅が `contentWidth`（＝最も幅の広い行）に追随している** ことが原因と
判明した。症状が 2 通り出る:

- **浅いツリー（初報時、ルート 1 行のみ）**: ハイライトが x=0–111 で終わり、パネル幅 202px に
  届かない。半端な塗りに見える。
- **深いツリー（今回、6 階層）**: 最深行の幅がパネル幅を超えたため `contentWidth` が伸び、
  ハイライトは x=0–219 とパネル幅いっぱいになる。ただしこれは「たまたま溢れているから
  埋まっている」だけで、ビューをスクロールすれば右にはみ出した部分も塗られている。

- **3 回目（リビルド後、2 階層、パネル幅 220px）**: 選択中の "Cloud Drive" 行のハイライトは
  **x=0–122（幅 123px）** で終わり、パネル幅 220px の **56% しか塗られていない**。

つまりフォルダー構成によって見た目が変わる。`TreeViewDelegate` の background が
`implicitWidth`（インデント + テキスト幅）基準で、ビューポート幅を参照していないため。

**修正済（S0 / 2026-08-03）**: 予想どおり D2 = (c) の 1 修正で閉じた。`TreeView` に
`columnWidthProvider: function (column) { return root.width; }` と `onWidthChanged: forceLayout()`
を置いただけで、背景幅・名前の切断・横スクロールの 3 つが同時に解消している。実測でハイライトは
x=0–219（パネル幅 220px と一致）、6 階層まで展開しても変わらない。

なお §0-3 が提案する共通行コンポーネント（`RowSurface.qml`）への集約は **S5 以降**。S0 では
`TreeView` 側に置いた。

### 3-4. クイックアクセスとツリーのインデントが揃っていない

実測（リビルド後）: ピン行のラベル左端 **x=20**、ツリー第 1 階層（`depth 0`）のラベル左端
**x=28**。`QuickAccessSection.qml:85` の「ツリーの第 1 階層に揃える」というコメントに反して
**8px ずれている**（ツリー側は `leftMargin(4) + indicator.width(20) + spacing(4)` = 28 になる
ため。3-2 の式を参照）。

`leftPadding: 20` という即値は、ずれの大きさが `TreeViewDelegate` の `leftMargin` /
`indicator.width` / `spacing` という 3 つのスタイル既定値の合計で決まる以上、**そもそも手で
合わせ続けられない**。スタイルが変われば黙ってずれる。

**修正案**: ピン行にもツリーと同じ幅のインジケータ相当スペーサ（またはフォルダアイコン）を
置いて物理的に揃える。`leftPadding: 20` の即値をやめ、Theme のトークンから両者を導出する。

### 3-5. アイコンがない

ツリー行・ピン行ともにフォルダアイコンがない。ファイル一覧（絵文字 📁）とも不整合。
→ 4-4 のアイコン整備とまとめて、16px のフォルダアイコンを行頭に置く。

### 3-6. 「Quick access」ヘッダの体裁

`font.bold: true` + `opacity: 0.7`（`QuickAccessSection.qml:53-54`）。Windows 11 のセクション
ヘッダは太字ではなく「少し小さい + アクセント寄りの弱色」。opacity で透かすと背景色が変わった
ときに濁るので、`Theme.color.textSecondary` を使う。上下マージン（6/2）も非対称。

### 3-7. クイックアクセスとツリーの区切り線が見えない・詰まっている

実測: y=135 に `SystemPalette.mid` の 1px 線があるが、`#282828` 相当で背景 `#202020` との差が
小さくほぼ不可視。しかも線の直下（y=136）からいきなりツリーの選択行が始まっており、上下の
余白が 0。

**修正案**: 線色を Theme 由来に変え、線の上下に 4–6px の余白を入れる。または
線をやめてセクション見出し（「フォルダー」など）を置いて区切る。

**線色は S3 で対応済み（2026-08-03）**: `SystemPalette.mid` → `Theme.color.stroke`。当初は
「同一サーフェス内の仕切りだから弱い線で」と `strokeSubtle` を当てたが、実測で背景との差が
ダーク 6/255 しかなく元の `mid` と同じく見えなかったため `stroke` に一本化した
（`strokeSubtle` トークン自体を削除。§0-1 参照）。実測でライト `#e5e5e5` / ダーク `#303030`。
**上下の余白は S5 の担当**（サイドパネルの余白設計そのもの）で、S3 では触っていない。

### 3-8. 深い階層でフォルダー名が省略記号なしで切り落とされる ★重大（今回の追加調査で判明）

6 階層のフォルダーを入れて再確認したところ、`this is a long name…` に相当する行が
**パネル右端（当時の実測で x=219）で文字の途中からいきなり消える**。「…」もなく、単語の
途中で切れているため、名前が長いのか切れているのかすら分からない。

構造（**S0 着手時に 6 階層すべてを実機で実測済み**。導出値ではない）:

```
depth 0  Cloud Drive              label x=28
depth 1  └ Test Folder            label x=48
depth 2    └ my second folder     label x=69   （導出値 68、AA 分の誤差）
depth 3      └ bar                label x=89   （導出値 88）
depth 4        └ this is a long na…    label x=108  ← 修正前はここで切断
depth 5          └ last node      label x=129  （導出値 128）
```

3-2 で確定した式 `leftPadding = 4 + depth*20 + 20 + 4` は 6 階層すべてで実測と ±1px で一致し、
**導出は正しかった**ことが確認できた（§11 の「6 階層ツリーの再実測」はこれで解消）。

※ 2 回目の調査で記録していた `label x=31/51/71/90/131` は古いバイナリ（`leftPadding` が
30 起点）の値。差は 2〜3px なので、切断が起きるという結論自体は変わらない。

原因: `TreeViewDelegate` の幅が `implicitWidth`（コンテンツ幅）で決まるため、ラベルに
「縮められる上限」が伝わらず `elide` が発動しない。`TreeView` 自体は `clip: true`
（`FolderTreePanel.qml:33`）なので、はみ出した分は単に切り落とされる。

さらに **横スクロールバーも縦スクロールバーも付いていない**（`FolderTreePanel.qml` に
`ScrollBar` の記述が一切ない）ため、切れた名前を読む手段が「SplitView を広げる」しかない。

**修正済（S0 / 2026-08-03）**: デリゲート幅をビューポート幅に固定し、**ホバー時にツールチップで
全名を出す**ようにした。実測で `this is a long na…` と省略され、ホバーで「this is a long name
folder」が出る。

実装上の発見: **Basic の `TreeViewDelegate` の stock `contentItem` は最初から
`elide: Text.ElideRight` を持っていた**（`Basic/TreeViewDelegate.qml:61-67`）。デリゲートが
自分のコンテンツ幅で採寸されていたため、ラベルが常に要求どおりの幅をもらえて elide が発動する
余地がなかっただけ。つまり幅を固定するだけで省略記号は出るようになり、`contentItem` の差し替えは
**ツールチップを付けるためだけ**に必要だった。

この選び方の効果は名前の切断だけにとどまらない:

- デリゲート幅を固定するので **B3（ハイライト幅が `contentWidth` 追随）も同時に解消**する。
- 横スクロールが発生しなくなるので、**B9（左ドラッグでのパン）も横方向については論点が消える**
  （縦方向のドラッグパンは残るので、他ビューと揃えて無効化する判断は別途必要）。
- MEGA のフォルダー名は長くなりがちなので、(a) 単独（ツールチップなし）だと全名を読む手段が
  「SplitView を広げる」しか残らない。ツールチップは事実上必須。

見送った案: **(b) 横スクロール**は Explorer のナビゲーションペインにない操作で、しかも B3 の
「行背景をビューポート幅に固定する」修正と併用すると `contentX` 追従の実装が別途必要になる。

なお **`ScrollBar.vertical` は (c) を選んでも必須**（B5。フォルダー数が増えたときにスクロール
可能であることが現状まったく分からない）。4-2 のファイル一覧と同じ指摘。→ S0 で追加済み
（1200x430 まで縮めてツリーを溢れさせ、ホイール操作で右端に出ることを実測）。横スクロールバーは
(c) により不要になったので追加していない。

### 3-9. インデントが 1 階層 20px あり、深い階層で名前の置き場がなくなる

インデント量は 1 階層あたり **20px**。3-2 で確定したとおり、これは直接書かれた値ではなく
`indentation: indicator ? indicator.width : 12` により **indicator の幅がそのまま流用されている**
（`indicator.implicitWidth: 20`）。`depth 5` ではラベル開始位置が x=128 となり、220px 幅の
パネルに対して名前用の幅が **92px しか残らない**（3-8 の切断はこれが直接の引き金）。

**修正案**: `TreeViewDelegate.indentation` を明示的に 16px に落とす（Windows 11 ナビゲーション
ペインと同値）。`leftPadding` は `4 + depth*16 + 20 + 4` となり、`depth 5` で
**92 → 112px** に増える。

> **D1b との関係（重要）**: D1b は「グリフだけ縮小し、当たり判定の `Item` は幅 20px を維持」と
> 決めた。つまり `indicator.width` は 20px のままなので、**`indentation` を明示的に書かない限り
> インデントは 20px から動かない**。「シェブロンを小さくすればインデントも詰まる」は
> D1b の下では成立しないので、`indentation: 16` を必ず明示すること。

### 3-10. 階層の手がかりが「インデントだけ」しかない

6 階層並ぶと、どの行がどの親に属するのかインデント量を目測するしかない。アイコン（3-5）も
インデントガイド線もなく、chevron は暗くて小さい。

**修正案**: 各階層に 1px の縦ガイド線（インデント位置に配置）を入れる。
色は S3 で `strokeSubtle` を削除したので、`stroke` で試して強すぎるなら**この用途に合わせた値で
弱い線トークンを再導入する**（§0-1 の経緯を参照 — 消費者のいない推測値を先に置かないこと）。
VS Code / 各種 IDE のツリーと同じ表現で、深い階層の追従が一気に楽になる。3-5 のフォルダー
アイコンと合わせると、階層の視認性はほぼ解決する。

### 3-11. ツリーだけ左ドラッグでパン（横スクロール）できてしまう（要検証）

ファイル一覧の 2 ビューは `acceptedButtons: Qt.NoButton` で Flickable のドラッグパンを
明示的に殺している（`FileTableView.qml:433`, `FileGridView.qml:39`）が、
`FolderTreePanel.qml` の `TreeView` にはその指定がない。Flickable の既定は
`Qt.LeftButton` なので、**ツリーだけ行を左ドラッグすると内容がパンする**はず。
Explorer のナビゲーションペインにこの挙動はなく、ビュー間で一貫していない。

D2 = (c) によりデリゲート幅がビューポート幅に固定されるので、**横方向のパンは発生しなくなる**。
残るのは縦方向のドラッグパンで、これは他の 2 ビューと揃えて `acceptedButtons: Qt.NoButton` で
無効化するのが筋。

**修正済（S0 / 2026-08-03）**: `acceptedButtons: Qt.NoButton` を追加。ツリーが溢れた状態
（1200x430）で行を 130px 上方向にドラッグしても、ツリー領域のピクセル差分はゼロ。ホイール
スクロールは従来どおり効く（`Flickable.acceptedButtons` はドラッグのみを対象とする）。

## 4. ファイル一覧（詳細表示） — `FileTableView.qml`

### 4-1. 選択行のハイライトが行の途中で切れる ★重大

実測: 1200px 幅で行を選択すると、ハイライトは x≈975（= 全列幅の右端）で終わり、そこから右
225px は塗られない。行の右端がどこか分からず、クリック可能領域（実際は列の右外もヒットする
— `FileTableView.qml:534`）とも一致していない。

**修正済（S0 / 2026-08-03、(a) 案）**: `columnWidthProvider` を書き換え、**名前列がビューポートの
残り幅を吸収する**ようにした（日付列・サイズ列は従来どおり固定幅 + 永続化）。列幅の合計が
ビューポート幅と一致するので、セル背景がそのまま行いっぱいに伸び、4-2 も同時に閉じる。実測で
1200px 幅の選択ハイライトは x=222–1199（ビュー右端）まで届く。

**代償**: 名前列の右端をドラッグしても何も起きなくなった（provider が列 0 の明示幅を無視する
ため）。日付列・サイズ列をリサイズすると名前列が連動して伸縮する形になる。永続化されている
`columnWidthName` は保存・復元の配線ごと残してあるが、読まれない。

### 4-2. 列幅が可変幅に追随しない

実測: 1200px では右に 225px の死に空間。800px に縮めると Date modified が途中で切れ、
**水平スクロールバーも出ない**（`TableView` に `ScrollBar` 未接続）ので、Size 列に到達する
手段がない。

**修正済（S0 / 2026-08-03）**: 名前列を「残り幅を吸収する列」にし（4-1 参照）、`ScrollBar.vertical`
と `ScrollBar.horizontal` を両方追加した。800x600 で 3 列すべてが収まり、Size 列に到達できることを
実測で確認。横スクロールバーは、ユーザーが日付列・サイズ列を極端に広げて合計がビューポートを
超えた場合のために残してある。

### 4-3. 行とヘッダの体裁

- 行高 28px、内側マージン 4px（`:556`, `:588`）で文字が上下に詰まる。→ 行高 32px、
  上下パディング 6px。
- ヘッダ高 32px・マージン 6px（`:391`, `:405`）に対し行はマージン 4px なので、ヘッダの
  「Name」（x=210）と行のファイル名（x=208）が **2px ずれる**。→ 同一トークンに揃える。
- ヘッダに下境界線がなく、列と列の区切りもない。→ ヘッダ下に 1px、列間に薄い縦線
  （またはヘッダ hover 時のみ）。
- ソート矢印が「▲」文字で、ラベルとの間がスペース 1 個（`:409`）。→ Segoe Fluent Icons の
  小さいシェブロンにし、ヘッダの右端寄せに置く。
- 行の hover 表現がない（背景が `transparent` 固定、`:572`）。→ hover で subtle fill。
- 交互行の塗り分けもない。Explorer にもないので必須ではないが、Size 列が右寄せなので視線の
  対応付けが弱い。ホバーが入れば十分と判断。

### 4-4. アイコンが絵文字文字列 ★ユーザー指摘に関連

実測/コード: `(cell.isFolder ? "📁 " : "📄 ") + cell.name`（`FileTableView.qml:595`）。
名前ラベルの **テキストの一部** として絵文字を連結している。問題点:

1. Segoe UI Emoji のカラー絵文字なので、モノクロの Fluent アイコンと画面内で二重基準になる。
2. アイコンと名前の間隔が「半角スペース 1 個」で、フォント依存かつ調整不能。
3. ファイル種別に関わらず全ファイルが同じ 📄。画像/動画/PDF の区別がつかない。
4. `elide: Text.ElideMiddle`（`:591`）なので、極端に狭いとアイコンごと省略される。
5. グリッド側は `font.pixelSize: 32` の絵文字（`FileGridView.qml:373-374`）で、リスト側と
   デザインが揃っていない。

**修正案**: アイコンをテキストから分離し、行デリゲートを `RowLayout`（16px アイコン +
名前ラベル）にする。アイコン自体は段階的に:

- **第 1 段階**: Segoe Fluent Icons のフォルダ/汎用ファイル グリフ（`` / ``）に
  差し替え、色は `Theme.color.accentFolder` / `textSecondary`。SVG 資産不要で即やれる。
  **D6 により、UI 整理フェーズはここまで**。上の 5 点のうち 1・2・4・5 がこれで閉じ、
  3（種別の区別がつかない）だけが残る。
- **第 2 段階（別フェーズへ先送り）**: 拡張子 → アイコン のマッピング（画像/動画/音声/
  ドキュメント/圧縮/その他）。`FileEntry` は現在
  `name`/`handle`/`sizeBytes`/`isFolder`/`modificationTime`/`hasThumbnail` のみで、種別
  フィールドを持たない。**QML 側で拡張子判定するか `FileEntry` に種別を持たせるかは、同じ
  判定を必要とするプレビュー機能（フェーズ 15）と一緒に決める** — UI 整理フェーズ内で先に
  決めると、プレビュー側の要件次第で作り直しになるため。
  ※ C++ 側に触れる場合は `IMegaClient`/`FileEntry` 越しに（`CLAUDE.md` の設計方針）。

## 5. サムネイルグリッド — `FileGridView.qml`

実測（グリッド表示のスクリーンショット）:

- **タイルの外側余白がない**: セル 120x120（`:33-34`）が隙間なく敷き詰められ、1 行目が

## 12. ライト/ダークの切り替え（S3 で追加）

S3 の主眼は「ライト側を初めて実機で見る」ことだが、確認のたびに Windows の個人用設定を
切り替えるのは現実的でない。そこで**環境変数でアプリのカラースキームを上書きできる**ようにした。

```
MEGAEXPLORER_COLOR_SCHEME=light   # または dark。未設定 / それ以外の値 = 従来どおり OS 追従
```

`main.cpp` が `QGuiApplication` 構築直後にこれを読み、`QStyleHints::setColorScheme()`（Qt 6.8+）
を呼ぶ。**これ 1 箇所で UI 全体が切り替わる** —— FluentWinUI3 自身も `Theme.qml:17` の `isLight` も
同じ `Application.styleHints.colorScheme` を見ているため、スタイルと自前トークンがずれることが
構造的にありえない（§0-1 が S1 時点で確認済みの性質がそのまま効いている）。
`ui-style` スキルの `launch` / `cycle` には `--theme light|dark|system` を足してあり、
`--size` と同じく `.session.json` に記憶される。

**将来**: 設定画面 + `QSettings` に載せ替える想定。その時も「最終的に `setColorScheme()` を
呼ぶ」という中身は変わらず、値の出どころが環境変数から設定に変わるだけ。

### 副産物: ウィンドウ外枠のテーマ追従

QWindowKit は外周 1px のネイティブボーダーに対し **`dark-mode` を常に true** で設定している
（`windows10borderhandler_p.h:42` の `setupNecessaryAttributes`、「さもないと枠が白くなる」という
コメント付き）。そのためライトにしても枠だけ暗いまま残っていた。
`QWK::WindowAgentBase::setWindowAttribute` は `Q_INVOKABLE`（`windowagentbase.h:35`）なので、
`Main.qml` から `winAgent.setWindowAttribute("dark-mode", !Theme.isLight)` を呼んで追従させた。

- **`setup()` より後**でないと効かない（それ以前はエージェントの内部コンテキストが無い）
- 実行中のテーマ変更にも追従するよう `Connections { target: Theme; onIsLightChanged }` で再適用
- vendored 側は `WM_THEMECHANGED` 時に「**すでに true なら**再適用」する作りなので、
  false を入れても勝手に true に戻されることはない

実測（DWM 合成込みでキャプチャ、同一ピクセル）: ライト `#6a5254` / ダーク `#4d454c`。
Windows 11 の枠は半透明で背後の壁紙と混色するため絶対値はきれいなグレーにならないが、
**ライトのほうが一貫して明るい**ことは確認できる。
