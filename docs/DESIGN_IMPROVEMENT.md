調査方法: `ui-style` スキルで実機起動（1200x800 / 800x600、ライトではなく Windows のダーク
テーマ追従）→ スクリーンショットをピクセル単位で実測 + QML ソースの読解。以下の「実測」は
すべて DPI 100% 時の物理ピクセル値。

3-4 / 3-8 / 3-9 の数値を実測し直した（ツリー行高は 24px ではなく **50px**、ラベル左端 **x=28**、
スタイル実装は Fusion ではなく **Basic**）。

> **計測前に必ずリビルドすること。** `ui-style` の `launch` はビルドしないので、直前の
> `cmake --build` を経ていないと古いバイナリを測る。close → build → launch → shot を 1 コマンドで
> 行う `cycle` を使う。この取り違えで 2 回連続して誤った数値をこのドキュメントに書いている。

**2026-08-03 に S0（B1〜B9）/ S1 / S2 / S3 / S4 / S5 / S6 / S6a を実装した。** 各段階の内容・変更

  ガイド線が本当に弱い線を要るなら **S5 でその用途に合わせて値ごと再導入する** —— 消費者ゼロの

### 0-2. すべての面（サーフェス）が同一色で、境界線が 1 本もない

実測（1200x800、ダーク）:

- キャプションバー背景 = ツールバー背景 = サイドパネル背景 = コンテンツ背景 = **すべて
  `#202020`**
- y=36（キャプション下端）、y≈80（ツールバー下端）、y≈752（フッター上端）に境界線 **なし**
- SplitView のハンドルだけ x=202–203 に 2px の `#1c1c1c` があるが、`#202020` との差が 4/255
  しかなく事実上見えない

つまり「どこからどこまでが何の領域か」を示す視覚情報がゼロ。ユーザー指摘の「各境界に境界線が
ない」はこれ。

~~**修正案**~~ → **修正済（S3 / 2026-08-03）**。3 点とも実施した。

1. **面の色を分ける**（**D3 で確定**） — サイドパネル・キャプション行・**フッター**を
   `surfaceAlt`、ツールバー行とファイル一覧側を `surface`。
   **鍵は「ウィンドウ自体の `color` を `surface` にする」こと**: 一覧側の 5 領域
   （`TabContentPane` / `FileTableView` / `FileGridView` / `Breadcrumb` / `LoginView`）は
   どれも背景を描いておらずウィンドウ色に落ちていたので、`Main.qml` の
   `ApplicationWindow.color` 1 行で片付いた。自前で塗るのはそこから外れる 2 領域
   （サイドパネル・フッター）だけ。
2. **1px の区切り線を入れる** — 4 箇所すべて `Theme.color.stroke`。
   **キャプション下の線は S2 との噛み合わせがある**: アクティブタブの角丸背景は不透明な
   `surface` でキャプション下辺と面一（§1-1/§1-2）なので、線を**背景 `Rectangle` の内側**
   （= `TabStrip` より下の z）に描くと、アクティブタブがその上を塗って**線が自動的に途切れる**。
   Chrome / Explorer 11 と同じ見え方で、追加の重ね描きやマスクは不要だった。
3. SplitView のハンドルは **`handle:` デリゲート自体が存在しなかった**（Fluent 既定の 2px）。
   当たり判定と見た目を分離し、`implicitWidth: 6` の掴み代の中に 1px のラインを置いた。
   ホバー/ドラッグ中は `border.drop`(2px) + `accent` に太る。
   **ラインは中央ではなく右端に置く**: ハンドルを透明にすると線の両側が同じ `surface` になり、
   線が面の境界から 2px コンテンツ側にずれて見える。ハンドルを `surfaceAlt` で塗ってパネルの
   延長にし、線をその右端に置くことで境界と一致する。自前デリゲートにするとスタイル既定の
   リサイズカーソルが失われるので `HoverHandler { cursorShape: Qt.SplitHCursor }` を付けている。

### 0-3. Fluent 標準コントロールの一部だけを上書きしていて、寸法体系が混在している

`FileTableView` のセル、`FolderTreePanel` の背景、`FileGridView` のタイルは背景を自前の
`Rectangle` に差し替えているが、パディング・ホバー表現・背景の伸び方は Fluent 既定のまま。
結果、同じ「行」でもコンポーネントごとに高さ（ピン **24** / ツリー **50** / テーブル 28）も
内側パディング（4/6）も背景の横幅の決まり方（3-3）も揃っていない。

しかも `FolderTreePanel.qml` の 50px は**意図した値ですらない** — スタイル既定の indicator が
そのまま行高になっている（3-2）。上書きの仕方が中途半端だと、既定値がどこから来ているのか
書いた本人にも見えなくなる、という典型例。

なお **フォントサイズ自体は揃っている**（3 回目の調査でも再確認: 文字の ink 高がツリー行 /
ピン行とも 11px で一致）。バラついているのは行高・パディング・背景の描画範囲であって、
文字サイズではない。

~~**修正案**: 「行」の見た目を担う共通コンポーネント（例 `qml/components/RowSurface.qml`）を
1 つ作り、選択/ホバー/ドロップ受け入れの 3 状態と行高・角丸・パディングをそこに集約する。~~
→ **S5-c で見送りに決定（2026-08-03）**。S5 でツリー行とピン行を Theme トークン参照

なる公算が高い。**共通化するなら S6/S8 で実際の要件が出そろってから**、という判断

### 1-1. アクティブタブのインジケータがキャプション行の外にはみ出している ★重大

実測: キャプションバー高 36px（`CaptionBar.qml:32`）に対し、アクティブタブの下線インジケータが
**y≈41–45**（ツールバー行の領域）に描画されていた。原因は `TabStrip` の `TabBar` に
`Layout.fillHeight` がないこと（`TabStrip.qml:57-59`）で、`CaptionBar` 側が 36px に固定していても
内側の `TabBar` は自分の implicitHeight のまま配置され、`clip` もされていないので下にはみ出す。

**修正済（S0 → S2 / 2026-08-03）**: `TabBar` に `Layout.fillHeight: true` を付け、キャプション高を
36→48px（S0）→ **40px**（S2）にした。48px は Fluent の自然高（`TabButton` は label 20 + 上下
padding 10 = **40 固定**、`TabBar` がさらに上下 4px。`FluentWinUI3/Config.qml`）で、40px に
収めるには padding を潰す必要があり、§0-3 の「標準コントロールの寸法の一部だけを上書きする」
パターンになるため S0 では見送った。S2 で `TabButton.background` を差し替えるのと同時に
**`TabBar.topPadding` 4 + `TabButton` 36 + `TabBar.bottomPadding` 0 = 40** として実施。

下 padding を 0 にしたのは高さ合わせのためだけではなく、これが §1-2 の「アクティブタブの下辺は
コンテンツと地続き」の実装そのものだから — 下に余白があるとタブがキャプション行の中に浮き、
角丸タブがツールバー行へ繋がらない。`TabButton` 側は Fluent の 12/12/10/10 に対し
**上下 8 / 左 12 / 右 4**（右だけ詰めるのは閉じるボタンの置き場）。

### 1-2. インジケータの位置とラベルの位置が噛み合っていない

実測: タブ幅 200px に対し、ラベル "Cloud Drive" は x≈16 から左寄せ、インジケータは x≈92–108
（タブの中央）。左寄せテキストの下に短い中央寄せの下線があるので、どのタブが選択中なのか
視線で結び付かない。

~~**修正案**~~ → **修正済（S2 / 2026-08-03）**: Explorer 11 / Chrome 方式を採り、アクティブタブを
**背景を `Theme.color.surface` で塗った角丸タブ**（上 2 角だけ角丸、下辺はコンテンツと地続き）に
した。下線方式の代案は採っていない。

実装上の発見が 2 つある。

1. **Fluent のインジケータは `background` の中に住んでいる**（`TabButton.qml` の
   `Impl.StyleImage` が持つ `selector` プロパティ）。つまり **`background` を差し替えれば下線は
   自動的に消える** — 別途消す処理は要らなかった。
2. `StyleImage` 自体は **何も描いていない**（`filePath` が全 8 状態で空、対応する PNG も無い）。
   にもかかわらず implicit 77x40 の下駄を履かせていて、これが `TabButton` の最小幅・最小高を
   決めていた。差し替えでこの下駄も外れる。`TabBar` 側の `background` も同様に空の
   `StyleImage`（implicit 470x48）なので `background: null` にして外した。

角丸は Qt 6.7+ の `bottomLeftRadius`/`bottomRightRadius` を 0 にするだけで済み、従来よくやる
「下辺を四角い矩形で塗り潰して隠す」重ね描きは不要だった。

なお Fluent の `TabButton` は**ホバー時の背景を持たない**（`contentItem` の文字色 alpha だけで
表現している）。背景を自前化するとその表現ごと失われるので、`Theme.color.subtleHover` /
`subtlePressed` を新設して塗りで置き換えている（§0-1 の追加トークン表を参照）。

### 1-3. タブの閉じる「×」が描画されていない ★重大

実測: タブ幅 200px の全域を拡大しても × が一切見当たらない。`TabStrip.qml:109-115` で 22x22 の
`ToolButton` を `contentItem` の `RowLayout` に入れているのに出ていなかった。

**原因（S0 で確定）— 1-1 とは別物だった。** Fluent の `ToolButton` は左右 padding が 11px ずつ
（`Config.qml` の `controls.toolbutton`）ある。そこに `implicitWidth: 22` を強制していたため
`availableWidth = 0` となり、「×」が幅ゼロに潰れて省略されていた。これも §0-3 の
「Fluent の寸法の一部だけを上書きする」パターンの一例。

**修正済（S0 / 2026-08-03）**: 強制サイズをやめ、Fluent の自然サイズに戻した。ただし
`contentItem` の中に置いたままだと**別の副作用が出る**: `TabButton.implicitHeight` は
`implicitContentHeight` から導かれ、Fluent は content 行をラベルだけの 20px に合わせているので、
32px の `ToolButton` を入れるとタブ自体が 52px に膨らみ、B1 のインジケータが再びクリップされる。
そのため**閉じるボタンは `contentItem` の兄弟**（`TabButton` 直下の子）として `anchors.right` +
`verticalCenter` で置き、ラベル側は右マージンでその分を空ける形にした。

**S2 で「アクティブ / ホバー中のタブのみ表示」も実施**（`visible: tabButton.checked ||
tabButton.hovered`。`hovered` は閉じるボタン上も含むので、カーソルを乗せた瞬間に消える事故は
起きない）。その際 20x20 に縮めるのに `padding: 2` と書いて **B2 を一度再発させている** —
Fluent の `ToolButton.qml` は `leftPadding: __config.leftPadding || 0` のように **4 辺を個別に
束縛している**ため、まとめ書きの `padding` は負けて 11 のまま残る。4 辺を個別に書いて解消した。
**B2 の教訓は「implicitWidth を強制するな」ではなく「Fluent が個別に束縛している値は個別に
上書きしろ」**。あわせて `background` も自前の `Rectangle` に差し替えている（Fluent の
`ButtonBackground` は implicit 32x32 を持ち、padding を詰めるだけでは 32px を下回れない）。

## 3. サイドパネル（`SidePanel.qml`, `QuickAccessSection.qml`, `FolderTreePanel.qml`）

### 3-1. パネル全体に外周マージンがない

実測: 「Quick access」ラベルの左端 x=8、ツリー行の文字左端 x=28、パネル右端は SplitView
ハンドル（x=202）まで詰まっている。上端も y=88 のツールバー直下から即コンテンツ。

~~**修正案**~~ → **修正済（S5 / 2026-08-03、S5-a）**。行の左右 4px インセット + 角丸 4px のピルに
した。パネル上下の余白は `TreeView` の `topMargin`/`bottomMargin`（= Flickable のマージン）で
4px 取っている —— padding ではなく margin にしたのは、余白がコンテンツと一緒にスクロールする
ようにするため。

インセットは背景 `Rectangle` に `x`/`width` を書くのではなく **`Control` の `leftInset`/
`rightInset`** で入れた。`Control` は background の矩形を inset だけ内側に置き直すので、
padding（= ラベル位置）にもクリック判定にも影響しない —— 「見た目は 4px 内側、当たり判定は
全幅」がそのまま出る。実測で選択ピルは x=4..215（パネル幅 220 に対し左右 4px）。

ホバー塗り（`Theme.color.subtleHover`）もここで入れた。従来ツリー行にはホバー表現が一切なく、
背景を自前化したせいでスタイル既定のそれも失われていた（§0-3 / §0-1 の `subtleHover` の項）。

### 3-2. ツリー行が 50px と高すぎる ★ユーザー指摘（原因を式レベルで特定）

この節は 2 度訂正している。初報の「ツリーの文字が大きい」も 2 回目の「行高 24px」も誤りで、
**フォントサイズは同一・行高は 50px**、原因はスタイル既定の indicator であることを 3 回目
（リビルド後）に式レベルで特定した。

#### 実測値（1200x800、DPI 100%、リビルド後）

| 項目 | ツリー | クイックアクセス |
|---|---|---|
| **行高** | **50px** | **24px** |
| ラベル左端 | x=28 | x=20（**8px ずれ** → 3-4） |
| 文字の ink 高 | 11px | 11px（**同一**） |
| シェブロンの ink | **10 × 16px** | — |
| 選択ハイライトの幅 | 123px（`contentWidth` 追随 → 3-3） | 行幅いっぱい |

**フォントサイズの不統一は存在しない**（ink 高が両方 11px）。一方で **行高は 2 倍以上**、
**シェブロンは文字の 1.45 倍**ある。ユーザーが「文字が大きい」と感じたのは、文字ではなく
**行とアイコンが大きい**ことの裏返しだった。

#### 原因: `background` の `implicitHeight` は効いていない

`FolderTreePanel.qml` の `TreeViewDelegate` は、FluentWinUI3 ではなく **Basic スタイル**の実装に
解決されている（FluentWinUI3 は `TreeViewDelegate.qml` を持たないため）。実測値が Basic の式と
完全に一致することで確認した:

```qml
// QtQuick/Controls/Basic/TreeViewDelegate.qml
implicitHeight: Math.max(indicator ? indicator.height : 0, implicitContentHeight) * 1.25
indentation: indicator ? indicator.width : 12
leftPadding: leftMargin + __contentIndent        // = 4 + depth*20 + 20 + 4
indicator: Item { implicitWidth: 20; implicitHeight: 40 }   // ← 行高の支配項
```

| 式 | 計算 | 実測 |
|---|---|---|
| `implicitHeight` | `max(40, 19) * 1.25` = **50** | 50 ✓ |
| `indentation` | `indicator.width` = **20** | 20 ✓ |
| `leftPadding`（depth 0） | `4 + 0 + 20 + 4` = **28** | 28 ✓ |

決定的なのは、**Basic の `implicitHeight` の式に `implicitBackgroundHeight` が入っていない**こと。
つまり `FolderTreePanel.qml:87-88` の

```qml
background: Rectangle { implicitHeight: 24 }
```

は **一切効いていない**。同ファイル 84-86 行の「implicitHeight restates what the style's
background supplies」というコメントは**誤り**で、削除するか正しい説明に置き換えること。
→ **S0 で対応済み**（無効な `implicitHeight: 24` を削除し、コメントを「Basic の式に background
の項がないので、ここに書いた implicitHeight は無視される」という正しい説明に差し替えた）。
（ピン行の `QuickAccessSection.qml:83` は `ItemDelegate` **自身**に `implicitHeight: 24` を
書いているので、こちらは意図どおり効いている。この非対称が「揃っていない」の正体。）

もう一点、`indicator` の 40px は**見えているシェブロンの大きさではない**。Basic のコメントが
"Create an area that is big enough for the user to click on, since the image is a bit small" と
明記しているとおり、**クリック領域を確保するための透明な `Item`** であり、シェブロン画像は
その中央に置かれた小さい子要素。だから「アイコンを小さくすれば行が縮む」というより、
**当たり判定の `Item` が行高を決めている**。

#### 修正方針（D1a / D1b で確定）

1. **行高を 28px に統一**（ツリー 50→28、ピン 24→28）。`background` ではなく
   **デリゲート自身の `implicitHeight`** に書く。Basic の式は `max(...) * 1.25` なので、
   indicator を縮めるだけでは狙った値に着地しない — 明示指定が必須。
2. **シェブロンはグリフだけ縮小**し、ink 高を文字と同等（10〜11px）にする。
   **当たり判定の `Item` は幅 20px を維持**する（グリフごと縮めるとクリックしづらくなる）。
3. ツリー行とピン行の両方に**明示的にフォントを指定**して、スタイル既定への暗黙依存をやめる
   （現状は偶然一致しているだけで、スタイル更新で崩れうる）。
4. 行頭に 16px のフォルダーアイコンを追加（3-5）、インデントを 16px に（3-9）。

> **実装上の注意**: `indicator` を差し替えるとき、`FolderTreePanel.qml` 冒頭のコメントが
> 警告しているのは `pointerNavigationEnabled: false` + 自前 `TapHandler` の話であって、
> `indicator:` を別 `Item` に差し替えること自体ではない。stock のポインタ処理は indicator の
> 矩形を見て展開/折りたたみを判定するので生き残るはずだが、**S5 の着手時に実機で要確認**。
> また `indentation: indicator.width` なので、D1b で `indicator.width` を 20px のまま残すなら
> **`indentation` を明示的に 16 と書かないとインデントは 20px のまま**になる。
>
> → **S5 で実機確認済み（2026-08-03）: 差し替えても展開/折りたたみは生きていた。** 上の
> 予想どおり、判定は indicator の矩形に対して行われている。`indentation: 16` の明示が必須
> だという点も予想どおり。

**修正済（S5 / 2026-08-03）**。4 点とも実施した。

1. `implicitHeight: Theme.rowHeight.compact`（28）を**デリゲート自身**に書いた。実測 28px。
2. `indicator` を Basic の実装ごと写して `ColorImage`（arrow-indicator.png）を
   **Segoe Fluent Icons のシェブロン**（`` / ``）に置き換えた。`Item` は
   `implicitWidth: 20` を維持（D1b）、`implicitHeight` は行高と同じ 28。
   実測でグリフの ink は **6×10px**（従来 10×16、本文 11px より小さい）。
   **`implicitHeight` に `treeDelegate.height` を束縛しないこと** —— デリゲートの高さは
   `implicitHeight` 由来なので束縛ループになる。Theme の定数を直接書く。
   回転ではなく 2 グリフを使ったのは、回転だと `transformOrigin` の調整が要るのに対し
   フォントが両方持っているため。
3. ツリー / ピン両方のラベルに `font.pixelSize: Theme.font.body` を明示し、色は
   `palette.buttonText` → `Theme.color.text`（§0-1 が S5 で確認せよとしていた差し替え。
   ライト / ダーク両方で見え方に問題なし）。

### 3-8. 深い階層でフォルダー名が省略記号なしで切り落とされる ★重大（今回の追加調査で判明）

途中で切れているため、名前が長いのか切れているのかすら分からない。

構造（**S0 着手時に 6 階層すべてを実機で実測済み**。導出値ではない）:

```
depth 0  Cloud Drive              label x=28
depth 1  └ Test Folder            label x=48
depth 2    └ my second folder     label x=69   （導出値 68、AA 分の誤差）
depth 3      └ bar                label x=89   （導出値 88）
depth 4        └ this is a long na…    label x=108  ← 修正前はここで切断
depth 5          └ last node      label x=129  （導出値 128）
```

3-2 で確定した式 `leftPadding = 4 + depth*20 + 20 + 4` は 6 階層すべてで実測と ±1px で一致し、
**導出は正しかった**ことが確認できた。

原因: `TreeViewDelegate` の幅が `implicitWidth`（コンテンツ幅）で決まるため、ラベルに

`ScrollBar` の記述が一切ない）ため、切れた名前を読む手段が「SplitView を広げる」しかない。

**修正済（S0 / 2026-08-03、D2 = (c)）**: デリゲート幅をビューポート幅に固定し、**ホバー時に
ツールチップで全名を出す**ようにした。MEGA のフォルダー名は長くなりがちで、ツールチップが
ないと全名を読む手段が「SplitView を広げる」しか残らないため事実上必須。見送った **(b) 横
スクロール**は Explorer のナビゲーションペインにない操作で、B3 の修正と併用すると `contentX`
追従の実装が別途必要になる。

実装上の発見: **Basic の `TreeViewDelegate` の stock `contentItem` は最初から
`elide: Text.ElideRight` を持っていた**（`Basic/TreeViewDelegate.qml:61-67`）。デリゲートが
自分のコンテンツ幅で採寸されていたため elide が発動する余地がなかっただけで、幅を固定すれば
省略記号は出る。`contentItem` の差し替えは**ツールチップを付けるためだけ**に必要だった。

この 1 修正で **B3（ハイライト幅の `contentWidth` 追随）も同時に解消**し、横スクロールも
発生しなくなるので **B9 の横方向の論点も消える**（縦方向のドラッグパンは別途無効化が必要）。
なお **`ScrollBar.vertical` は (c) を選んでも必須**（B5）で S0 で追加済み。横スクロールバーは

### 3-12. 開閉シェブロンが常時表示（Explorer はホバー時のみ）

### 4-4. アイコンが絵文字文字列 ★ユーザー指摘に関連

### 4-5. 列のリサイズが両方の境界で破綻している ★重大（S6 後に判明）

2026-08-03、S6 の完了後にユーザーが発見。**S6 の変更が原因ではない**（`columnWidthProvider`
まわりは S6 で 1 行も触っていない）。**S0 の 4-1 で入れた「名前列が残り幅を吸収する」設計の
そのままの帰結**で、S6 以前からこうなっていた。

症状:

- **Name / Date modified の境界はドラッグしても無反応**
- **Date modified / Size の境界をドラッグすると Date 側が伸縮する**。しかも掴んだ境界自体は
  動かず、**隣（Name / Date）の境界が逆方向に動く**

原因は、`TableView` のリサイズハンドルが**「その境界の左側の列」の明示幅を書き換える**のに対し、
provider が列 0 の明示幅を読まないこと:

| 境界 | ハンドルが書く列 | provider の扱い | 見え方 |
|---|---|---|---|
| Name / Date | 列 0 = Name | **無視される**（列 0 は導出値） | 完全に無反応 |
| Date / Size | 列 1 = Date | Date は伸びるが Name が同量縮む | 掴んだ境界は動かず隣が逆に動く |

**「Name が残り幅を吸収する」限り、両方の境界が必ずおかしくなる** —— Name の幅が他 2 列から
導出される以上、Name 側の境界は原理的に動かせない。§4-1 が「代償」として記録していた
「名前列の右端をドラッグしても何も起きない」は、この現象の片割れでしかなかった。

~~**修正案（S6a 着手時にどちらか選ぶ）**~~ → **(B) を採用（S6a-a / 2026-08-03）**。
候補は 2 つあった:

- **(A) 吸収する列を最後尾（Size）に移す** —— provider の 5 行だけ。`QHeaderView` の
  「最後のセクションを Stretch」と同じ形で、両方の境界がポインタに追従するようになる。
  ただし 1200px 幅で Size 列が約 600px になり、**S6-d で左寄せにした「Size」ヘッダ文字が
  右寄せの数値から 500px 以上離れて宙に浮く** → S6-d の再検討がほぼ必須。**不採用**。
- **(B) Explorer 本来の形に戻す** ← **採用**。3 列とも明示幅にして右側に余白を残す。
  見た目が最も Explorer に近く、S6-d も維持できる。**S0 の §4-1 の決定を覆す**。

### (B) の実装（S6a / 2026-08-03）

変更は `FileTableView.qml` 1 ファイルに閉じた。`Theme.qml` へのトークン追加も **0 個**
（S6 が `chevronUp` 1 個で済んだのに続き、既存トークンだけで足りた）。列幅の永続化配線
（`Settings` ⇄ `Main.qml` → `TabContentPane` → `FileTableView`）は 3 列とも元から生きており、
**これまで「保存はされるが読まれない」だった `columnWidthName` がようやく消費されるように
なった**だけで、配線側は 1 行も触っていない。

| # | 内容 |
|---|---|
| 1 | `columnWidthProvider` を `column => root.columnWidthFor(column)` に。`fixedColumnWidth` は列 0 を特別扱いしなくなったので `columnWidthFor` に改名し、インラインだった `[220, 150, 100]` は `defaultColumnWidths` に切り出した |
| 2 | **S6a-b**: `fitNameColumnOnce()` —— 未設定のときだけ初回レイアウトで Name をビューポートに合わせる。`Component.onCompleted` と `TableView.onWidthChanged` の 2 箇所から呼び、`completed` / `nameWidthInitialized` / `columnWidthName >= 0` の 3 ガードで 1 回に収束させる |
| 3 | セルの `trailing`（§4-1 参照）で行の塗りを右端まで伸ばす |
| 4 | ホバー判定を**ビューポート単位の `HoverHandler`** に移した（下記） |
| 5 | ドロップ枠を**行に 1 本**に（下記） |
| 6 | **S6a-c**: 横スクロールバーを条件付き `AlwaysOn`（§4-2 に詳細） |

**ホバーがセル単位では成立しなくなった**: S6 は「3 枚のセルが `hoverRow` を書き合う」形で
行全体を光らせていたが、最終列の右の帯にはデリゲートが無いので届かない。S6 が
「死に空間が消えたので不要」として見送った**ビューポート単位の `HoverHandler` +
`cellAtPosition`** に戻した —— 結果としてセル 3 枚の相互書き込みは消え、view-level の
`TapHandler` / `DropArea` と**同じ `rowAt()` を共有する**形になって、むしろ短くなっている。
ただし 1 点だけ補いが要る: ポインタを止めたままホイールでスクロールすると点イベントが
飛んでこないので、`TableView.onContentYChanged` からも `refreshHoverRow()` を呼んでいる
（セル単位の実装ではデリゲートの移動が勝手に面倒を見てくれていた部分）。

**ドロップ枠の既存の不整合もここで潰した**: 現行コードは `anchors.fill: parent` + 全周
ボーダーを**セルごとに**描いており、「Top/bottom only, so adjacent cells of the same row join
into one band」というコメントに反して**列境界に縦線が出ていた**。(B) では枠が最終列で
止まる問題も加わるので、**列 0 のセルだけが「行頭からビューポート右端まで」の枠を 1 本描く**
形に変えた。既知の限界: 列を極端に広げて**横スクロールで列 0 を画面外へ送った状態**だと
列 0 のデリゲートが解放されて枠が消えうる（枠は `border` なので、塗りと同じ `trailing` 方式に
すると内部の縦線が戻ってしまう。この形が最も素直と判断した）。

### 教訓

4-1 は「代償」を 1 行記録したが、それが**ユーザー操作として破綻している**ことまでは
詰めていなかった。「provider で列幅を導出する」型の修正を入れるときは、**その列に付く
リサイズハンドルがどう振る舞うか**を必ず実機で確かめること。

もう 1 つ、S6a-c で見つかったほうが射程が広い: **「例外的にしか起きない状態」への対処は、
その状態を実際に作って確かめない限り効いているとは言えない**。S0 は横スクロールバーを
「日付列・サイズ列を極端に広げた場合のために残してある」と書いたが、そう書いた状態を
実機で作ってはいなかったので、**そもそも出てこない**ことに S6a まで気づかなかった。

## 12. ライト/ダークの切り替え（S3 で追加）

S3 の主眼は「ライト側を初めて実機で見る」ことだが、確認のたびに Windows の個人用設定を
切り替えるのは現実的でない。そこで**環境変数でアプリのカラースキームを上書きできる**ようにした。

```
MEGAEXPLORER_COLOR_SCHEME=light   # または dark。未設定 / それ以外の値 = 従来どおり OS 追従
```

`main.cpp` が `QGuiApplication` 構築直後にこれを読み、`QStyleHints::setColorScheme()`（Qt 6.8+）
を呼ぶ。**これ 1 箇所で UI 全体が切り替わる** —— FluentWinUI3 自身も `Theme.qml:17` の `isLight` も
同じ `Application.styleHints.colorScheme` を見ているため、スタイルと自前トークンがずれることが
構造的にありえない（§0-1 が S1 時点で確認済みの性質がそのまま効いている）。
`ui-style` スキルの `launch` / `cycle` には `--theme light|dark|system` を足してあり、
`--size` と同じく `.session.json` に記憶される。

### 副産物: ウィンドウ外枠のテーマ追従

QWindowKit は外周 1px のネイティブボーダーに対し **`dark-mode` を常に true** で設定している
（`windows10borderhandler_p.h:42` の `setupNecessaryAttributes`、「さもないと枠が白くなる」という
コメント付き）。そのためライトにしても枠だけ暗いまま残っていた。
`QWK::WindowAgentBase::setWindowAttribute` は `Q_INVOKABLE`（`windowagentbase.h:35`）なので、
`Main.qml` から `winAgent.setWindowAttribute("dark-mode", !Theme.isLight)` を呼んで追従させた。

- **`setup()` より後**でないと効かない（それ以前はエージェントの内部コンテキストが無い）
- 実行中のテーマ変更にも追従するよう `Connections { target: Theme; onIsLightChanged }` で再適用
- vendored 側は `WM_THEMECHANGED` 時に「**すでに true なら**再適用」する作りなので、
  false を入れても勝手に true に戻されることはない

なお Windows 11 の枠は半透明で背後の壁紙と混色するため、実測値はきれいなグレーにならない。

### 実装メモ

- `ui_shot.py` の `do_build` が cp932 コンソールに非 ASCII を含むビルド診断を出そうとして
  `UnicodeEncodeError` で落ちる既存の不具合を、この作業中に踏んだので併せて修正した
  （`main()` で stdout/stderr を UTF-8 + `errors="replace"` に再設定）。
- QML を再コンパイルすると Qt 自身のヘッダ（`qjsengine.h` / `qvariant.h` /
  `qjsprimitivevalue.h`）から **C4702（到達しないコード）が 9 件**出る。AOT 生成の
  `*_qml.cpp` 翻訳単位由来で、こちらのコードとは無関係。`main.cpp` / `src/` は `/W4` でクリーン。
