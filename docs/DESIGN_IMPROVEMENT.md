## 0. 総評 — 3 つの根本原因

個別の「余白が足りない」「線がない」は症状で、原因はこの 3 つに集約される。ここを直さずに
個別値だけ触ると、また同じ状態に戻る。

### 0-1. デザイントークンが存在しない

余白・角丸・行高・フォントサイズがすべて各ファイルにベタ書きされた即値で、共有の定義が一つも
ない。実際に散らばっている値:

| 種類 | 現状の値 | 出現箇所 |
|---|---|---|
| 行高 | 24 / 24 / 28 / 32 | `QuickAccessSection.qml:85`, `FolderTreePanel.qml:88`, `FileTableView.qml:556`, `FileTableView.qml:391` |
| 内側マージン | 2 / 4 / 4 / 6 / 8 | `FileTableView.qml:618,588,405`, `FileGridView.qml:349`, `QuickAccessSection.qml:49` |
| 角丸 | 4 のみ（3 箇所で個別に） | `FileGridView.qml:266,337`, `DragProxy.qml:62` |
| ハードコード色 | `"crimson"`, `"#c42b1c"`, `"#e81123"`, `"white"` | `LoginView.qml:85,123`, `CaptionBar.qml:106,110` |

**修正案**: `qml/Theme.qml`（`QML_SINGLETON` 相当の QML シングルトン。`pragma Singleton` +
`qt_add_qml_module` の `QML_FILES` に追加）を新設し、`spacing.xs/sm/md/lg`、`radius.sm/md`、
`rowHeight.compact/normal`、`font.body/caption`、`color.surface/surfaceAlt/stroke/strokeSubtle`
を一元化する。以降の全項目はこのトークンを参照する形で書く。ハードコード色のうち閉じるボタンの
赤（`#c42b1c`/`#e81123`）だけは Windows 仕様の固定値なので Theme 側に「Windows 固定色」として
名前付きで持たせる。

### 0-2. すべての面（サーフェス）が同一色で、境界線が 1 本もない

実測（1200x800、ダーク）:

- キャプションバー背景 = ツールバー背景 = サイドパネル背景 = コンテンツ背景 = **すべて
  `#202020`**
- y=36（キャプション下端）、y≈80（ツールバー下端）、y≈752（フッター上端）に境界線 **なし**
- SplitView のハンドルだけ x=202–203 に 2px の `#1c1c1c` があるが、`#202020` との差が 4/255
  しかなく事実上見えない

つまり「どこからどこまでが何の領域か」を示す視覚情報がゼロ。ユーザー指摘の「各境界に境界線が
ない」はこれ。

**修正案**:

1. **面の色を分ける** — Explorer 11 に倣い、サイドパネルとキャプション行を
   `surfaceAlt`（ダークなら `#272727` 前後、ライトなら `#f3f3f3` 前後）、ファイル一覧側を
   `surface`（`#202020` / `#ffffff`）にする。パレット直値ではなく Theme 経由で、
   `SystemPalette` のライト/ダークに応じて切り替える。
2. **1px の区切り線を入れる** — キャプション下、ツールバー下、フッター上、SplitView の
   ハンドル。色は `stroke`（既存の `SystemPalette.mid` は暗すぎるので専用トークンに）。
3. SplitView のハンドルは幅 1px の可視ラインにし、ホバー時のみアクセント色に太らせる
   （現状の 2px 不可視ハンドルより掴みやすくなる）。

### 0-3. Fluent 標準コントロールの一部だけを上書きしていて、寸法体系が混在している

`FileTableView` のセル、`FolderTreePanel` の背景、`FileGridView` のタイルは背景を自前の
`Rectangle` に差し替えているが、パディング・ホバー表現・背景の伸び方は Fluent 既定のまま。
結果、同じ「行」でもコンポーネントごとに高さ（24/24/28）も内側パディング（4/6）も背景の
横幅の決まり方（3-3）も揃っていない。

なお **フォントサイズ自体は揃っている**（実測: 同一文字列 "Test Folder" の描画幅がツリー行 /
ピン行 / ファイル一覧行のいずれも 72px、字高 11px で完全一致）。バラついているのは行高・
パディング・背景の描画範囲であって、文字サイズではない。

**修正案**: 「行」の見た目を担う共通コンポーネント（例 `qml/components/RowSurface.qml`）を
1 つ作り、選択/ホバー/ドロップ受け入れの 3 状態と行高・角丸・パディングをそこに集約する。
ツリー行・ピン行・テーブル行・グリッドタイルはそれを使う。今バラバラに書かれている
`Qt.rgba(highlight, 0.35)` の選択色（4 箇所で個別に同じ式を書いている）もここに寄せられる。

## 1. キャプションバー / タブ（`CaptionBar.qml`, `TabStrip.qml`）

### 1-1. アクティブタブのインジケータがキャプション行の外にはみ出している ★重大

実測: キャプションバーの高さは 36px（`CaptionBar.qml:32`）だが、アクティブタブの下線
インジケータ（ティール色のダッシュ）は **y≈41–45** に描画されている。つまりキャプション行の
下、ツールバー（パンくず）行の領域に重なって浮いている。

原因: `TabStrip` は `RowLayout` で、`TabBar` に `Layout.fillHeight` が指定されていない
（`TabStrip.qml:57-59`）。`CaptionBar` 側は `anchors.top/bottom` で 36px に固定している
（`CaptionBar.qml:49-51`）が、内側の `TabBar` は自分の implicitHeight（Fluent 既定で 36 より
大きい）のまま配置され、`clip` もされていないので下にはみ出す。

**修正案**: `TabBar` に `Layout.fillHeight: true` を付け、キャプション高を Explorer 11 に
合わせて 40px 程度に上げる。インジケータがキャプション内に収まることを実測で確認する。

### 1-2. インジケータの位置とラベルの位置が噛み合っていない

実測: タブ幅 200px に対し、ラベル "Cloud Drive" は x≈16 から左寄せ、インジケータは x≈92–108
（タブの中央）。左寄せテキストの下に短い中央寄せの下線があるので、どのタブが選択中なのか
視線で結び付かない。

**修正案**: Explorer 11 / Chrome 方式に寄せる。すなわちアクティブタブは「下線」ではなく
**背景を surface 色で塗った角丸タブ**（上 2 角だけ角丸、下辺はコンテンツと地続き）にする。
下線方式を維持する場合はインジケータをタブ幅いっぱい（左右 8px インセット）にする。

### 1-3. タブの閉じる「×」が描画されていない ★重大

実測: タブ幅 200px の範囲（x=0–200）を拡大しても × が一切見当たらない。`TabStrip.qml:109-115`
で 22x22 の `ToolButton` を `contentItem` の `RowLayout` に入れているのに出ていない。1-1 の
レイアウト崩れ（`contentItem` が想定より狭い/高さ不足で潰れている）と同根の可能性が高い。

**修正案**: 1-1 を直したうえで再確認。それでも出ない場合は `contentItem` を `RowLayout` から
`Item` + 明示的な `anchors` 配置に変える。併せて Explorer 同様「ホバー中またはアクティブな
タブのみ × を表示」にすると、非アクティブタブのラベル可読幅が稼げる。

### 1-4. その他

- タブ 1 枚のときも 200px 幅を占有し、しかも 1 枚しかないのに閉じるボタン等の余地だけがある。
  Explorer もタブ 1 枚時は同様なので許容だが、**タブが 1 枚のときはタブ全体を隠す**選択肢も
  ある（`tabsController.count > 1`）。
- タブとタブの間に区切りがない。非アクティブタブが 2 枚以上並ぶと境目が消える。
  → 非アクティブタブ間に 1px の縦セパレータ（Explorer 11 と同じ）。
- 「+」ボタンとタブの間隔が 0（`spacing: 0`, `TabStrip.qml:24`）。→ 4px 程度空ける。
- タブにフォルダアイコンがない。Explorer はタブにフォルダアイコンを出す。3-4 のアイコン整備と
  セットで検討。

## 2. ツールバー行（`Main.qml:152-214` / `Breadcrumb.qml`）

### 2-1. 行全体に左右マージンがない

`RowLayout` が `anchors.fill: parent`、`spacing`/`margins` 未指定（`Main.qml:153-154`）。
`ToolBar` 自体の既定パディングに委ねているため、「← Back」の左端が x≈18、検索欄の右端が
x≈1155、≡ が x≈1176 で、ウィンドウ端まで 20px 程度しかない。要素間の間隔も既定任せで不揃い。

**修正案**: `anchors.margins: Theme.spacing.md`（8–12px）＋ `spacing: Theme.spacing.sm` を明示。
ツールバー行の高さも 44px → 40px に詰めてよい（キャプション 40 と揃う）。

### 2-2. ナビゲーションボタンが「← Back」というテキストボタン

実測: `text: qsTr("← Back")`（`Main.qml:157`）。矢印が文字で、ラベルが英語のまま横に付いて
いるので幅を食い、アイコンボタンが並ぶ Explorer 風の見た目にならない。前へ/上へも無い。

**修正案**: Segoe Fluent Icons（`CaptionBar.qml:127` で既に採用済み）でアイコン化し、
戻る / 進む / 上へ の 3 ボタンを 32x32 の正方アイコンボタンとして並べる。ツールチップで
テキストを補う。※「進む」「上へ」はナビゲーション機能の追加を伴うため、見た目整理とは別
フェーズにしてもよい（`FolderNavigationController` に `canGoForward`/`goUp` が要る）。

### 2-3. パンくずの余白と区切りが不揃い

実測/コード: セグメントのラベルは `leftPadding: 4` / `rightPadding: 2`（`Breadcrumb.qml:92-93`）
で左右非対称。区切りの「>」は独立 Label でパディング 0（`Breadcrumb.qml:185-189`）。オーバー
フロー表示の «  も 4/2（`Breadcrumb.qml:73-74`）。結果、"Cloud Drive" と ">" の間だけ詰まり、
">" と次のセグメントの間だけ空く。

**修正案**:

- セグメントのパディングを左右対称（`leftPadding = rightPadding = Theme.spacing.sm`）に。
- 区切りは文字「>」ではなく Segoe Fluent Icons のシェブロン（``）にし、上下中央・
  左右 2px のパディングを明示。文字サイズも本文より 1–2px 小さく。
- 先頭に「クラウドドライブ」アイコンを置く（Explorer の PC アイコン相当）。
- セグメントにホバー時の背景（角丸 4px の subtle fill）を入れる。現在はクリックできることが
  見た目からわからない。
- ドロップ受け入れ枠が `border.width: 2` の矩形（`Breadcrumb.qml:106`）で、他所（グリッド
  タイル/ツリー行）と角丸の有無が揃っていない。→ 0-3 の共通コンポーネントに寄せる。

### 2-4. 検索欄

- 幅がツールバーの 3/10 固定比（`Main.qml:192`）。1200px 時 320px は妥当だが、800px 時は
  200px まで縮み、プレースホルダ "Search in this folder" が入りきらない（実測で末尾が切れる
  寸前）。→ `Layout.minimumWidth: 160` と、狭いときはプレースホルダを短縮するか虫眼鏡
  アイコンボタンに畳む。
- 検索アイコンがない。→ 先頭に虫眼鏡、入力中はクリア（×）を出す。

### 2-5. 「≡」（サインアウト）ボタン

テキストの ≡ でフォントサイズ既定（`Main.qml:201`）。アイコンフォント化し、Explorer の
「…（もっと見る）」に相当する位置づけであることが分かる見た目にする。

## 3. サイドパネル（`SidePanel.qml`, `QuickAccessSection.qml`, `FolderTreePanel.qml`）

### 3-1. パネル全体に外周マージンがない

実測: 「Quick access」ラベルの左端 x=8、ツリー行の文字左端 x≈31、パネル右端は SplitView
ハンドル（x=202）まで詰まっている。上端も y=88 のツールバー直下から即コンテンツ。

**修正案**: パネル上下に 4–8px、行の左右に 4px のインセットを入れ、行の背景（選択/ホバー）を
角丸 4px の「浮いたピル」にする（Windows 11 のナビゲーションペインの表現）。

### 3-2. ツリーの文字が「大きすぎる」と感じる理由 ★ユーザー指摘（初報から訂正）

**訂正**: 初報では「ツリーの文字がピン行より 1〜2px 大きい」と書いたが、これは**誤り**。
拡大画像で別々の文字列（"Test Folder" と "Cloud Drive"）を見比べた際の錯覚だった。
同一文字列で実測し直した結果:

| 場所 | "Test Folder" の描画幅 | 字高 |
|---|---|---|
| クイックアクセスのピン行 | 72px | 11px |
| ツリー行 | 72px | 11px |
| ファイル一覧の行 | 72px | 11px |

**3 者とも完全に同一**で、フォントサイズの不統一は存在しない。

では何が「大きすぎる」と感じさせているのか。原因は文字サイズではなく **行の密度** と
**文字以外の要素の不在**:

1. 行高 24px に対して字高 11px。上下の余白が 6px ずつしかなく、文字が行を占有している。
2. 行の中身が **文字だけ**（アイコンなし）。文字が行の唯一の視覚要素なので相対的に巨大に見える。
3. インデントが 1 階層 20px（3-8）なので、深い階層では文字が置ける幅が急速に減り、
   「文字がコンテナに対して大きい」印象が強まる。

比較対象の Windows 11 ナビゲーションペインは、**同じ 12px 相当のフォント**を使いつつ、
行高 32px + 16px フォルダーアイコンで、文字が行の一要素に収まっている。

**修正案（2 案、どちらかを選択）**:

- **案 A（推奨・Explorer 準拠）**: フォントサイズは据え置き、行高を 24 → 30px、行頭に 16px の
  フォルダーアイコンを追加（3-5）、インデントを 20 → 16px（3-8）。「大きく見える」原因の
  1〜3 をすべて潰す。文字の可読性は落ちない。
- **案 B（情報密度優先）**: サイドパネルを「二次的クローム」と位置づけ、Theme に
  `font.caption`（本文より 1px 小さい 11px 相当）を定義してツリー行・ピン行の双方に適用。
  行高は 26px 程度。ファイル一覧より一段小さくすることで主従が明確になる。多くのファイル
  マネージャが採るやり方だが、Windows 標準からは外れる。

いずれの案でも、ツリー行とピン行の両方に**明示的にフォントを指定**して、Fluent 既定への
暗黙依存をやめること（現状は偶然一致しているだけで、スタイル更新で崩れうる）。

### 3-3. 行の背景幅がビュー幅ではなくコンテンツ幅に追随する ★重大（初報から詳細化）

初報では「ハイライトが行幅いっぱいでない」と書いたが、階層を深くしたツリーで再実測した結果、
より正確には **行の背景幅が `contentWidth`（＝最も幅の広い行）に追随している** ことが原因と
判明した。症状が 2 通り出る:

- **浅いツリー（初報時、ルート 1 行のみ）**: ハイライトが x=0–111 で終わり、パネル幅 202px に
  届かない。半端な塗りに見える。
- **深いツリー（今回、6 階層）**: 最深行の幅がパネル幅を超えたため `contentWidth` が伸び、
  ハイライトは x=0–219 とパネル幅いっぱいになる。ただしこれは「たまたま溢れているから
  埋まっている」だけで、ビューをスクロールすれば右にはみ出した部分も塗られている。

つまりフォルダー構成によって見た目が変わる。`TreeViewDelegate` の background が
`implicitWidth`（インデント + テキスト幅）基準で、ビューポート幅を参照していないため。

**修正案**: 背景 `Rectangle` をデリゲート本体から切り離し、`x: treeView.contentX` /
`width: treeView.width` でビューポートに固定する（横スクロールしても行背景は常に画面幅）。
0-3 の共通行コンポーネント側で吸収するのが筋。

### 3-4. クイックアクセスとツリーのインデントが揃っていない

実測: ピン行のラベル左端 x≈21、ツリー第 1 階層のラベル左端 x≈31。`QuickAccessSection.qml:85`
の「ツリーの第 1 階層に揃える」というコメントに反して 10px ずれている（ツリー側は
`TreeViewDelegate` のインジケータ幅ぶんが加算されるため）。

**修正案**: ピン行にもツリーと同じ幅のインジケータ相当スペーサ（またはフォルダアイコン）を
置いて物理的に揃える。`leftPadding: 20` の即値をやめる。

### 3-5. アイコンがない

ツリー行・ピン行ともにフォルダアイコンがない。ファイル一覧（絵文字 📁）とも不整合。
→ 4-4 のアイコン整備とまとめて、16px のフォルダアイコンを行頭に置く。

### 3-6. 「Quick access」ヘッダの体裁

`font.bold: true` + `opacity: 0.7`（`QuickAccessSection.qml:53-54`）。Windows 11 のセクション
ヘッダは太字ではなく「少し小さい + アクセント寄りの弱色」。opacity で透かすと背景色が変わった
ときに濁るので、`Theme.color.textSecondary` を使う。上下マージン（6/2）も非対称。

### 3-7. クイックアクセスとツリーの区切り線が見えない・詰まっている

実測: y=135 に `SystemPalette.mid` の 1px 線があるが、`#282828` 相当で背景 `#202020` との差が
小さくほぼ不可視。しかも線の直下（y=136）からいきなりツリーの選択行が始まっており、上下の
余白が 0。

**修正案**: 線色を `Theme.color.strokeSubtle` に変え、線の上下に 4–6px の余白を入れる。または
線をやめてセクション見出し（「フォルダー」など）を置いて区切る。

### 3-8. 深い階層でフォルダー名が省略記号なしで切り落とされる ★重大（今回の追加調査で判明）

6 階層のフォルダーを入れて再確認したところ、`this is a long name…` に相当する行が
**x=219（パネル右端）で文字の途中からいきなり消える**。「…」もなく、単語の途中で切れている
ため、名前が長いのか切れているのかすら分からない。

実測した構造:

```
Cloud Drive              chevron x=14   label x=31
└ Test Folder            chevron x=34   label x=51
  └ my second folder     chevron x=54   label x=71
    └ bar                chevron x=74   label x=90
      └ this is a long nam|   ← x=219 で切断（省略記号なし）
        └ last node      chevron x=114  label x=131
```

原因: `TreeViewDelegate` の幅が `implicitWidth`（コンテンツ幅）で決まるため、ラベルに
「縮められる上限」が伝わらず `elide` が発動しない。`TreeView` 自体は `clip: true`
（`FolderTreePanel.qml:33`）なので、はみ出した分は単に切り落とされる。

さらに **横スクロールバーも縦スクロールバーも付いていない**（`FolderTreePanel.qml` に
`ScrollBar` の記述が一切ない）ため、切れた名前を読む手段が「SplitView を広げる」しかない。

**修正案**: 次のいずれか。Explorer は (b) 相当。

- (a) デリゲート幅をビューポート幅に固定し、ラベルに `elide: Text.ElideRight` を効かせる。
  名前は途中で「…」になるが、パネル幅内に必ず収まる。ツールチップで全体を出す。
- (b) 横スクロールを正式にサポートする。`ScrollBar.horizontal` を付け、切れていることを
  スクロールバーの存在で示す。深い階層でも全名を読める。
- (c) 併用: 通常は `elide`、ホバー時にツールチップで全名。

いずれにせよ **`ScrollBar.vertical` は必須**（フォルダー数が増えたときにスクロール可能で
あることが現状まったく分からない）。4-2 のファイル一覧と同じ指摘。

### 3-9. インデントが 1 階層 20px あり、深い階層で名前の置き場がなくなる

実測: chevron の x 座標が 14 → 34 → 54 → 74 → 94 → 114 と **1 階層あたり 20px** 刻み。
第 5 階層ではラベル開始位置が x=131 となり、220px 幅のパネルに対して名前用の幅が
**89px しか残らない**（3-8 の切断はこれが直接の引き金）。

**修正案**: `TreeViewDelegate.indentation` を明示的に 16px に落とす（Windows 11 ナビゲーション
ペインと同値）。第 5 階層で 20px × 4 = 80px 節約でき、名前領域が 89 → 109px に増える。
chevron 自体も現状は 16px 相当の領域を占めているので、12px に詰めるとさらに稼げる。

### 3-10. 階層の手がかりが「インデントだけ」しかない

6 階層並ぶと、どの行がどの親に属するのかインデント量を目測するしかない。アイコン（3-5）も
インデントガイド線もなく、chevron は暗くて小さい。

**修正案**: 各階層に 1px の縦ガイド線（`strokeSubtle`、インデント位置に配置）を入れる。
VS Code / 各種 IDE のツリーと同じ表現で、深い階層の追従が一気に楽になる。3-5 のフォルダー
アイコンと合わせると、階層の視認性はほぼ解決する。

### 3-11. ツリーだけ左ドラッグでパン（横スクロール）できてしまう（要検証）

ファイル一覧の 2 ビューは `acceptedButtons: Qt.NoButton` で Flickable のドラッグパンを
明示的に殺している（`FileTableView.qml:433`, `FileGridView.qml:39`）が、
`FolderTreePanel.qml` の `TreeView` にはその指定がない。Flickable の既定は
`Qt.LeftButton` なので、**ツリーだけ行を左ドラッグすると内容がパンする**はず。
Explorer のナビゲーションペインにこの挙動はなく、ビュー間で一貫していない。

3-8 で横スクロールを (b) 案にする場合はホイール/スクロールバー経由に限定し、
ドラッグパンは他ビューと揃えて無効化するのが筋。※実機での再現確認はまだ。

## 4. ファイル一覧（詳細表示） — `FileTableView.qml`

### 4-1. 選択行のハイライトが行の途中で切れる ★重大

実測: 1200px 幅で行を選択すると、ハイライトは x≈975（= 全列幅の右端）で終わり、そこから右
225px は塗られない。行の右端がどこか分からず、クリック可能領域（実際は列の右外もヒットする
— `FileTableView.qml:534`）とも一致していない。

**修正案**: 選択/ホバーの背景を「セル単位の `Rectangle`」ではなく、行全体に張る背景レイヤーに
分離する。`TableView` は行背景を持たないので、(a) 最終列を余白列として `fillWidth` させる、
(b) ビュー幅いっぱいの行背景を別途描く、のどちらか。(a) のほうが安く、「名前列を残り幅で
伸ばす」（4-2）と同時に解決できる。

### 4-2. 列幅が可変幅に追随しない

実測: 1200px では右に 225px の死に空間。800px に縮めると Date modified が途中で切れ、
**水平スクロールバーも出ない**（`TableView` に `ScrollBar` 未接続）ので、Size 列に到達する
手段がない。

**修正案**: 名前列を「残り幅を吸収する列」にする（`columnWidthProvider`（`:446`）で
`viewport - 他列合計` を返す）。日付・サイズ列は固定幅を維持。加えて縦横とも
`ScrollBar.vertical/horizontal` を明示的に付ける（現状スクロールバーが一つもない。行数が
ビューを超えたときのスクロール可能性も見た目から分からない）。

### 4-3. 行とヘッダの体裁

- 行高 28px、内側マージン 4px（`:556`, `:588`）で文字が上下に詰まる。→ 行高 32px、
  上下パディング 6px。
- ヘッダ高 32px・マージン 6px（`:391`, `:405`）に対し行はマージン 4px なので、ヘッダの
  「Name」（x=210）と行のファイル名（x=208）が **2px ずれる**。→ 同一トークンに揃える。
- ヘッダに下境界線がなく、列と列の区切りもない。→ ヘッダ下に 1px、列間に薄い縦線
  （またはヘッダ hover 時のみ）。
- ソート矢印が「▲」文字で、ラベルとの間がスペース 1 個（`:409`）。→ Segoe Fluent Icons の
  小さいシェブロンにし、ヘッダの右端寄せに置く。
- 行の hover 表現がない（背景が `transparent` 固定、`:572`）。→ hover で subtle fill。
- 交互行の塗り分けもない。Explorer にもないので必須ではないが、Size 列が右寄せなので視線の
  対応付けが弱い。ホバーが入れば十分と判断。

### 4-4. アイコンが絵文字文字列 ★ユーザー指摘に関連

実測/コード: `(cell.isFolder ? "📁 " : "📄 ") + cell.name`（`FileTableView.qml:595`）。
名前ラベルの **テキストの一部** として絵文字を連結している。問題点:

1. Segoe UI Emoji のカラー絵文字なので、モノクロの Fluent アイコンと画面内で二重基準になる。
2. アイコンと名前の間隔が「半角スペース 1 個」で、フォント依存かつ調整不能。
3. ファイル種別に関わらず全ファイルが同じ 📄。画像/動画/PDF の区別がつかない。
4. `elide: Text.ElideMiddle`（`:591`）なので、極端に狭いとアイコンごと省略される。
5. グリッド側は `font.pixelSize: 32` の絵文字（`FileGridView.qml:373-374`）で、リスト側と
   デザインが揃っていない。

**修正案**: アイコンをテキストから分離し、行デリゲートを `RowLayout`（16px アイコン +
名前ラベル）にする。アイコン自体は段階的に:

- **第 1 段階**: Segoe Fluent Icons のフォルダ/汎用ファイル グリフ（`` / ``）に
  差し替え、色は `Theme.color.accentFolder` / `textSecondary`。SVG 資産不要で即やれる。
- **第 2 段階**: 拡張子 → アイコン のマッピングを QML 側に小さく持つ（画像/動画/音声/
  ドキュメント/圧縮/その他）。`FileEntry` に種別を持たせるか、QML で拡張子を見るかは要検討。
  ※ C++ 側に触れる場合は `IMegaClient`/`FileEntry` 越しに（`CLAUDE.md` の設計方針）。

## 5. サムネイルグリッド — `FileGridView.qml`

実測（グリッド表示のスクリーンショット）:

- **タイルの外側余白がない**: セル 120x120（`:33-34`）が隙間なく敷き詰められ、1 行目が
  ツールバー直下・左端がパネル直下に密着。→ ビューに `topMargin`/`leftMargin` 相当（8px）と、
  セル間の視覚的隙間（`cellWidth = tileWidth + gap`）を入れる。
- **サムネイル枠がない**: `Image` が `PreserveAspectFit` でセルいっぱいに配置される
  （`:356-367`）ため、横長画像と縦長画像でタイル内の絵の大きさ・位置がバラバラに見える。
  → 固定サイズ（例 80x80）のサムネイル枠 `Rectangle`（角丸 4px、1px ストローク、
  `clip: true`）を置き、その中に収める。Explorer と同じく枠のほうを揃える。
- **ファイル名が 1 行 + ElideMiddle**（`:378-384`）。日本語ファイル名が数文字で消える。
  → 2 行折り返し + 3 行目以降を省略（`maximumLineCount: 2`, `elide: ElideRight`,
  `wrapMode: Wrap`）。そのぶんセル高を 120 → 140 に。
- **選択ハイライトがタイル全面の薄塗り**（`:337-340`）。サムネイルの上にも被るので画像が
  濁る。→ 塗りは名前ラベル側とタイル枠のみ、サムネイル部分はアクセント枠線で示す。
- 絵文字アイコン（4-4 参照）。

## 6. フッター / ステータスバー — `Main.qml:220-295`

- **高さが約 48px** あり、常時は表示モード切替ボタン 2 個しか置いていない。Explorer の

- **チェック中の表示モードボタンが強いアクセント塗り**（実測: ティールの角丸ベタ塗り 40x36）。

- 転送中のラベルとプログレスバー（`:224-257`）が左寄せで、幅 160px 固定。項目数表示を入れる
  なら並び順の再設計が要る（左: 項目数 / 中: 転送 / 右: 表示モード）。

- **3 つのポップアップが同じ位置に重なる**: `DownloadSnackbar.qml:35-36`、

- ダイアログ（`Main.qml` の 4 つ）は `Label` を直接子に置いているだけでパディング指定がない。

## 11. 未確認・要判断

判断が要るものは冒頭の進捗チェックリスト A に D1〜D6 として集約してある。以下はその根拠。

- **ライトテーマでの見た目**（D3）: 今回の実測はすべてダーク（Windows のテーマ追従）。サーフェス
  色を分けるときはライトでも検証が要る（`ui-style` の `cycle` で Windows 側のテーマを
  切り替えて再撮影）。
- **タブの × が出ない件**（B2 / 1-3）は、B1 のレイアウト修正後に再現するかを実機で確認して
  から原因を確定させる。現時点では 1-1 と同根という推測。
- **アイコンフォント依存**: Segoe Fluent Icons は Windows 11 前提。Windows 10 では Segoe MDL2
  Assets にフォールバックする（`CaptionBar.qml:120-122` に既存の判断あり）が、4-4 で使う
  グリフが両方に存在するかは要確認。S4 の着手前に確認すること。
- **ファイル種別アイコン**（D6 / 4-4 第 2 段階）は `FileEntry` にフィールドを足すか QML 側で
  拡張子判定にするかの設計判断が要る。UI 整理のスコープを超えるので別フェーズ推奨。
- **「進む」「上へ」ボタン**（D4 / 2-2）はナビゲーション機能の追加であり、見た目整理では
  ない。やるなら `FolderNavigationController` の変更を伴う別フェーズ。
- **狭いときのサイドパネル自動折り畳み**（D5 / 9）は挙動変更なので、やるかどうかの判断が要る。
- **ツリーのフォント方針**（D1 / 3-2 の案 A・案 B）は好みの問題なので要判断。実測上は
  「大きい」のではなく「行が詰まっていて文字以外に何もない」のが原因。
- **ツリーの左ドラッグパン**（B9 / 3-11）は実機での再現確認がまだ。コード上は Flickable の
  既定（`Qt.LeftButton`）が生きているので発生するはず。S0 の最初に再現確認する。
- **深い階層の名前の扱い**（D2 / 3-8）は省略記号（案 a）か横スクロール（案 b）かの判断が要る。
  MEGA のフォルダー名は長くなりがちなので、ツールチップ併用の (c) が無難かもしれない。
  **B4 の修正内容がこれで決まるので、S0 に入る前に決めること。**
