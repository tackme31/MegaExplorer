## 0. 結論（先に要約）

1. **上書きは SDK のバージョン機構に任せ、ゴミ箱を使わない。** MEGA は同名の putnodes を自動で
   「既存を第 1 版にした新ノード」にする（§1-3）。初版はこれを知りつつ移動とアップロードで
   ゴミ箱先行にしていたが、**ゴミ箱は日数経過で自動的に空になる**（`getRubbishBinAutopurgePeriod`、
   無効化できるのは PRO のみ）ので、上書きの退避先としては期限付きの保管庫でしかない。
2. **ゴミ箱に入るのは、ユーザが「消す」と言ったものと、移動の移動元だけ。** この不変条件を
   全経路で成立させる。移動元は内容が移動先に版として生きているので、purge されても失われない。
3. **`versions_disabled` はアカウント設定どおりに尊重する。** 上書きで版を残すか完全に消すかは
   ユーザが意図して切り替えた設定なので、アプリ側で固定しない。**ダイアログの文言だけを切り替える**。
4. **ダイアログは「衝突したファイル」用と「衝突したフォルダ」用に分ける。** 選択肢の意味が
   種別ごとに閉じるので、混在時に「スキップしたのにフォルダだけ勝手にリネームされた」が起きない。
   混在は 2 枚出す。
5. **ただしアップロードだけは 1 枚**で、訊くのは「重複しているファイルが N 個ある」ことだけ。
   フォルダのマージは SDK がやることで、ユーザから見た結果は「中のファイルが上書きされるか
   どうか」に尽きる。**「結合」という概念をユーザに見せない。**
6. **フォルダの無確認リネームを廃止する。** 同名フォルダを複数作るのは意図的にやる操作ではない
   （MEGA が許すことすら知られていない）ので、コピー／移動とも訊く。

## 1. SDK 調査（事実）

### 1-1. 存在チェックにネットワークは要らない

`MegaApi::getChildNodeOfType()` は `MegaRequestListener` を取らない同期関数で、実装は
`client->childnodebynametype()` → `NodeManager`（メモリ）→ 未ロードならローカル SQLite の
`SELECT ... FROM nodes WHERE parenthandle=? AND name=? AND type=? limit 1` に落ちる。

- `third_party/sdk/src/megaapi_impl.cpp:19410`（`getChildNodeOfType`）
- `third_party/sdk/src/db/sqlite.cpp:4212`（`childNodeByNameType`）

`fetchNodes()` 済みならサーバには行かない。コストは `sdkMutex` の取得と最悪 1 名前あたり SQLite
クエリ 1 本のみ。**本仕様はこの事実に依存する**（§3-5 のネスト衝突検出）。初版は §4 の判断により
使わない予定だったが、本改訂で前提に戻った。

### 1-2. フォルダアップロードは既存フォルダへ強制マージする

`MegaFolderUploadController::start()` は転送ルートの leaf 名で `getChildNode()` を引き、同名
フォルダがあればそれを再利用する:

```cpp
auto leaf = transfer->getFileName() ? transfer->getFileName() : path.leafName().toPath(true);
newTreeNode->megaNode.reset(megaApi->getChildNode(mUploadTree.megaNode.get(), leaf.c_str()));
```
（`megaapi_impl.cpp:32055-32060`。`32078` のコメントが「同名フォルダなら両者の内容はマージ
される」と明言している）

中のファイルは `UseLocalVersioningFlag` 付きで putnodes されるため、同名ファイルは新バージョンと
して積まれる。**本仕様はこのマージを機能として使う**（ローカルの `dir` に写真を足して再アップロード
＝マージ、はユーザが期待する挙動そのもの）。初版が「バグの機構」として潰そうとしたのは誤りで、
発端のバグは**マージそのものではなく、マージの結果が黙って起きること**だった。

**ネストしたファイル単位のフックは無い。** `genUploadTransfersForFiles()` が作るサブ転送は
`mtime` / `mFolderTransferTag` / `appData` / `mFsType` しか設定せず、名前は常にローカルの leaf
（`megaapi_impl.cpp:32497-32513`）。したがって「中の 1 ファイルだけ飛ばす」は SDK の再帰
アップロードを使う限り表現できない。→ §5-2 でアプリ側が歩く。

### 1-3. 上書きの実現手段は経路ごとに違う

| 経路 | 同名の既存ファイルがあるとき |
|---|---|
| コピー | **自動で版になる。** `copyTreeFromOwnedNode()` が `getovnode()` で既存を引き `ovhandle` を立て、`putnodes(..., UseLocalVersioningFlag, ...)`（`megaapi_impl.cpp:21844,21781`） |
| アップロード | **自動で版になる。** `File::completed()` が同じく `getovnode()` を引く（`file.cpp:493-502`）。手動アップロードは `startxfer(..., UseLocalVersioningFlag, ...)`（`megaapi_impl.cpp:20288`） |
| 移動 | **何もしない。** `moveNode()` → `MegaClient::rename()` → `CommandMoveNode`（`m` コマンド）だけで `ov` も `vb` も送らない（`megaclient.cpp:10023-10110`）。MEGA は同名兄弟を許すので、同名が 2 つ並ぶ |

コピーとアップロードについて、初版の「`newName` を空にすると版として乗る」は不正確だった。
正しくは 2 点:

- **判定は「結果の名前が既存ファイルと一致するか」**。既存と同じ名前を明示的に渡しても同じく
  版が積まれる。`newName` が空かどうかは関係ない。
- **fingerprint が完全一致なら通信すらしない。** 既存ハンドルを返して `API_OK` で終わる
  （`megaapi_impl.cpp:21847,21915-21918`）。同一ファイルの上書きは無害な no-op。

フォルダには一切効かない。`ov` は `type == FILENODE` のトップレベルにしか付かず、`proctree()` が
作る子ノードには入らないので、**フォルダのコピーは常に同名 2 つになる**。`copyNode()` はサブツリーを
1 リクエストでサーバ側コピーするため、「既存フォルダへマージ」は書けない（`src/core/IMegaClient.h:247-260`）。

`COLLISION_RESOLUTION_OVERWRITE / NEW_WITH_N / EXISTING_TO_OLDN` は `startDownload()` の引数で
（`megaapi.h:17600`）、アップロードに対応物は無い。

### 1-4. `versions_disabled` が「上書き」の意味を二分する

`UseLocalVersioningFlag` はアカウント設定で 2 つに分岐する（`commands.cpp:1171-1173`）:

| 設定 | 実際の動作 |
|---|---|
| バージョン管理 **有効**（既定） | `ClaimOldVersion` — 旧ノードが新ノードの第 1 版になる。復元可能 |
| バージョン管理 **無効** | `ReplaceOldVersion` — **旧ノードは完全削除。ゴミ箱にも行かない**（`types.h:1158`、`file.cpp:497`） |

アプリ側で `ClaimOldVersion` に固定する案もあったが、**採らない**。バージョン管理を切るのは
容量のためにユーザが意図してやる設定で、それを無視して版を積むほうが不具合に見える。
アプリがやるのは**ダイアログの文言を切り替えること**だけ（§3-5）。

読み取りは `MegaApi::getFileVersionsOption()`（非同期、未設定なら `API_ENOENT`＝有効が既定、
`megaapi.h:21447`）。ログイン後にキャッシュする。

### 1-5. 名前は転送・移動の時点で変えられる

- **アップロード**: `MegaUploadOptions::fileName` は "Custom file or folder name in MEGA"
  （`megaapi.h:11530`）で、§1-2 の `getFileName()` がこれを読む。現状 `IMegaClient::upload()` に
  名前引数が無く `startUpload(..., /*options*/ nullptr, ...)`（`src/mega/MegaSdkClient.cpp:477`）。
- **移動**: `MegaApiImpl::moveNode(node, newParent, newName, listener)` が存在し
  （`megaapi_impl.cpp:21415`）、`MegaClient::rename()` が `attrUpdates['n']` として先に流すので
  **リネーム込みで 1 リクエスト**（`megaclient.cpp:10092-10107`）。`IMegaClient::moveNode` には
  `newName` が無いので配線が要る（§5-3）。

### 1-6. 件数とサイズは同期・ローカルで取れる

`MegaApi::getSize(node)` はフォルダに対しサブツリー全体の合計を返す同期関数
（`megaapi.h:20241-20250`）。`getNumChildFiles()` も同様。ネットワークに行かない。

## 2. 現状のコードで何が起きているか

### 2-1. Keep both は「一選択肢」ではなくコピー経路の既定エンジン

`startCopyBatch()` は衝突が無ければ `onConflict = CopyConflict::Rename` に落とし、全エントリを
`uniqueCopyName()` に通す（`src/qml/FileMutationController.cpp:558, 583-588`）。Rename は
ダイアログの答えである前に通常のコピー経路そのもの。単純に削除すると壊れる。

### 2-2. フォルダは今もダイアログを通っていない

`collides()` が `!entry.isFolder` 条件付き（`FileMutationController.cpp:538`）。MEGA は同名
フォルダの共存を許すため「衝突ではない」と扱われ、必ず `uniqueCopyName()` 経由で `- Copy` が
付く。**別フォルダへの貼り付けでも**そうなる。本仕様はここを変える（§3-2）。

### 2-3. 同一フォルダへの貼り付けは、ファイルだけダイアログを通る

自分自身が `existingFiles` に入るため。フォルダは 2-2 により通らない。

判定手段は追加 API 不要。コピー経路は貼り付け先の一覧をすでに読み直しているので
（`FileMutationController.cpp:456, 513, 690`）、**エントリ自身のハンドルがその一覧に含まれるか**
で同一フォルダ判定ができる。

### 2-4. ダウンロードは無言のサフィックス付け

`COLLISION_RESOLUTION_NEW_WITH_N` を使っており、ローカルの Downloads で衝突しても黙って
`(1)` が付く（`src/qml/DownloadController.cpp:132`）。ブラウザと同じ。本仕様の対象外。

### 2-5. アップロードの Replace は SDK の版化と二重に動いている（要実測）

`UploadController` は転送成功後に旧ノードを `moveToRubbish` する（`:61-85`）。ところが §1-3 の
とおり **SDK はその時点で既に旧ノードを新ノードの第 1 版にしている**。つまりアプリは「版として
保存された旧ファイルを、直後にゴミ箱へ送っている」可能性が高い。

そうであれば `replaceHandle` 機構（`UploadController.cpp:61-85, 360-389`、`UploadService` の
`replaceHandle` フィールド）は SDK と戦っているだけで、しかも戦った結果ユーザが失うものが
増えている。本仕様では機構ごと削除するので実装上は解決するが、**現行バージョンの挙動として
実測しておく価値がある**（§6-2）。

### 2-6. 移動の Replace はゴミ箱先行

`moveOne()` の `replaced` 分岐（`FileMutationController.cpp:454-497`）が移動先の既存ファイルを
先にゴミ箱へ送り、成功してから `moveNode` する。§0-1 により本仕様で作り替える。

## 3. 仕様

### 3-0. 選択肢の意味

| 選択肢 | 衝突したエントリ | 衝突していないエントリ |
|---|---|---|
| **置き換える** | 実行する。既存は版になる（`versions_disabled` が ON なら完全削除、§1-4） | 実行する |
| **名前を変えて〜** | 使われていない名前を付けて実行する | 実行する |
| **スキップ** | 何もしない | 実行する |
| **キャンセル** | 何もしない | **実行しない**（操作ごと取りやめ） |

スキップとキャンセルの差は右列だけで、ここが仕様の肝。ダイアログ本文に「他の N 件はそのまま
コピーされます」と書かないとスキップの意味が伝わらない。

### 3-1. ダイアログの構成

**衝突の種別ごとに 1 枚**にする。混在時は 2 枚（ファイル → フォルダの順）。理由は選択肢の意味が
種別ごとに閉じること: ファイル用のスキップは衝突したファイルだけを、フォルダ用のスキップは
衝突したフォルダだけを外す。1 枚にまとめると「ファイルは置き換えたいがフォルダはスキップしたい」が
表現できず、初版のように「置き換えるを選んでもフォルダはスキップされます」という注釈が要る。

**不変条件: 全部の回答を集めてから発行する。** 1 枚目に答えて 2 枚目でキャンセルしたとき、
API が 1 本も飛んでいない状態でなければならない。

**アップロードだけは 1 枚**で、種別で分けない（§3-3）。

### 3-2. コピー / 移動 — 経路 × 衝突対象

| 経路 | 衝突した対象 | ダイアログ | 選択肢（既定は先頭） |
|---|---|---|---|
| コピー（別フォルダ） | ファイル | ファイル用 | 置き換える / スキップ / キャンセル |
| コピー（別フォルダ） | フォルダ | フォルダ用 | 名前を変えてコピー / スキップ / キャンセル |
| コピー（別フォルダ） | 混在 | 2 枚 | 上の 2 つを順に |
| コピー（同一フォルダ＝複製） | 全部 | **出さない** | `- Copy` 付与（§3-6） |
| 移動 | ファイル | ファイル用 | 置き換える / スキップ / キャンセル |
| 移動 | フォルダ | フォルダ用 | 名前を変えて移動 / スキップ / キャンセル |
| 移動 | 混在 | 2 枚 | 上の 2 つを順に |
| 両方 | 名前が同じで**種別が違う** | 出さない | 衝突扱いしない（MEGA が共存を許す） |

**フォルダに「置き換える」は無い。** MEGA にフォルダのマージ手段が無く（§1-3）、置き換えを実装
すると「既存フォルダごとゴミ箱送り」になってソースに無いファイルまで消えるため。

**リネーム時の名前はダイアログに出す。** サフィックスは経路で変える — コピーは
`uniqueCopyName()` の `dir - Copy`、移動は `dir (2)`（移動は複製ではないので `- Copy` は
語感が合わない）。どちらも「`dir (2)` という名前で移動します」と本文に書く。

### 3-3. アップロード — 訊くのは「重複ファイルが何個あるか」だけ

フォルダかファイルか、トップレベルかネストかで**分岐しない**。ダイアログは 1 種類:

| 条件 | ダイアログ | 選択肢 |
|---|---|---|
| 重複するファイルが 1 個以上 | 出す | 置き換える / スキップ / キャンセル |
| 重複するファイルが 0 個 | **出さない** | — |

フォルダのマージは SDK がやること（§1-2）で、ユーザから見た結果は「中のファイルが上書きされるか
どうか」に尽きる。「結合」という概念を見せない。

この一本化から素直に出る帰結が 2 つあり、どちらも望ましい:

- **100 個入りの `/dir` に `file1.txt` だけを足した `dir` をアップロードすると、ダイアログは
  出ず 101 個になる。** 同名フォルダはあるが同名ファイルが無いので、訊くことが何も無い。
- **トップレベルのファイル衝突とネストしたファイル衝突が同じ扱いになる。** どちらも
  「N 個のファイルが重複しています」に合流する。

### 3-4. 選択肢 → 実際に何が起きるか

| 経路 | 選択肢 | 発行される呼び出し | ゴミ箱 |
|---|---|---|---|
| コピー | 置き換える | `copyNode(src, dst, newName="")`。SDK が同名既存を検出し版を積む | 使わない |
| コピー | 名前を変えてコピー | `copyNode(src, dst, newName=uniqueCopyName())` | — |
| コピー | スキップ | そのエントリは発行しない。**他の種別・非衝突分は実行** | — |
| コピー | キャンセル | 何も発行しない | — |
| 移動 | 置き換える | ① `copyNode(src, dst, newName="")` → 成功したら ② `moveToRubbish(src)` | **移動元のみ** |
| 移動 | 名前を変えて移動 | `moveNode(src, dst, newName="dir (2)")` 1 本（§1-5） | — |
| 移動 | スキップ | 発行しない。移動元はその場に残る | — |
| 移動 | キャンセル | 何も発行しない | — |
| アップロード | 置き換える | 通常の `upload` のみ。SDK がマージし版を積む。**`replaceHandle` 廃止** | 使わない |
| アップロード | スキップ | 重複するファイルだけ外して発行（§5-2） | — |
| アップロード | キャンセル | キューに何も入れない | — |

**移動の置き換えは「コピー＋移動元をゴミ箱」で実装する。** 移動先の既存ファイルは版として残り
ゴミ箱に入らない。ゴミ箱に入るのはユーザが自分で「ここから消す」と言った移動元だけで、その内容は
移動先の最新版として生きているので、ゴミ箱が purge されても失われるものが無い。

- 順序は固定。コピー成功を確認してから移動元を捨てる。①が失敗したら②は撃たず移動元を残す。
- **ノードハンドルが変わる**ので、移動元に張った公開リンクは切れる。既知の差異（§4-3）。
- バイト同一なら①は no-op で成功する（§1-3）ので、結果は「移動元が消えて移動先はそのまま」＝
  期待どおり。

### 3-5. ダイアログ本文

置き換えの結果は `versions_disabled` で変わる（§1-4）ので、文言を切り替える:

| 設定 | 本文 |
|---|---|
| バージョン管理 有効（既定） | 「既存のファイルは以前のバージョンとして残ります」 |
| バージョン管理 無効 | 「既存のファイルは**完全に削除されます**（バージョン管理をオフにしているため）」 |

アップロードは重複ファイルを**一覧で**出す。件数だけでなく何が当たっているかを見せる:

> アップロード先に、同じ名前のファイルが **3 個**あります。
> 　`dir/file1.txt` `dir/sub/a.png` `dir/sub/b.png`
> 既存のファイルは以前のバージョンとして残ります。他の 98 個はそのままアップロードされます。
> 　[置き換える] [スキップ] [キャンセル]

**衝突が 1 件でも選択肢は減らさない。** そのときスキップとキャンセルは結果が同じになるが、
件数でボタン構成が変わるほうが混乱する。Explorer も単一衝突でスキップを出す。

件数と追加サイズ（§1-6）はどのダイアログにも添えられる。

### 3-6. 同一フォルダへの貼り付け

| 対象 | 挙動 |
|---|---|
| ファイル / フォルダ / 混在 | **無確認**、`- Copy` 付与 |

同一フォルダへの貼り付けは衝突ではなく**複製**なので、訊かない。Windows Explorer と同じ線引き。
`uniqueCopyName()` が `taken` を都度更新するので、同名が複数あっても `- Copy (2)` と重複回避
される（`FileMutationController.cpp:583-588`）。

### 3-7. ダウンロード

対象外・現状維持（§2-4）。

## 4. この仕様が導く帰結

### 4-1. 発端のバグは「マージを止める」ではなく「マージの中身を見せる」ことで消える

ネストしたファイルの上書きは同名フォルダへのマージ経由でしか起きない（§1-2）。初版はマージ自体を
禁じて経路を消したが、本仕様は**マージを残したままネストした衝突を検出して見せる**。§1-1 のとおり
MEGA 側の照合はネットワーク不要なので、コストはローカルの再帰走査だけ（§5-1）。

初版が §4-2 で認めていた機能欠落（「ローカルの `FolderA` に写真を 3 枚足して再アップロード」が
通らない）も同時に無くなる。

### 4-2. ゴミ箱に入るものが 2 つに限定される

- ユーザが明示的に「削除」したもの（`FileMutationController.cpp:192-202`）
- 移動の置き換えにおける**移動元**（内容は移動先に版として生きている）

上書きされた側がゴミ箱に入ることは無くなる。ゴミ箱の自動 purge（§0-1）が上書きの取り消し可能性に
影響しなくなる、というのが本改訂の一番の狙い。

### 4-3. Windows Explorer との差異は 2 つに減る

初版で最大の差異だった「フォルダの スキップ がサブツリーごと除外する」は、マージを残したので
**解消**した。残るのは:

- **コピー／移動でフォルダは結合できない**（§1-3、SDK の制約）。Explorer は結合する。
  アプリでは「名前を変える」か「スキップ」になる。アップロードだけは結合できる。
- **移動の置き換えでノードハンドルが変わる**（§3-4）。移動元に張った公開リンクは切れる。

## 5. 実装メモ

### 5-1. ローカル再帰走査は `src/core` のポートとして生やす

アップロードのネスト衝突検出（§3-3）にはローカルのディレクトリ走査が要るが、`src/core` に
ファイルシステムのポートが無く、`UploadController` が `QFileInfo` を直接触っている
（`UploadController.cpp:333`）。`docs/ARCHITECTURE.md` の分割に従い:

- `src/core/ILocalFileSystem.h` — 1 階層ぶんの列挙だけを持つ最小のポート。`MegaExplorerCore` は
  Qt を一切リンクしないので、`std::string` と自前の構造体で受ける。
- `src/platform/` — アダプタ（`src/mega` と並ぶローカル側アダプタ置き場）。
- **再帰は core 側のサービスに置く。** 「両側に同名フォルダがある枝にだけ降りる」判断はテストで
  固定したいロジックなので、フェイクを差せる位置に無ければならない。

`listRecursive` ではなく 1 階層ずつ返す形にするのは、走査コストを衝突面の大きさに比例させる
ため。100 個入りの `/dir` に 1 個足すケースなら、走査は 1 階層・MEGA 側の照合 1 回で終わる。

### 5-2. アップロードのスキップは、衝突した枝だけをアプリが歩く

SDK の再帰アップロードにはファイル単位のフックが無い（§1-2）ので、「重複する 3 個だけ外す」は
そのままでは表現できない。ただし全部を自前で歩く必要も無い:

- **置き換えるを選んだとき**は何もしない。トップレベルのパスをそのまま `upload` に渡せば、
  SDK がマージして版を積む（現状の経路のまま）。
- **スキップを選んだとき**だけ、**衝突がある枝に沿って**降りる。各階層で:
  - 重複するファイル → キューに入れない
  - 重複しないファイル → 解決済みの親ハンドルへ個別に `upload`
  - 衝突を含まないサブフォルダ → **そのディレクトリのパスをそのまま `upload`**（SDK の
    フォルダ転送 1 本で済む）
  - 衝突を含むサブフォルダ → 降りる

`UploadService::enqueue()` はローカルパスと親ハンドルを取るので、ディレクトリを渡せば SDK の
フォルダ転送になる。**新しいアップロード基本操作は要らず、必要なのは階層ごとの親ハンドルだけ**で、
それは §5-1 の走査が `findNameCollisions()`（`UploadService`、既存）から受け取る `FileEntry` の
ハンドルとして手に入る。

### 5-3. `IMegaClient` に足りないもの

| 追加 | 用途 |
|---|---|
| `moveNode` に `newName` | §3-2 の「名前を変えて移動」。SDK 側は 1 リクエストで済む（§1-5） |
| `getFileVersionsOption` 相当 | §3-5 の文言切り替え。ログイン後にキャッシュ |
| `getSize` / `getNumChildFiles` | §1-6 の件数・追加サイズ表示 |

### 5-4. 消えるもの

| 対象 | 変更 |
|---|---|
| `UploadController` の `replaceHandle` 一式（`:61-85, 360-389`）と `UploadService::replaceHandle` | **削除**（§2-5） |
| `UploadController::collisionsFor()` の `isFolderUpload` 除外（`:334`） | フォルダも走査対象にし、ネストへ降りる |
| `FileMutationController::moveOne` の `replaced` 分岐（`:454-497`） | ゴミ箱先行 → 「コピー→移動元をゴミ箱」 |
| `FileMutationController::collides()` の `!entry.isFolder`（`:538`） | 条件を外し、フォルダ用ダイアログへ回す |

## 6. 積み残し

### 6-1. MEGA がコピーをストレージに二重計上するか（未検証）

MEGA のコピーは物理ブロブを再アップロードせずノードだけ作るため、課金がノード単位か実体単位かで
「大きいフォルダの複製は容量を食う」という懸念の重みが変わる。テストアカウントで `megatool` を
使い、フォルダをコピーする前後で `getAccountInfo` の使用量を比較すれば判定できる。

移動の置き換えを「コピー＋移動元をゴミ箱」で実装する（§3-4）ので、**二重計上されるなら移動の
置き換えが一時的に容量を食う**（移動元がゴミ箱にある間）。優先度が上がった項目。

### 6-2. アップロードの Replace が版をゴミ箱へ送っているか（未検証）

§2-5。本仕様では機構ごと消えるが、現行バージョンの挙動として確認する価値がある。

### 6-3. 同名エントリを複数まとめて置き換えたとき

クリップボードに同名のファイルが 2 つ（別フォルダ由来）あり、両方が衝突した状態で置き換えを
選ぶと、2 つ目が 1 つ目に対して版を重ねる。アップロード経路には `claimedReplaceHandles` による
対策があるが（`UploadController.cpp:367`）、コピー経路には対応物が無い。**`replaceHandle` 機構を
削除しても（§5-4）この問題は残る**ので、名前ベースの重複排除として作り直す必要がある。

## 7. 初版から変えた判断と、その理由

初版（同日）は「上書き＝既存をゴミ箱へ送ってから実行」「フォルダ衝突＝スキップのみ」を軸にして
いた。レビューで 2 つの前提が崩れた。

**(a) ゴミ箱は退避先として期限付きだった。** `getRubbishBinAutopurgePeriod` の無効化は PRO 限定
（`megaapi.h:16930`）で、無料アカウントでは日数経過で確実に消える。「上書きしても取り消せる」が
期間限定でしか成り立たないなら、SDK が既に持っているバージョン機構のほうが素直で、しかも
**コピーとアップロードについてはアプリが何もしないほうが正しく動く**（§1-3）。初版の
`replaceHandle` 機構は SDK の版化と二重に動いていた疑いすらある（§2-5）。

**(b) フォルダのマージは、潰すべきバグの機構ではなく期待される機能だった。** 初版は「フォルダ
衝突をスキップにすればネストした上書きが起きない＝再帰チェック不要」という筋の良さで組み立てて
いたが、それは「`dir` に 1 ファイル足して再アップロードしたら 101 個になる」という素直な期待を
一緒に捨てていた。§1-1 でネスト検出がネットワーク不要と分かっている以上、コストの理由も無い。

**副次的に、ダイアログの一貫性を捨てた。** フォルダ衝突の選択肢は経路ごとに違う（コピー＝
リネーム、移動＝リネーム、アップロード＝そもそも訊かない）。SDK でできることが経路ごとに違う
以上、揃えると全部を最小公倍数に合わせることになる。**一貫性より、その経路で実際に可能な最善**を
採った。

**アップロードのダイアログを 1 枚に畳んだ**のもこの流れ。フォルダかファイルかはユーザにとって
どうでもよく、知りたいのは「何個上書きされるのか」だけ。「結合」という語をユーザに教えずに済む。

**`versions_disabled` は尊重する。** アプリ側で `ClaimOldVersion` に固定して常に版を残す案も
あったが、バージョン管理を切るのは容量のためにユーザが意図してやる設定で、それを無視するほうが
不具合に見える。文言だけ切り替える（§3-5）。
