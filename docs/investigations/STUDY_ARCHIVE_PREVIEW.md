# 書庫ファイルの中身一覧プレビュー（zip / rar / 7z） — 実装前調査

> **状態: 実装の予定なし。相談ベースの机上調査で、どのフェーズにも紐づいていない。**
> 2026-08-20 時点のコード（`f608e5f`）に対して「もしやるならどういう方針になるか」を見ただけで、
> コード変更・計測・プロトタイプはいずれも行っていない。**実測値はこの文書に一つもない。**
> 結論は §0、フォーマットごとの可否は §2、既存コードへの影響は §3、着手順は §6。

想定している機能は「書庫ファイルを選ぶと、右のプレビューペインに中のエントリ一覧（ツリー）が
出る」。**展開はしない**（中身の取り出し・中のファイルのプレビューは対象外）。

---

## 0. 結論（先に要約）

1. **3 形式とも「一覧だけ」なら原理的に可能。ただし難易度が大きく違う。**
   zip = 易 / 7z = 中（要 LZMA 展開器）/ rar = 難（逐次走査＋独自の名前符号化）。
2. **どれも全体をダウンロードする必要はない。** zip と 7z は**末尾**に全エントリの目録があり、
   レンジ取得 2〜3 回・数十 KB で一覧が作れる。100MB の書庫でも転送量は同じ。
   **rar だけは目録が末尾に無く**、原則としてヘッダを先頭から辿る必要がある（§2.2）。
3. **`IMegaClient` に範囲読みの口が要る。** 既存の `readFileContent()` は
   `startStreaming(node, 0, size)` 固定なので、`readFileRange(handle, offset, length, onDone)`
   を足すのが土台（§3.1）。SDK 側の罠（`setStreamingMinimumRate(0)`）は既存実装で対処済み。
4. **ライブラリを入れるなら libarchive（BSD-2）が唯一の「3 形式まとめて」の選択肢**だが、
   **I/O が同期ブロッキング**なので専用スレッドが要る（§4.1）。この非同期／同期の不整合が、
   本件で一番大きな設計上の争点。
5. **推奨は zip 単独から始めること。** zip の目録パースは外部依存ゼロ・200 行程度で書け、
   実用上の大半を覆う。7z / rar はそれぞれ独立した追加として後から足せる（§6）。

---

## 1. なぜ「先頭数 KB」ではだめなのか

当初の発想は「先頭数 KB だけ取れば構造が読めるのでは」だったが、**zip と 7z は目録が末尾**、
**rar は目録そのものが無い**ので、先頭固定では成立しない。形式ごとの目録の位置:

| 形式 | 全エントリの目録 | 位置 | 先頭からの逐次走査 |
| --- | --- | --- | --- |
| zip | Central Directory | **末尾**（EOCD が指す） | 不可（§2.1 の data descriptor） |
| rar4 | 無い | — | **必須** |
| rar5 | Quick Open（任意・無いことがある） | 末尾（main header の locator が指す） | フォールバックとして必須 |
| 7z | Header | **末尾**（先頭 32 バイトが指す） | 不可（構造上あり得ない） |

## 2. フォーマット別

### 2.1 zip — 易しい。レンジ 2 回で確実に取れる

**手順**

1. 末尾 `min(size, 65557)` バイトを取得（`65557 = EOCD 22 + コメント最大 65535`）。
2. 後方から `PK\x05\x06` を探す。**見つけただけで確定してはいけない** — 中のファイルが
   たまたま同じ 4 バイトを持ちうるので、`コメント長フィールド == 残りバイト数` で検証する。
3. EOCD から Central Directory の位置と長さを読み、その範囲をレンジ取得。
4. 46 バイト固定部＋可変長を順に舐めてエントリを作る。

**EOCD（22 バイト + コメント）**

```
0  4  50 4B 05 06
4  2  このディスク番号            8  2  このディスクの CD エントリ数
6  2  CD が始まるディスク番号     10 2  CD エントリ総数
12 4  CD のサイズ                16 4  CD の位置（先頭から）
20 2  コメント長 n               22 n  コメント
```

**Central Directory File Header（46 バイト + 名前 n + extra m + コメント k）**

```
0  4  50 4B 01 02              20 4  圧縮後サイズ
4  2  version made by          24 4  圧縮前サイズ
6  2  version needed           28 2  名前長 n
8  2  汎用フラグ                30 2  extra 長 m
10 2  圧縮方式                  32 2  コメント長 k
12 2  更新時刻(DOS)             34 2  開始ディスク番号
14 2  更新日付(DOS)             36 2  内部属性
16 4  CRC-32                   38 4  外部属性
                               42 4  ローカルヘッダ位置
46 n  ファイル名 → extra m → コメント k
```

**罠（実装時に必ず踏む順）**

- **先頭から Local File Header を辿るのは不可。** 汎用フラグ bit 3 が立った書庫（ストリーム
  生成されたもの。ネット配布の zip に多い）はローカルヘッダのサイズ欄が 0 で、実データ長が
  後ろの Data Descriptor にしか無い。**スキップ幅が決まらないので走査が破綻する。**
- **文字コード。** 汎用フラグ **bit 11** が立てば UTF-8、立たなければ規格上は CP437。
  ところが Windows 製の日本語 zip は**フラグを立てずに Shift-JIS を入れる**のが実情で、
  文字化けの主因はここ。Info-ZIP Unicode Path 拡張フィールド（ID `0x7075`、
  `version(1) + 元名の CRC32(4) + UTF-8 名`）があればそちらを優先する。
  総当りの推測はせず、「UTF-8 として妥当なら UTF-8、でなければ CP932」程度に留めるのが無難。
- **ZIP64。** エントリ数 `0xFFFF` / サイズ・オフセット `0xFFFFFFFF` が飽和値。飽和していたら
  EOCD の直前の ZIP64 EOCD Locator（`PK\x06\x07`、20 バイト）→ ZIP64 EOCD（`PK\x06\x06`）を
  読む。エントリ側は extra field ID `0x0001` に**飽和したフィールドだけが**
  「非圧縮 → 圧縮 → ローカルヘッダ位置 → ディスク」の順で入る（欠けた分は詰まる）。
- **前置データ。** 自己解凍 exe などでは CD 位置が実位置とずれる。
  `delta = EOCD の実位置 - CD サイズ - CD 位置` を全オフセットに足して補正する。
- **ディレクトリ判定**は「名前が `/` で終わる」が最も確実。外部属性の bit は host OS 依存。
- **暗号化**（汎用フラグ bit 0）でも**名前は平文で見える**。中央ディレクトリごと暗号化する
  `.zipx` の一部だけが例外。「暗号化」バッジを出せば足りる。
- 日時は DOS 形式（`時<<11 | 分<<5 | 秒/2`、`(年-1980)<<9 | 月<<5 | 日`）でローカル時刻。
  タイムゾーン情報が無いので、extra field の NTFS/Unix 拡張があればそちらのほうが正確。

### 2.2 rar — 一覧は取れるが、3 形式で一番厄介

**rar4（署名 `52 61 72 21 1A 07 00`）には末尾目録が無い。** 各ファイルヘッダが自分のデータの
直前に置かれているだけなので、`次のブロック位置 = 現在位置 + HEAD_SIZE + PACK_SIZE` で
**先頭から飛び石に辿る**しかない。zip と違って PACK_SIZE はヘッダに必ず入っているので走査は
成立するが、**エントリ数だけレンジ取得の往復が要る**のが致命的で、1000 エントリなら 1000 回。
現実解は「ヘッダは書庫全体に散っているが 1 個は数十〜数百バイト」という性質を使い、
**512KB 程度ずつ先読みしてキャッシュ**し、飛び先が窓内なら追加取得しないこと。それでも
巨大な rar では読む位置が全域に散るので、**小さい書庫は丸ごと落とすほうが速い**（§5）。

**rar5（署名 `52 61 72 21 1A 07 01 00`）には Quick Open がある。** main archive header
（type 1）の extra area に **locator レコード（type 1）**が入っていれば、そこに書庫末尾付近の
Quick Open サービスブロック（名前 `QO`）の位置が書いてある。QO には全ファイルヘッダの写しが
入っているので、**先頭 + 末尾の 2 回で一覧が取れる** — zip と同じ効率になる。

> **未確認。** QO の中身が無圧縮の写しなのか rar 自身の圧縮が掛かるのか、locator のオフセット
> が書庫先頭基準かを本調査では確定できていない。実装前に unrar ソースの `qopen.cpp` /
> `arcread.cpp` と技術仕様書 `techspec.txt` で裏を取ること。**また QO は任意**で、小さい書庫や
> `-qo-` 付きでは無い。**逐次走査のフォールバックは必ず要る。**

**その他の罠**

- rar4 の Unicode 名は**独自の圧縮符号化**（LHD_UNICODE フラグ時）で、単純な UTF-8/UTF-16 では
  ない。ここだけで実装量が跳ねる。rar5 は素直に UTF-8。
- `-hp` 付き書庫は**ヘッダごと暗号化**されるので名前も出せない。「暗号化された書庫」と出す。
- 分割書庫（`.part1.rar`）は他のノードを跨ぐので**対象外にする**のが妥当。

**ライセンス（重要）。** 公式 unrar のソースは「RAR 圧縮アルゴリズムの再現に使わない」条項の
付いた独自ライセンスで OSI 準拠ではない。**本件は展開をしないので、そもそも unrar を使わない**
— 容器フォーマットのヘッダを自前で読むだけならアルゴリズムに触れず、ライセンス上の問題は
生じない。ライブラリを使う場合は libarchive（BSD-2）だが、**その rar リーダの出自が unrar 派生
でないかは採用前に確認すること**（本調査では未確認）。

### 2.3 7z — 位置は明快、ただしヘッダ自体が圧縮されている

**先頭 32 バイトが目録の位置を直接教えてくれる。**

```
0  6  '7' 'z' BC AF 27 1C      12 8  NextHeaderOffset（32 からの相対）
6  1  major(0)                 20 8  NextHeaderSize
7  1  minor(4)                 28 4  NextHeaderCRC
8  4  StartHeaderCRC
```

つまり目録は絶対位置 `32 + NextHeaderOffset` に `NextHeaderSize` バイト。**ここまでは
レンジ 2 回。** 問題はその中身で、先頭バイトが

- `0x01`（kHeader）ならそのまま平文の構造体 → 解析するだけ
- **`0x17`（kEncodedHeader）なら、目録自体が LZMA で圧縮**されている

後者が**通常の 7z の既定**。この場合 kEncodedHeader は「目録を復号するための folder 定義」で、
その PackInfo が指す位置（これも 32 相対）をもう一度レンジ取得し、**LZMA で展開してから**
本来の目録を解析する。よって **7z だけは展開器が必須**で、ここが zip との決定的な差。

- 展開器の入手先は **LZMA SDK（パブリックドメイン）**。`LzmaDec.c` だけなら小さく、
  `7zArcIn.c` まで使えば目録解析も込みで済む。SDK の `ILookInStream` は**シーク付きの
  ストリーム抽象**なので、レンジ取得と噛み合わせやすい。
- 名前は UTF-16LE。**ディレクトリ判定は属性ではなく `kEmptyStream` / `kEmptyFile` の組**で
  決まる（ストリームを持たない項目のうち kEmptyFile が立っていないものがディレクトリ）。
  ここは定番の罠。
- `-mhe=on`（ヘッダ暗号化）だと目録が AES で包まれ、**名前も出せない**。

## 3. 既存コードのどこに何が増えるか

### 3.1 `IMegaClient` — 範囲読みの口（土台、これだけは必ず要る）

現状 `readFileContent(handle, maxBytes, onDone)` は `startStreaming(node, 0, node->getSize())`
固定（`src/mega/MegaSdkClient.cpp`）。ここに範囲版を足す:

```cpp
virtual void readFileRange(std::uint64_t handle,
                           std::uint64_t offset,
                           std::uint64_t length,
                           std::function<void(Result<std::vector<char>>)> onDone) = 0;
```

- `setStreamingMinimumRate(0)` は既存実装が既に入れている（数十 KB は「低速」と判定されて
  `API_EAGAIN` で落ちるため）。範囲版でも同じ扱いでよい。
- 既存の「キャンセル手段を意図的に持たない」という設計判断は、**再検討が要る**。理由は
  ヘッダのコメントどおり「payload が数十 KB で回収する帯域が無い」からだが、rar の逐次走査は
  **往復が数百回になりうる**ので、選択が変わったのに読み続ける状態が起きる。少なくとも
  「世代カウンタで結果を捨てる」（`STUDY_PREVIEW_PANE.md` §4.2 と同じ手）は要る。
- テストは既存の `FakeMegaClient` に範囲読みを足せば、**書庫パーサ自体は完全にオフラインで
  ユニットテストできる**。バイト列を食わせて木が出るだけの純粋関数にしておくこと。

### 3.2 プレビュー側

- `src/core/PreviewKind.h` の `enum { None, Image, Text }` に `Archive` を足し、
  `previewKindForName()` に拡張子を追加。
- `PreviewController` に「一覧取得中／取得済み／非対応／暗号化」の状態が増える。
  QML 側はツリー表示（既存のファイル一覧のデリゲートは流用できない。別物として作る）。
- `STUDY_PREVIEW_PANE.md` §4.3 の「`DownloadService` を経由しない」、§4.4 の
  「エラーをトーストしない」、§4.1 のキャッシュ方針はそのまま本件にも効く。
- **一覧はキャッシュしてよいと思う**（数十 KB のテキスト相当で、書庫の中身は基本不変）。
  ただし現行プレビューは「キャッシュしない」方針なので、変えるなら明示的な判断として書くこと。

## 4. ライブラリを入れる場合

### 4.1 libarchive（BSD-2）— 3 形式まとめて。ただし同期 I/O

zip / rar / rar5 / 7z を全部読め、`archive_read_open2()` + `archive_read_set_seek_callback()`
で**自前ストリームを差せる**。zip と 7z のリーダはシークが使えると末尾の目録を直接読む
効率的な経路に入るので、レンジ取得と相性が良い。

**最大の問題は I/O が同期ブロッキングであること。** libarchive は「read コールバックが
戻ってきたらデータがある」前提で書かれているが、`IMegaClient` は全部コールバック非同期。
噛み合わせるには**専用ワーカースレッドを立て、read コールバックの中で条件変数を待つ**形に
なる。`IMegaClient` を通す規約（`CLAUDE.md`）は守れるが、スレッドと寿命の管理が一段増える。
自前パーサなら**既存の非同期コールバックのままステートマシンで書ける**ので、この差は大きい。

vcpkg に在庫あり。依存（zlib / bzip2 / lzma / zstd）を機能スイッチで削れる。

### 4.2 使わないほうがよいもの

- **`QZipReader`** — Qt の private ヘッダ（`qzipreader_p.h`）でバージョン間の保証が無く、
  しかも `QIODevice` 全体を要求するのでレンジ取得と噛み合わない。
- **7-Zip の `7z.dll` を叩く系（bit7z / lib7zip）** — dll 同梱が要り、ライセンスも LGPL 混じり。
  本プロジェクトのライセンス整理（`CLAUDE.md`）を余計に複雑にするだけの利がない。
- **miniz** — zip だけなら候補だが、目録を読むだけなら自前で十分で、依存を増やす意味が薄い。

## 5. 「小さければ丸ごと落とす」逃げ道

レンジ取得 1 回はネットワーク往復 1 回で、書庫が小さいと**往復のほうが転送より高くつく**。
閾値（たとえば 4〜8MB）以下なら丸ごと `readFileContent` して、メモリ上のバイト列を同じ
パーサに食わせるほうが速く、コードも 1 本で済む（パーサを「バイト範囲を返す関数」に対して
書いておけば、供給元がメモリでもレンジ取得でも同じ）。**rar4 ではこれが事実上の主経路**に
なる可能性が高い。閾値は実測してから決めること。

## 6. 着手順（推奨）

1. **`readFileRange` を `IMegaClient` に足す**（+ `FakeMegaClient`）。単独で価値があり、
   他のプレビュー改善にも効く。
2. **zip のみ、自前パーサ。** 外部依存ゼロ、200 行程度。`PreviewKind::Archive` と
   QML のツリー表示もここで作る。実用上の大半はここで覆える。
3. **7z を LZMA SDK（パブリックドメイン）で追加。** `ILookInStream` にレンジ取得を差す。
   ここで初めて依存が 1 つ増える。
4. **rar。** rar5 の Quick Open が使えるかを実書庫で検証してから判断する。rar4 の逐次走査＋
   独自名前符号化まで自前でやる価値があるかは、そこで改めて決める。libarchive に丸ごと
   寄せる判断をするならこの段階。

各段は独立して出荷でき、途中で止めても「対応していない形式」として自然に縮退する。

## 7. この調査で確認していないこと

- **実測が一つも無い。** レンジ取得 1 回の実時間（MEGA の API 往復）、`startStreaming` に
  小さな範囲を渡したときの下限や丸め、転送量クォータがチャンク境界にどう丸められるか。
- **rar5 Quick Open の実在率と中身の形式**（§2.2 の未確認事項）。手元の rar で `-qo` 既定が
  どう効くかを含む。
- **libarchive の rar リーダの出自とライセンス上の位置づけ**。
- 7z の kEncodedHeader が LZMA2 や BCJ を挟む実例があるか（LzmaDec だけで足りるか）。
- 分割書庫・自己解凍 exe・書庫内書庫をどこまで拒否するかの UI 方針。
