# タスクトレイ常駐・複数ウィンドウ・ウィンドウ間 D&D — 実現可能性調査

2026-10-05。**状態: 調査のみ。コードは変えていない。ROADMAP にも未登録。**

**結論:** 3 つとも実現可能。規模は
**トレイ常駐 S〜M ／ 複数ウィンドウ M〜L ／ ウィンドウ間 D&D M**、`/evolve` でおよそ **6〜8 周**（§7）。
タブごとの部品はもう工場関数で作り分けており（`main.cpp` の `tabFactory`）、タブ間の更新通知も
ある（`TabsController` のファンアウト）ので、骨格は流用できる。費用の大半は
**「ウィンドウは 1 つ」を前提にした全体共通コントローラと `Main.qml` の `Settings` の切り分け**（§4-2・§6）。
§4 と §5 は既存設計の作り直しを含むので、着手前に人の了承が要る（CLAUDE.md「Pre-1.0」）。

## 1. やりたいこと／範囲

- **トレイ常駐:** ウィンドウを閉じてもプロセスが残り、トレイから再表示・終了できる。
- **複数ウィンドウ:** Explorer と同じく「新しいウィンドウ」を開ける。2 つ目の起動も、既存のプロセスに
  ウィンドウを 1 枚足すだけにする。
- **ウィンドウ間 D&D:** あるウィンドウからファイルやフォルダをドラッグし、別のウィンドウの一覧・
  ツリー・ピン・パンくず・タブ見出しへ落として移動やコピーをする。
- **範囲外のまま:** タブ見出しをウィンドウの外やほかのウィンドウへドラッグすること
  （ROADMAP 見送り「タブをウィンドウの外へ切り離す」）。エクスプローラーへドラッグしてダウンロード
  することもここでは扱わない（§5 の方式 B でだけ土台ができる）。

## 3. トレイ常駐（S〜M）

- **トレイアイコン:** `QApplication` に替え、`QSystemTrayIcon` を使う。Qt Widgets は LGPL なので
  ライセンス上の問題は無いが、配布 zip に `Qt6Widgets.dll` が増える。`package.ps1` の確認項目にも
  足す。`Qt.labs.platform` の `SystemTrayIcon` も、Windows ではメニューの表示に Widgets を使う
  ので、結局同じことになる。
- **閉じる＝隠す:** `setQuitOnLastWindowClosed(false)` にする。×ボタンでは隠すだけにする。
  トレイメニューは「表示／新しいウィンドウ／終了」。「終了」は今と同じく `app.exec()` から戻る経路を
  通し、`client->shutdown()` を必ず呼ばせる。
- **二重起動の防止（必須）:** 常駐していると、もう一度ダブルクリックされることが増える。
  `QLocalServer` の名前をアプリ名から作る（**プロファイル名を含める**。`applyAppIdentity()` の後で決まる名前を使う）。
  2 つ目のプロセスは既存のプロセスへ「表示して」（複数ウィンドウを入れた後は「新しいウィンドウ」）と
  送って終了する。Qt Network はすでにリンク済み。
- **設定:** 「閉じたらトレイに格納」の ON/OFF（既定値は人が決める。§8）。Windows 起動時の自動起動は任意。
- **注意:**
  - 常駐中も、アカウントのノードツリーは SDK のメモリに残る。大きなアカウントなら数百 MB。
  - 隠している間も転送は続く。これは利点。ただし、ウィンドウが無い間に出たトーストの行き先を決める
    必要がある（トレイの吹き出しに出すか、捨てるか）。
  - 外部ブラウザでの再生（Open with > Browser）は「アプリを閉じると止まる」ので、常駐すればこの
    制約が和らぐ（`roadmap-done.md` evolve/129 の判断①）。

## 4. 複数ウィンドウ（M〜L）

### 4-1. 骨格

- ウィンドウごとに `TabsController` を 1 つ持たせ、それを持つ `WindowRegistry`（仮称）を C++ に置く。
  共有するサービス（`client`、転送、アカウント、サムネイル、クリップボードなど）は今のまま 1 つ。
- QML には、ウィンドウごとに **ルートコンテキストの子 `QQmlContext`** を作り、ウィンドウ単位のもの
  （`tabsController` など）をそこで上書きして渡す。`QQmlComponent::create(context)` を使う。
  `Main.qml` の中の参照は書き換えずに済む。
- タブ間の更新通知を **ウィンドウをまたいで配る** ように広げる。今は `TabsController` が自分の持つ
  タブにしか配らないので、配る範囲を `WindowRegistry` 全体にする。仕組みはもうあり、配る範囲を
  広げるだけなので **S**。ウィンドウ A で移動したのに、同じフォルダを開いているウィンドウ B が古いまま、
  という問題を防ぐために D&D が無くても必要。
- ログアウト時は全ウィンドウをログイン画面に戻すか、1 枚だけ残して閉じる。これは人が決める（§8）。

### 4-2. 全体共通コントローラの仕分け

ここが一番重い。案を下に挙げる。

| コントローラ | 案 | 理由 |
| --- | --- | --- |
| `tabsController` | ウィンドウごと | 骨格そのもの |
| `previewController` / `propertiesController` | ウィンドウごと | プレビューペインが「そのウィンドウで選択中の項目」を前提にしている |
| `folderTreeModel` | 要調査 | 遅延読み込みのキャッシュは共有したいが、展開状態と現在フォルダの強調表示がモデル側にあるならウィンドウごとに切り出す |
| `notificationController` | 共有して、発生元のウィンドウを記録 | トーストは操作したウィンドウ（不明なら直近にアクティブだったウィンドウ）に出す |
| `pluginController` | 共有 | `ui.search`（「表示中のタブ」に対して動く）と進捗ダイアログは **直近にアクティブだったウィンドウ** に向ける。`Main.qml:750` の `onSearchRequested` が `tabsController` を直接見ている |
| `quickAccessModel` / `clipboardController` / 転送 / `accountController` / `authController` / `cacheController` / `localFolderController` / `openWithController` / `viewerController` | 共有 | ウィンドウに関係ない。クリップボードを共有すると、ウィンドウ間でコピー＆貼り付けがそのままできる |

### 4-3. 入口

- メニューの「新しいウィンドウ」と Ctrl+N（今のタブで開いている場所を引き継ぐ）。
- 右クリックの「新しいウィンドウで開く」（フォルダ）。
- トレイメニュー、2 つ目の起動（§3）。

## 5. ウィンドウ間 D&D（M）

同じウィンドウの中では、`DragHandler` が掴んだまま別のタブへ切り替えても、ドラッグは生き続ける
ことが実機で確認済み（`STUDY_CROSS_TAB_DRAG_MOVE.md` の追記）。ほかのタブの一覧へ落とすと
そのフォルダへ移動する、という挙動も **すでにある**。なので、ウィンドウをまたいでも挙動として新しく
決めることはほぼ無く、問題は「ドラッグをどうやってほかのウィンドウへ届けるか」だけになる。

| | **A. 内部ドラッグのまま、別ウィンドウへ持ち替える（推奨）** | B. OS のドラッグ（`Drag.Automatic` / `QDrag`）に切り替える |
| --- | --- | --- |
| 規模 | M | L |
| やり方 | ボタンを押している間、マウスは移動元のウィンドウが掴んだまま。移動中にカーソルの下のウィンドウ（`QGuiApplication::topLevelAt`）が変わったら、`DragProxy` をそのウィンドウの Overlay へ付け替え、`Drag.active` を一度落として立て直す（相手側の `DragEnter` を発生させるため）。`DragProxy` を 1 つのウィンドウに置くのはやめ、`WindowRegistry` 側から付け替えられる形にする | Windows 標準のドラッグに乗せる。ドラッグ中は OLE の `DoDragDrop` のイベントループが回る |
| 既存の挙動 | 自動スクロール、Ctrl でのコピー切り替え、ホバー時の強調、タブ見出しのばね式切り替え（600ms で開く）は、そのまま動く見込み | 上の 4 つとゴーストを作り直す。DropArea 周りの QML テストもほぼ書き直す |
| 弱点 | ウィンドウとウィンドウの間（デスクトップの上）ではゴーストが消える（落とし先が無いので実害は無い）。後ろに隠れているウィンドウには落とせない（Explorer と同じ） | — |
| おまけ | なし | エクスプローラーへドラッグしてダウンロード、の土台になる |

- **A は最初に試作で確かめる:** Windows の Qt が、ボタンを押している間カーソルがウィンドウの外へ
  出てもマウスを掴み続けるか（`SetCapture`）を確かめる。また、ドラッグ中に Item を別の
  `QQuickWindow` へ付け替えたとき `DragHandler` の grab が保たれるかも確かめる。ここが崩れたら
  B しかない。
- 移動やコピーを実行するのは今と同じく移動元のタブ（`sourceMutations`）。移動先の更新は
  §4-1 のウィンドウをまたぐ更新通知に任せる。

## 6. 永続データ（リリース済みの設定キーの扱い）

`Main.qml` の `Settings` は、性質の違う 2 種類のキーを同じ場所で持っている。

- **ウィンドウの配置:** `viewMode`、`windowWidth/Height`、`sortColumn/Ascending`、`columnWidth*`、
  `treePanelWidth`、`previewVisible`、`previewPaneWidth`
- **アプリ全体の設定:** `colorSchemePreference`、`localRootFolder`、`playbackVolume`

ウィンドウが 2 枚になると、どちらの種類にも別々の問題が出る。

- **アプリ全体の設定:** 各ウィンドウが別々に alias で持つと、ウィンドウ A でテーマを変えても B は
  古い値を持ったままになり、閉じたときに書き戻して上書きしてしまう。**C++ 側（または QML の
  singleton）1 か所に移す。** キー名は変えない。リリース済みのビルドが書いた値をそのまま読めるので、
  移行は不要。
- **ウィンドウの配置:** 「直近に閉じた（または最後に動かした）ウィンドウの値を保存し、新しい
  ウィンドウはそれで開く」にする。Explorer に近い挙動。キー名を変えなければ移行は不要。
  ウィンドウごとに保存し直すとキーが増えるので、やらない。
- 開いているウィンドウの組み合わせ（どのウィンドウでどのタブを開いていたか）の復元は、今もタブを
  保存していないので、範囲に含めない。

## 7. 分割案と見積もり

| 順 | 行 | 規模 | 前提 |
| --- | --- | --- | --- |
| 1 | 二重起動の防止（`QLocalServer`。2 つ目の起動は既存のウィンドウを前面に出す） | S | — |
| 2 | トレイ常駐（`QApplication` 化、閉じる＝隠す、トレイメニュー、設定の ON/OFF） | S〜M | 1 |
| 3 | アプリ全体の設定を `Main.qml` の `Settings` から 1 か所へ移す（§6） | S | — |
| 4 | `WindowRegistry` とウィンドウごとのコンテキスト（`TabsController`・preview・properties）。タブ間の更新通知をウィンドウをまたいで配る | M | 3 |
| 5 | 共有コントローラの行き先（トースト・プラグインを直近にアクティブなウィンドウへ）、ログアウト時の挙動 | M | 4 |
| 6 | 入口：新しいウィンドウ／Ctrl+N／新しいウィンドウで開く／トレイ／2 つ目の起動 | S | 2, 4 |
| 7 | ウィンドウ間 D&D（方式 A。冒頭で試作して確かめる） | M | 4 |

合計で **6〜8 周**。1〜2 だけでもトレイ常駐として完結するし、3〜6 だけでも複数ウィンドウとして
完結する。4 と 7 は既存設計の作り直しを含む（ウィンドウ 1 つ前提の配線、`DragProxy` の置き場所）。

## 8. 人が決めること

1. 「閉じたらトレイに格納」の既定値（ON／OFF）。初回に閉じたとき、トレイに残ったことを知らせるか。
2. ウィンドウが 1 枚も無い間に出たトーストの扱い（トレイの吹き出しに出す／捨てる）。
3. ログアウト時の扱い（全ウィンドウをログイン画面に戻す／1 枚だけ残して閉じる）。
4. 2 つ目の起動の意味（既存のウィンドウを前面に出す／新しいウィンドウを開く）。Explorer は後者。
5. D&D の方式（A 推奨。エクスプローラーへドラッグしてダウンロードもやりたいなら B）。
