# プラグイン API — ダイアログをプラグインから明示的に出す

**状態（2026-10-27）: 仕様確定、未実装。** マニフェストの `progress` / `result` を廃止し、コマンドごとの
`progressDialog`（真偽値、既定 `true`）だけを残す。表示はすべてプラグインが `ui.*` で行う
（`ui.showProgress` / `ui.hideProgress` / `ui.alert` / `ui.showResult` / `ui.toast` を追加、`ui.progress` は
`ui.updateProgress` に改名、`ui.confirm` は存続）。進捗は `show` が開く（開いていればエラー）・`update` が
送った内容で丸ごと置き換える・`hide` が閉じる、の3役で、「省略＝前の値を維持」は持たない。進捗の表示内容は割合と文字列だけで、件数・速度・残り時間・
経過時間はプラグインが書く（`command.execute` に `startedAt` を渡す）。
**破壊的変更で、`kPluginApiVersion` を 2 に上げる。**
同じ作業で `plugin_sample/` と `plugin_recipes/` を作り直す。`private_plugins/` の移行は後回し（対象外）。
仕様の正は実装後の `PLUGINS.md`。この文書は決定の経緯と理由を残す。

## 1. 背景

v1 ではダイアログの出し方を、マニフェストが実行開始時に固定していた（`progress`: `true` / `false` /
`"never"` / `{show}`、`result`: `"toast"` / `"dialog"`）。そのため、次のように段階ごとに見せ方を変える
コマンドを書けなかった。

> 件数なしの進捗 → アラート → 件数ありの進捗 → アラート → 件数なしの進捗 → 結果表示

足りなかったのは次の5つ。OK だけのアラート、実行中に表示項目（`show`）を変えること、進捗ダイアログを
閉じる／出し直すこと、結果をダイアログで出すかを実行中に決めること、段階ごとの見出し。

検討の途中で、`"manual"` モードを足して旧モードを非推奨にする案（v1 のまま追加だけ）も出た。
しかし互換を保つための決めごと（省略時の意味をいつ変えるか、`"never"` との関係、警告をどこに出すか）が
増える一方だった。利用者がほぼ作者一人でプラグインもまだ外部に無く、破壊的変更の注意書きもあるので、
**互換は捨てて API バージョンを上げる**ことにした。

## 2. マニフェスト

`commands[].progress` と `commands[].result` は**廃止**する（書かれていたら未知キーとして無視される）。
代わりに次の1つだけを置く。

| キー | 値 | 意味 |
|---|---|---|
| `commands[].progressDialog` | `true`（省略時） | 実行と同時に、件数なしの進捗ダイアログ（キャンセル付き・モーダル）を出す。アプリが開始時にプラグインの代わりに `ui.showProgress {}` を呼ぶのと同じで、その後はプラグインが自由に変えたり閉じたりできる。既に開いているので、プラグインの最初の呼び出しは `ui.updateProgress` になる（`ui.showProgress` はエラー。§3）。 |
| | `false` | 最初は何も出さない。 |

- 名前を `auto` / `manual` にしなかった理由：それはプラグインが自分で表示するかどうかという作る側の
  分類で、マニフェストが本当に決めるのは「既定のダイアログを最初に出すか」の1点だけだから。
- 表示までの待ち時間（旧 0.3 秒 / 3 秒）は**無くす**。`true` なら即座に出し、`false` なら出さない。
  一瞬で終わるコマンドでダイアログが一瞬出て消えても、アプリ側では何もしない。気になるコマンドは
  `false` にして `ui.toast` で知らせる。
- 旧 `"never"`（プラグインが自前ウィンドウを持つ）は `progressDialog: false` に含まれる。
- `progress: false` のときに 3 秒後にダイアログを自動で出していた仕組み（キャンセルをそこで提供していた）は
  **廃止**する。`false` のコマンドの中止手段はプラグインの責任（§5）。
- `kPluginApiVersion` を 2 にする。`apiVersion: 1` のプラグインは、今の仕組みのとおり一覧に出るが実行できず、
  設定画面には既存の「(⚠ Incompatible)」が出る。非推奨の警告を出す仕組みは作らない。

## 3. メソッド

ダイアログ系はすべて、`progressDialog` の値に関係なくいつでも呼べる。既定のダイアログが邪魔なら
マニフェストで消す、という分担にする。

| メソッド | 種類 | 引数 | 応答 | 動作 |
|---|---|---|---|---|
| `ui.showProgress` | リクエスト | `title?`, `message?`, `value?`, `detail?` | すぐ `{}` | 進捗ダイアログを開く。**既に開いていればエラー**（下記）。 |
| `ui.updateProgress` | 通知（旧 `ui.progress` を改名） | `title?`, `message?`, `value?`, `detail?` | なし | 開いている進捗ダイアログの内容を、送った内容で置き換える。閉じていれば無視し、アプリのログに残す。 |
| `ui.hideProgress` | リクエスト | なし | すぐ `{}` | 進捗ダイアログを閉じる。閉じていれば何もしない。 |
| `ui.alert` | リクエスト | `message`, `title?`, `okLabel?` | OK を押したら `{}` | OK だけのダイアログ。 |
| `ui.confirm` | リクエスト（既存） | `message`, `title?`, `okLabel?`, `danger?` | `{ok: bool}` | 変更なし。 |
| `ui.showResult` | リクエスト | `message`, `title?`, `kind?: "info"/"warning"/"error"` | すぐ `{}` | 結果ダイアログ。§4 のとおり、進捗ダイアログを置き換えずに別に積む。何度でも呼べ、呼んだ後も処理や表示を続けられる。 |
| `ui.toast` | リクエスト | `message`, `kind?: "info"/"warning"/"error"` | すぐ `{}` | 実行の途中で出すトースト。 |

- 引数の形が違う場合は、どのリクエストも Invalid Params を返す（今の `ui.confirm` と同じ）。
  通知の `ui.updateProgress` はエラーを返せないので、形の違う項目は無視してログに残す。
- **進捗の内容は毎回すべて送る**。`ui.showProgress` も `ui.updateProgress` も、送らなかった項目は表示しない
  （`title` だけは省略するとコマンド名）。前の値を引き継ぐ「省略＝維持」はやめた。プラグインが知らない状態が
  アプリ側に残るのを避けるため。前の値を使い回したいなら、プラグインが自分で持って毎回送る。
- 3つの役割は重ならない：`show` は開くだけ、`update` は中身を置き換えるだけ、`hide` は閉じるだけ。
  段階の切り替え（見出しやバーの種類を変える）は `update` で行う。`hide` → `show` でも書けるが、
  ダイアログが一度閉じて開き直す。
  - `show` が開いているときに「入れ替える」のをやめてエラーにしたのは、黙って中身が変わる挙動を持たせない
    ため。ユーザーが進捗ダイアログを閉じる手段はキャンセルだけで、キャンセル後は `show` 自体が拒否される（§5）
    ので、開いているかどうかは常にプラグインが分かっている。このエラーはプラグインの書き間違いでしか起きない。
  - エラーコードは Invalid Params（引数の形の誤り）ではなく、アプリ独自の範囲（−32000 台）に「状態が合わない」を
    1つ用意する。
  - `progressDialog: true` のコマンドでは開始時に既に開いているので、最初の `show` がこのエラーになる。
    作者がいちばんはまりやすい所なので、`PLUGINS.md` のマニフェストの説明に明記する。
  - `update` が閉じているときに無視するのは、キャンセル後の「キャンセル中…」表示を遅れて届いた `update` で
    上書き・再表示させないため。通知なのでエラーは返せず、ログに残すだけにする。
  - `hide` が閉じているときに何もしないのは、後片付け（`finally` など）で状態を気にせず呼べるようにするため。
    二重に呼んでも害がない。
- `show` / `update` を1つにまとめなかったのは、ループ内の頻繁な更新で応答待ちの往復を作らないため
  （旧 `ui.progress` が通知だったのと同じ理由）。両者は同じパイプで順に処理されるので、`show` の直後の
  `update` が先に届くことはない。

### 3-1. 進捗の表示内容

| 項目 | 型 | 表示 |
|---|---|---|
| `title` | 文字列 | 段階の見出し。省略するとコマンド名 |
| `message` | 文字列 | バーの上の説明文 |
| `value` | 0〜1 の数値 | バーの位置（割合）。省略すると件数なし（不定のバー）。範囲外は 0〜1 に丸める |
| `detail` | 文字列 | 右下の文字列。「123 / 1,234 件」「3.2 MB/s」「残り 約2分」「経過 2:13」などはプラグインが自分で書く |

- v1 の「どの項目を表示するか」（`show`: count / rate / elapsed / remaining）をやめ、「何を表示するか」を渡す形にした。
  件数とバーを切り離したので、「件数なしのバーで総数だけ表示する」「件数とは別の尺度でバーを進める」も書ける。
  旧案の「件数なしのダイアログに `total` が来たら」という曖昧なケースも、この形では起こらない。
- 速度・残り時間・経過時間をアプリが計算する仕組み（`PluginProgressRate`、`show`）は**廃止**する。
  数字の書式は `initialize` の `app.locale` に合わせられる。
- 経過時間：`command.execute` の引数に **`startedAt`**（アプリが実行を開始した時刻、エポックからのミリ秒）を足し、
  プラグインは `現在時刻 − startedAt` で計算する。プロセス起動やライブラリ読み込みの時間も含むので、プラグインが
  自分の起動時刻から数えるより正確になる。取得用のメソッドは作らない（往復が増えるだけ）。
  - 代償：経過時間はプラグインが更新を送ったときにしか進まない。長い処理（モデル読み込みや大きな `fetchFile`）の
    間に止まって見えるのを避けたければ、プラグインが別スレッドで定期的に送る。承知のうえで、アプリ側には
    経過時間の表示を置かないことにした。

## 4. 表示のふるまい

- **進捗ダイアログ**：実行ごとに1行で、1つの実行の中で開く・閉じる・内容の置き換えを何度でも繰り返せる。
  複数のプラグインが同時に動いていれば、今と同じく1つのダイアログに行が並ぶ。1つの実行が進捗ダイアログを
  2枚重ねて出すことはない（`show` を2回呼ぶとエラー。§3）。
- **alert / confirm / 結果**：1本の待ち行列（キュー）に来た順に入り、画面に出るのは先頭の1つだけ。閉じると次が出る。後ろの進捗ダイアログは
  出したままにする（今の `ui.confirm` と同じ `z` の関係）。
  - alert / confirm は応答を待つ。プロセスが終わったら、答えていないものは閉じる。
  - 結果は応答を待たず、ユーザーが閉じるまで残る。**プロセスが終わった後も残る**。
  - 結果を進捗ダイアログの置き換えにしなかった理由：`showResult` はすぐ応答を返すので、その直後の
    `showProgress` で、ユーザーが読む前に結果が上書きされてしまう。
- **正常終了の `message`**（`command.execute` の戻り）：返されたらトーストに出し、省けば何も出さない。
  `progressDialog` の値に関係しない。複数行の長い結果を見せたいときは、終わる前に `ui.showResult` を呼ぶ。
- **意図しないエラー**：`command.execute` のエラー応答（ヘルパでは捕まえていない例外）、異常終了、
  起動失敗、タイムアウト。どれもトーストに出す。プラグインが想定しているエラー（タグ付けの失敗など）を
  どう見せるかは作者に任せる。
- **終了時**：進捗ダイアログを閉じ、答えていない alert / confirm も閉じる。結果ダイアログは残す。
- キャンセルで終わったときは、今と同じく何も出さない。

## 5. キャンセルとモーダル

- キャンセルボタンは進捗ダイアログにしかない（`$/cancel`、無視され続けたら強制終了、は今のまま）。
  **進捗ダイアログを出していない間に中止できるようにするのはプラグインの責任**。将来の案として、画面右下に
  実行中のプラグインを並べて、そこからキャンセルできるようにすることを残しておく（未決定）。
- キャンセル要求の後は、ダイアログ系のリクエスト（`ui.showProgress` / `ui.alert` / `ui.confirm` /
  `ui.showResult` / `ui.toast`）を**拒否**する。進捗ダイアログは「キャンセル中…」のまま、終了まで残す。
- 進捗ダイアログはモーダルで、実行中にタグ変更やログアウトをして処理が狂うのを防いでいる。進捗ダイアログを
  出していない間はこの保護がない（旧 `"never"` と同じ）。`PLUGINS.md` に作者向けの注意として書く。

## 6. Python ヘルパ（サンプル）

`plugin_sample/` と `plugin_recipes/` の `megaexplorer_plugin.py` は同一内容に保つ。

```python
# progressDialog: false のコマンド。true なら最初の show_progress は不要（呼ぶとエラー）
ctx.show_progress(title="一覧を取得中")                    # 開く（件数なし）
ctx.update_progress(title="一覧を取得中", message="…/写真/2024")  # 毎回すべて送る
ctx.alert(f"{n}件見つかりました")                          # 進捗ダイアログは後ろに出たまま
ctx.update_progress(title="比較中", value=0, detail=f"0 / {n:,} 件")  # 段階の切り替えも update
for i, x in enumerate(xs):
    ctx.update_progress(title="比較中", value=i / n,
                        detail=f"{i:,} / {n:,} 件  経過 {ctx.elapsed_text()}")
ctx.alert(f"重複 {k} 組")
ctx.update_progress(title="後片付け中")                    # 件数なしに戻す
ctx.hide_progress()                                        # 閉じていても害はない
ctx.show_result(f"{k} 組を整理しました")
ctx.toast("一時ファイルを削除しました")
return                                                     # message を返せばトースト
```

ヘルパの引数は素直に `None` 既定でよい（`None` の項目は送らない＝表示しない）。「省略＝維持」が無いので、
省略と `null` を区別する番兵は要らない。

追加するもの：`show_progress` / `update_progress`（旧 `progress` を置き換える）/ `hide_progress` / `alert` /
`show_result` / `toast`、`started_at` と、速度・残り時間・経過時間を文字列にする補助（サンプル扱い）。
`confirm` は今のまま。

## 7. 実装で手を入れる場所と順序

1. `PluginManifest`：`progress` / `result` の解析と `PluginCommand` の該当フィールドを削除し、
   `progressDialog` を足す。`kPluginApiVersion = 2`。単体テストも合わせる。
2. `PluginRun`：新しいメソッドを受け付け、`ui.progress` を `ui.updateProgress` に改名する。応答を待つ alert は
   `ui.confirm` と同じ応答待ちIDの仕組みを使う。キャンセル後の拒否と、開いているときの `ui.showProgress` の
   エラー（独自コード）も入れる。`command.execute` に `startedAt` を足す。
3. `PluginController`：`ProgressState` を表示状態・`title` / `message` / `value` / `detail` に作り替える。
   `current` / `total` / `show` / `PluginProgressRate`（`src/qml/PluginProgressRate.h` ごと）、旧来の遅延表示タイマー、
   `resultInDialog` の処理を削除する。
   alert / confirm / 結果の待ち行列を作る（`mConfirms` に kind を足し、結果は終了後も残す）。
4. QML：`PluginConfirmDialog` に alert と結果の見た目を足す。`PluginProgressDialog` で行ごとのタイトル・
   割合のバー・`detail` を出し、項目を数字から組み立てる処理と結果表示の部分を削除する。
   ToastStack から `ui.toast` を出す。
5. `PLUGINS.md`：マニフェストの表、メソッドの節、"What the user sees"、キャンセルの節を書き直す。
6. `plugin_sample/`：新しい API の見本として全コマンドを作り直す（段階ごとに見せ方を変える例、
   `progressDialog: false` + `ui.toast`、`ui.showResult` の複数回呼び出しを含める）。
   `plugin_recipes/` の export-csv と slideshow も移行する。
