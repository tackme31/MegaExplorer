# 名前衝突の解決 — 全経路共通仕様

> **状態: 未実装。** `docs/REQUESTS.md` の `[バグ] フォルダに入ったファイルが上書き判定されない`
> を発端に、コピー・移動・アップロード・貼り付けの衝突挙動を横断で決め直したもの。SDK の調査は
> 済み（本書 §1 は実測ではなくコード読解に基づく事実）、UI 実装はこれから。**この仕様を採ると
> 発端のバグは再帰チェック無しで解消する**（§4-1）。積み残しは §6。

2026-08-14。コードは `third_party/sdk` まで読んだが、実機での検証はしていない。§6-2 だけは
実測が必要な項目として残してある。

---

## 0. 結論（先に要約）

1. **軸は「落とした集合」ではなく「衝突した部分集合」。** 非衝突分は常に通るので、ダイアログの
   形を決めるのは衝突側の構成だけ。これを取り違えると仕様が件数×種別で爆発する。
2. **Keep both（リネーム）を衝突ダイアログから全廃する。** ただし「同一フォルダへの貼り付け」は
   衝突ではなく**複製**として扱い、無確認で `- Copy` を付ける。Windows Explorer と同じ線引き。
3. **フォルダに Replace は出さない。** MEGA にフォルダのマージ手段が無く（§1-3）、Replace を
   実装すると「既存フォルダごとゴミ箱送り」になってソースに無いファイルまで消える。
4. **Replace は、衝突集合にファイルが 1 つ以上あるときだけ表示する。** この 1 行から §3 の表が
   全部導ける。
5. **フォルダの Skip は Explorer と意味が違う**（サブツリーごと除外される）。SDK の制約による
   既知の差異として受け入れる。§5 に明記。

## 1. SDK 調査（事実）

### 1-1. 存在チェックにネットワークは要らない

発端の疑問は「ドロップした全ファイルについて存在確認の API を叩く必要があるか」だったが、**答えは
否**。`MegaApi::getChildNodeOfType()` は `MegaRequestListener` を取らない同期関数で、実装は
`client->childnodebynametype()` → `NodeManager`（メモリ）→ 未ロードならローカル SQLite の
`SELECT ... FROM nodes WHERE parenthandle=? AND name=? AND type=? limit 1` に落ちる。

- `third_party/sdk/src/megaapi_impl.cpp:19410`（`getChildNodeOfType`）
- `third_party/sdk/src/db/sqlite.cpp:4212`（`childNodeByNameType`）

`fetchNodes()` 済みならサーバには行かない。コストは `sdkMutex` の取得と最悪 1 名前あたり SQLite
クエリ 1 本のみ。アップロードは `UploadController::kMaxFilesPerUpload = 100` で頭打ちなので、
同期呼び出しで問題ない。SDK 自身も `MegaFolderUploadController::createNextFolderBatch()` で
階層ごとに `client->getChildren(parent)` を 1 回呼んで子をプリロードしてから名前検索している
（`megaapi_impl.cpp:32321-32339`）ので、階層単位で一括化する余地もある。

**この事実は §4-1 により今回は使わないが、将来マージ対応（§6-1）を入れるときに前提となる。**

### 1-2. フォルダアップロードは既存フォルダへ強制マージする

これが発端のバグの機構。`MegaFolderUploadController::start()` は転送ルートの leaf 名で
`getChildNode()` を引き、同名フォルダがあればそれを再利用する:

```cpp
auto leaf = transfer->getFileName() ? transfer->getFileName() : path.leafName().toPath(true);
newTreeNode->megaNode.reset(megaApi->getChildNode(mUploadTree.megaNode.get(), leaf.c_str()));
```
（`megaapi_impl.cpp:32055-32060`。`32078` のコメントが「同名フォルダなら両者の内容はマージ
される」と明言している）

中のファイルは `UseLocalVersioningFlag` 付きで putnodes されるため、同名ファイルは新バージョンと
して積まれる＝ユーザから見れば無言の上書き。アプリ側は `UploadController::collisionsFor()` が
フォルダを除外している（`src/qml/UploadController.cpp:334`）ため第 1 階層のファイル名しか見て
おらず、ネストした衝突がすり抜けていた。

**ネストしたファイル単位のフックは無い。** `genUploadTransfersForFiles()` が作るサブ転送は
`mtime` / `mFolderTransferTag` / `appData` / `mFsType` しか設定せず、名前は常にローカルの leaf
（`megaapi_impl.cpp:32497-32513`）。したがって「中の 1 ファイルだけ別名で」も「中の 1 ファイル
だけ飛ばす」も、SDK の再帰アップロードを使う限り**表現できない**。

一方、**転送ルートのフォルダ名は変更できる**。`MegaUploadOptions::fileName` は "Custom file or
folder name in MEGA"（`third_party/sdk/include/megaapi.h:11530`）で、上記 `getFileName()` が
これを読む。ただし現状 `IMegaClient::upload()` に名前引数が無く、`MegaSdkClient` は
`startUpload(..., /*options*/ nullptr, ...)` を渡している（`src/mega/MegaSdkClient.cpp:477`）
ので、使うなら配線が要る。→ 本仕様では使わない（§2-3）。

### 1-3. コピーはマージできない / 移動はバージョン化しない

- `copyNode()` はフォルダのサブツリーを **1 リクエストでサーバ側コピー**する。中間状態が作れない
  ので「既存フォルダへマージ」という操作が原理的に書けない（`src/core/IMegaClient.h:247-260`）。
- 同じコメントが言うとおり、**ファイル**については `newName` を空にすると既存ファイルの新バージョン
  として乗る。これが MEGA における「上書き」の最も近い実現手段。
- `moveNode()` にはこのバージョン化が無い。単なる移動としか書かれていない
  （`megaapi.h:14431-14468`）。MEGA は同名兄弟を許すので、そのまま移動すると同名が 2 つ並ぶ。
  **移動の Replace は「既存をゴミ箱へ移動 → 移動」の 2 リクエスト**になる。
- `COLLISION_RESOLUTION_OVERWRITE / NEW_WITH_N / EXISTING_TO_OLDN` は `startDownload()` の引数で
  （`megaapi.h:17600`）、**アップロードに対応物は無い**。

### 1-4. 件数とサイズは同期・ローカルで取れる

`MegaApi::getSize(node)` はフォルダに対しサブツリー全体の合計を返す同期関数
（`megaapi.h:20241-20250`）。`getNumChildFiles()` も同様。ネットワークに行かないので、
**どのダイアログにも「N ファイル / X GB が追加されます」を無条件で添えられる**。

## 2. 現状のコードで何が起きているか

### 2-1. Keep both は「一選択肢」ではなくコピー経路の既定エンジン

`startCopyBatch()` は衝突が無ければ `onConflict = CopyConflict::Rename` に落とし、全エントリを
`uniqueCopyName()` に通す（`src/qml/FileMutationController.cpp:558, 583-588`）。つまり Rename は
ダイアログの答えである前に、**通常のコピー経路そのもの**。単純に削除すると壊れる。

### 2-2. フォルダは今もダイアログを通っていない

`collides()` が `!entry.isFolder` 条件付き（`FileMutationController.cpp:538`）。MEGA は同名
フォルダの共存を許すため「衝突ではない」と扱われ、必ず `uniqueCopyName()` 経由で `- Copy` が
付く。**別フォルダへの貼り付けでも**そうなる。

### 2-3. 同一フォルダへの貼り付けは、ファイルだけダイアログを通る

自分自身が `existingFiles` に入るため。フォルダは 2-2 により通らない。よって §3-2 は
「フォルダは現状維持、ファイルは挙動変更」になる。

判定手段は追加 API 不要。コピー経路は貼り付け先の一覧をすでに読み直しているので
（`FileMutationController.cpp:456, 513, 690`）、**エントリ自身のハンドルがその一覧に含まれるか**
で同一フォルダ判定ができる。`NodeRef` は親ハンドルを持たない（`src/core/NodeRef.h:12`）が、
持たせる必要もない。

### 2-4. ダウンロードは無言のサフィックス付け

`COLLISION_RESOLUTION_NEW_WITH_N` を使っており、ローカルの Downloads で衝突しても黙って
`(1)` が付く（`src/qml/DownloadController.cpp:132`）。ブラウザと同じ。本仕様の対象外。

## 3. 仕様

### 3-0. 選択肢の定義

| 選択肢 | 衝突したもの | 衝突していないもの |
|---|---|---|
| **Replace** | 上書き（**ファイルのみ**。フォルダは常にスキップ） | 実行 |
| **Skip** | 何もしない | 実行 |
| **Cancel** | 何もしない | **実行しない**（操作ごと取りやめ） |

Skip と Cancel の差は右列だけであり、ここが仕様の肝。ダイアログ本文に「他の N 件はそのまま
コピーされます」と書かないと Skip の意味が伝わらない。

**Replace は、衝突集合にファイルが 1 つ以上あるときだけ表示する。**

### 3-1. 別フォルダへのコピー / 移動 / アップロード

| 衝突した対象 | ダイアログ | 選択肢 | Replace の意味 |
|---|---|---|---|
| なし | 出さない | — | — |
| ファイル（単一） | 出す | Replace / Skip / Cancel | その 1 ファイルを上書き |
| ファイル（複数） | 出す | Replace / Skip / Cancel | 衝突した N ファイルすべてを上書き |
| フォルダ（単一） | 出す | **Skip / Cancel** | — |
| フォルダ（複数） | 出す | **Skip / Cancel** | — |
| ファイル・フォルダ混在 | 出す | Replace / Skip / Cancel | **ファイルのみ上書き。フォルダは Replace を選んでもスキップ** |

混在ケースは本文でこの非対称を明示すること:

> 3 個のファイルと 1 個のフォルダが、コピー先に既にあります。
> 「置き換える」を選ぶと**ファイルのみ**上書きされ、**フォルダはスキップ**されます。
> 　[置き換える] [スキップ] [キャンセル]

**衝突が 1 件でも選択肢は減らさない。** そのとき Skip と Cancel は結果が同じになるが、件数で
ボタン構成が変わる方が混乱する。Explorer も単一衝突で Skip を出す。

各操作の実装手段（§1-3 より）:

| 操作 | Replace の実現 |
|---|---|
| コピー | `copyNode()` に `newName` 空を渡す（新バージョンとして乗る）＝現状の `CopyConflict::Replace` のまま |
| 移動 | 既存をゴミ箱へ移動 → `moveNode()`。**2 リクエスト** |
| アップロード | 既存をゴミ箱へ移動 → アップロード。現状の `replaceHandle` 機構がそのまま使える |

### 3-2. 同一フォルダへの貼り付け

| 対象 | 挙動 |
|---|---|
| ファイル（単一 / 複数） | 無確認、`- Copy` 付与 |
| フォルダ（単一 / 複数） | 無確認、`- Copy` 付与 |
| ファイル・フォルダ混在 | 無確認、`- Copy` 付与 |

ダイアログを出さないので件数・種別で分岐しない。`uniqueCopyName()` が `taken` を都度更新する
ので、同名が複数あっても `- Copy (2)` と重複回避される（`FileMutationController.cpp:583-588`）。

### 3-3. ダウンロード

全パターン対象外・現状維持（§2-4）。

### 3-4. ダイアログ本文に添える情報

`MegaApi::getSize()` / `getNumChildFiles()` が同期・ローカルで使える（§1-4）ので、衝突ダイアログ
には件数と追加サイズを添える。フォルダが絡むとき特に効く。

## 4. この仕様が導く帰結

### 4-1. 発端のバグは、再帰チェック無しで消える

ネストしたファイルの上書きは「同名フォルダへのマージ」経由でしか起きない（§1-2）。本仕様では
フォルダ名が衝突した時点で Skip / Cancel なので**マージ自体が発生せず**、`/FolderA/foo.png` が
触られる経路が消える。§1-1 で確認した「全ファイルの存在チェック」は**不要**で、必要なのは
第 1 階層の名前照合だけ。見積もりが大きく下がる。

### 4-2. 代わりにフォルダのマージが失われる

ローカルの `FolderA` に写真を 3 枚足して再アップロード、という使い方が Skip / Cancel では通らない
（現状はマージされる。それが同時にバグの原因でもある）。回避策は「アプリで `/FolderA` を開いて
中身をドラッグ」。→ §6-1 へ。

## 5. Windows Explorer との既知の差異

本仕様は Explorer 準拠を軸に置いたが、**フォルダの Skip だけは意味が異なる**。

- Explorer: 同名フォルダは**マージ**され、Skip は衝突した**ファイル**だけを除外する。
  フォルダ内の非衝突ファイルはコピーされる。
- 本仕様: 同名フォルダは**サブツリーごと除外**される。中の非衝突ファイルも来ない。

原因は §1-3（`copyNode()` がマージできない）と §1-2（フォルダアップロードにファイル単位の
フックが無い）で、SDK の制約。**仕方ないものとして受け入れる**と決定した。ダイアログの文言で
「フォルダ `FolderA` はスキップされます（中身を含む）」と、中身ごとであることを明示して緩和する。

## 6. 積み残し

### 6-1. フォルダアップロードのマージ対応（別項目）

§4-2 の機能欠落を埋めるなら、アップロード経路にだけ 4 つ目の選択肢「マージ」を足すことになる。
可能なのはアップロードだけ（コピーは §1-3 により不可）なので、**今回入れると 3 経路の対称性が
即座に崩れる**。本仕様を実装したうえで、単独の項目として設計し直すのが順当。そのときは §1-1 の
「ネストした衝突の検出はネットワーク不要」が前提として効いてくる。

### 6-2. MEGA がコピーをストレージに二重計上するか（未検証）

MEGA のコピーは物理ブロブを再アップロードせずノードだけ作るため、課金がノード単位か実体単位かで
「大きいフォルダの複製は容量を食う」という懸念の重みが変わる。**未確認**。テストアカウントで
`megatool` を使い、フォルダをコピーする前後で `getAccountInfo` の使用量を比較すれば判定できる。

二重計上されないなら、§3-4 のサイズ表示や「閾値を超えるコピーは常に確認」といった案の優先度は
下がる。

### 6-3. 同名エントリを複数まとめて Replace したとき

クリップボードに同名のファイルが 2 つ（別フォルダ由来）あり、両方が衝突した状態で Replace を
選ぶと、2 つ目が 1 つ目に対して版を重ねる。アップロード経路には `claimedReplaceHandles` による
対策があるが（`src/qml/UploadController.cpp:367`）、コピー経路には対応物が無い。実装時に
揃えること。
