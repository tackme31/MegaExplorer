# サムネイルのローカルキャッシュ — 実装前調査

> **状態: 机上調査のみ。実装未着手、実測値ゼロ。** 2026-09-12、`develop` の `664d5ab` 時点のコードと
> `third_party/sdk`（pinned `v10.17.0`）に対する調査。`docs/ROADMAP.md` の
> 「サムネイルのキャッシュ化」(M) と、それを前提とする「設定画面からキャッシュを削除する」(S) の下調べ。
> **結論:** 再起動を跨ぐ永続化は素直に入る。そして**自動無効化の機構はほぼ要らない** ——
> 内容が変わると node handle も変わるので、キャッシュキーがそのままバージョン同一性を表している。
> 陳腐化が残るのは「同じノードにサムネイル属性だけ後から差し替えられ、しかもその画面を開いたまま」の
> 1 ケースだけで、それを拾う手段は `onNodesUpdate`（= ROADMAP の L「リアルタイム反映」）しか無い。
> §2 の 4 点（保存場所・アカウント分離・後始末・サイズ表示）は 2026-09-12 に決定済み。
> **残る未確認は §7** —— ヒット時の体感差、実サイズ、そして QML `Image` の URL キャッシュ（§6-4）。

## 1. 現状

`ThumbnailService`（`src/core/ThumbnailService.h`）が `IMegaClient::getThumbnail` の前に置かれ、
**プロセス内の** handle → パスの成功キャッシュ（`mCache`、`ThumbnailService.h:55`）、実行中／待機中の
重複排除、並列上限 4 を持つ。**失敗はキャッシュしない**（同 `:19`）。

出力先は呼び出し側が決める契約（同 `:30`）で、実際に決めているのは
`ThumbnailController::computeDestinationPath()`（`src/qml/ThumbnailController.cpp:46-57`）:
`%TEMP%/<applicationName>Thumbnails/<10進handle>.jpg`。`applicationName` を使うことで
`MEGAEXPLORER_PROFILE` の分離がタダで効いている（`src/app/AppIdentity.h`）。

足りないのは**再起動を跨ぐぶんだけ**。ファイルは消していないので既にディスク上に残っているが、
「キャッシュ済みか」の判定がプロセス内の `mCache` なので、起動するたびに全部取り直している。

なお **SDK 自身はサムネイルをローカルにキャッシュしない**。`MegaApiImpl::getNodeAttribute`
（`megaapi_impl.cpp:22462`）は出力先の存在を見ずに `client->getfa(...)` へ行き、重複排除
（`API_EEXIST` 経路、`megaapi_impl.cpp:22563`）は同一プロセス内の同時リクエストに対するものだけ。
自前キャッシュが必要という前提は正しい。

## 2. 決定事項

| # | 論点 | 決定 | 理由 |
|---|---|---|---|
| 2-1 | 保存場所 | **`QStandardPaths::CacheLocation`**（= `%LOCALAPPDATA%\MegaExplorer\<appName>\cache`）配下 | `%TEMP%` は「今すぐ捨ててよい」場所で、Storage Sense の「アプリが使用していない一時ファイルを削除する」やディスク クリーンアップ、環境によってはログオン時の GPO が中身を消す。消えても再取得すれば済むが、**機能の売り（2 回目以降は取り直さない）が OS の都合で確率的に破れ**、しかもユーザーには理由が見えない。`CacheLocation` は Qt の言う「消してよいが勝手には消えない、バックアップも同期もされない」場所。`applicationName` を含むのでプロファイル分離も従来どおり効き、SDK の state cache と `session.dat`（`main.cpp:120-131`）と同じ `%LOCALAPPDATA%` 側に永続物が揃う |
| 2-2 | アカウント分離 | **`currentUserHandle()` の 10 進値でディレクトリを分ける** | 前例がそのままある。クイックアクセスのピンは同じ方法で口座ごとに分けられており、理由も書かれている（`src/platform/QSettingsPinnedFolderStore.h:11`「フラットなキーはマシン全体のもので、アカウントを切り替えると相手のピンが見える」）。node handle がアカウント間で衝突しないとは SDK のどこにも書かれておらず、**文書化されていない不変条件への賭け**になる。破れたときの症状（あるファイルに別アカウントの絵が出る）は原因の見えない不気味なバグ。メールアドレスは変わりうるし、パス名に PII を置くことになるので使わない |
| 2-3 | ログアウト時の後始末 | **しない** | クラッシュや強制終了ではログアウトが走らないので、そもそも保証にならない（「他アカウントのものが見えない」を担保するのは 2-2 のほう）。副作用として、同じアカウントに入り直した人がキャッシュを丸ごと失う。バイト列を消したい人には設定の削除ボタンがある。なお `%LOCALAPPDATA%` は Windows ユーザー単位で ACL が掛かるので、露出は「同じ Windows ユーザーが別の MEGA アカウントを使う」場合に限られる |
| 2-4 | 上限・自動削除 | **入れない。代わりに設定の削除ボタンの隣（またはラベル）に現在のサイズを表示する** | 200×200 の JPEG は 1 枚 5〜15KB で、実際に閲覧したぶんしか溜まらない。ゴミの主な出所は**削除されたノードのサムネイル**で、ハンドルキーゆえ回収の契機が無く永久に残る。掃除機構を作るのではなく判断材料をユーザーに渡せば、上限は要らない |

削除ボタンとサイズ表示は ROADMAP の S 行「設定画面からキャッシュを削除する」の担当。
**サイズの算出はディレクトリ列挙**なので、そこだけはファイル数に比例する（§6-3）。

## 3. SDK 調査 — 変更を検出する手段

### 3-1. `onNodesUpdate` + `CHANGE_TYPE_FILE_ATTRIBUTES` だけ

`MegaNode::CHANGE_TYPE_FILE_ATTRIBUTES = 0x10`（`megaapi.h:570`）の説明がそのまま答え
（`megaapi.h:1494`）: "Check if file attributes have changed, usually the thumbnail or the preview
for images"。読むのは `hasChanged(type)` / `getChanges()` だが、どちらも
**`onNodesUpdate` で通知されたノードでしか意味を持たない**（それ以外では常に false、
`megaapi.h:1461-1476`）。

そして**このアプリは現在リスナを一切登録していない**（`src/mega/` に `MegaGlobalListener` /
`addGlobalListener` の参照がゼロ）。ROADMAP の「①リアルタイム反映が入るまで再取得の口は②だけ」は
順番の都合ではなく、**技術的に他に手が無い**ということ。

### 3-2. Pull 型の検証トークンは存在しない

「開くたびに軽く確かめる」方式は公開 API では作れない。

- **`MegaNode::getFileAttrString()` は使えない。** 「チャットに添付されたノードでのみ有効、それ以外は
  常に NULL」（`megaapi.h:1762-1772`）。`fa` 文字列を世代トークンにする案はここで潰れる。
- **`getFingerprint()`（`megaapi.h:1148`）も `getModificationTime()` も駄目。**
  `MegaApi::setThumbnail(node, srcFilePath)`（`megaapi.h:15392`）と `setThumbnailByHandle` は
  **ノード本体を触らずに属性だけ差し替える**ので、内容の指紋も更新日時も動かない。
- `getThumbnail` のリクエストは `MegaRequest::getPrivateKey` で fa 文字列を返すが
  （`megaapi.h:14941`）、**取得したときにしか読めない**ので、取得を省くための検証には使えない。

### 3-3. 内容が変わると handle が変わる（この調査の要点）

アップロードは常に新しいノードを作り、バージョニング有効時は `restoreVersion` の説明どおり
「ノードは複製されて current になり、旧 current がその previous version になる」
（`megaapi.h:14595-14598`）。つまり**別デバイスでファイルを上書きされても、一覧に出てくるのは
新しい handle** なので、キャッシュは黙って miss して取り直す。

**キャッシュキー（node handle）が既にバージョン同一性を表している。** リアルタイム反映が無くても
内容変更は取りこぼさない。陳腐化する窓は「同じノードにサムネイル属性だけ後から付け替えられた」
場合だけ —— サムネイルを生成しないクライアントがアップロードし、後で別のクライアントが貼った経路。

### 3-4. 「サムネイルが後から付いた」は負のキャッシュを持たないことで賄える

`getThumbnail` はサムネイルの無いノードに対して `API_ENOENT` で失敗する（`megaapi.h:14930`）。
現状は失敗をキャッシュしない（`ThumbnailService.h:19`）。**これを維持するのが答え。**
`hasThumbnail()` は毎回 `getChildren` の返す新しい `MegaNode` から読むので、後から付いた
サムネイルは**次にそのフォルダを開いた時点で自然に拾われる**。機構追加ゼロ。

裏を返すと、`0x10` の通知が本当に要るのは「**開いたまま**のフォルダでその変化が起きたとき」だけ。

## 4. 自動更新のタイミング

| 契機 | 今できるか | 動作 |
|---|---|---|
| 起動 / フォルダを開く | ○ | **何もしない**。handle が同じなら内容も同じ（§3-3） |
| 別デバイスで内容を上書き | ○（構造的に） | 新 handle → 自動で miss。特別な処理は不要 |
| サムネイルが後から付いた（閉じている間） | ○ | 負のキャッシュを持たないので次回の一覧で拾う（§3-4） |
| サムネイル属性の差し替え（開いたまま） | **リスナ必須** | `hasChanged(0x10)` でその handle のファイルを削除 + `mCache` から落とし、表示中なら再要求 |
| 大量通知 / 全アカウント再読込（`nodes == NULL`） | リスナ必須 | **何もしない**（§5-a） |
| ノード削除 | ○ だが不要 | 放置（孤児化。設定の削除ボタンで回収、§2-4） |
| ツールバーのリフレッシュ | ○ | 一覧中の handle 集合ぶんを捨てる（ROADMAP どおり非再帰） |

**今の周で入れるべき自動更新は実質ゼロ。** ②（手動リフレッシュ）だけ実装すれば、①が来るまでの
陳腐化は上表の 4 行目 1 ケースに限定される。①が入ったときの追加も分岐 1 本で済む。

## 5. リスナを入れるときの罠（①の周への申し送り）

- **(a) `nodes == NULL` がある。** 「全アカウント再読込、または大量の通知が一度に来たとき」
  （`megaapi.h:9677`）。何が変わったか分からないので、**何もしない**を推奨 —— 陳腐化するのは
  見た目だけで、burst のたびに数百 MB を捨てるほうが損。手動リフレッシュが逃げ道。
- **(b) 起動直後の一斉通知をゲートする。** `sc` の追いつきで木全体が「変わった」ように見える。
  `EVENT_NODES_CURRENT`（= 6、「外部のノード変更をすべて受信し終えた」`megaapi.h:6506, 6608`）
  まで無視する。**前例あり**: `STUDY_FETCHNODES_PROGRESS_UI.md:183, 399` が発火箇所
  （`megaapi_impl.cpp:17220` ← `megaclient.cpp:5467`）まで特定済み。
- **(c) コールバックは SDK 内部スレッド**（`ARCHITECTURE.md:135, 206`）。既存サービスと同じ渡し方に
  乗せる。加えて QML の `Image` が掴んでいるファイルを消す順序に注意（§6-4）。
- **(d) `0x10` はサムネイルとプレビューを区別しない。** 区別不要（プレビューはそもそも
  ディスクに残さない設計 —— `STUDY_PREVIEW_PANE.md` の結論）。

## 6. 実装の当たり

### 6-1. パス解決はサービス側へ移す

現在は `ThumbnailController::computeDestinationPath()` が決めているが、パスが**アカウントを含む**
ようになると controller では解決できない: `tabFactory`（`main.cpp:194-210`）は
`ThumbnailController` に `IMegaClient` を渡しておらず、しかも `TabsController`
（`main.cpp:217`）はログイン前に最初のタブを作りうる。

`ThumbnailService` は `mClient` を持つので `currentUserHandle()` を**要求時に遅延解決**できる。
基底ディレクトリ（`CacheLocation` は Qt の概念で、`src/core` は Qt 非依存）は
**コンストラクタに文字列で注入**する —— `MegaSdkClient` の basePath や `WindowsSessionStore` の
パス（`main.cpp:128-131`）と同じ形。サービスが `<base>/<accountKey>/<10進handle>.jpg` を組む。

`ThumbnailService.h:30` の「destinationPath は呼び出し側が解決する」契約はこの変更で消える。
**契約を書き換える判断ごと記録すること。**

### 6-2. ディスクヒットの判定は `ILocalFileSystem` 経由

変更の本体は「キャッシュ済みか」の判定を `mCache` から**ファイルの存在**へ広げること。
`ILocalFileSystem::entryFor(path)`（`src/core/ILocalFileSystem.h:46`）がそのまま使え、実体
（`QtLocalFileSystem`）は `main.cpp` で既に作られ共有されている。1 行あたり stat 1 回で足りる。

**一方、削除の口が無い。** 同ポートには `createFile` / `entryFor` / `listDirectory` /
`moveToFreeName` しか無いので、リフレッシュ時の破棄と設定の削除ボタンのために
**`ILocalFileSystem` へ削除操作を足す必要がある**。これが唯一のインタフェース変更。

### 6-3. アカウント配下はフラットでよい

リフレッシュが捨てる単位は「今の一覧に並んでいる handle の集合」なので、フォルダ→子の索引は
不要。ディレクトリのシャーディングも足さない —— 名前指定の open は NTFS の B-tree で速く、
ファイル数に比例するのは列挙だけ（= 削除とサイズ表示のときだけ、§2-4）。

### 6-4. **未解決のリスク: QML `Image` の URL キャッシュ**

`STUDY_PREVIEW_PANE.md` §4.1 が同じ問題を踏んでいる —— QML の `Image` は source URL で
ピクスマップをキャッシュするので、**同じパスのファイルを差し替えても古い絵が出る恐れがある**。
プレビューはメモリ保持に切り替えて回避したが、サムネイルは `file:///` を使い続ける（グリッドの
デリゲートが `thumbnailPath` をそのまま食う）ため、**リフレッシュで同じ handle を取り直す経路で
これが露出しうる**。候補は `Image.cache: false`、URL に版を付ける、`QQuickImageProvider` 経由。
**着手する周が実機で確認して決めること**（起動を跨ぐ経路ではプロセスが変わるので露出しない。
踏むのはリフレッシュと §4 の 4 行目だけ）。

## 7. 未確認・残る論点

- **ヒット時の体感差を測っていない。** Release で、サムネイルの多いフォルダを開き直したときの差。
  Debug で測ってはいけない（`docs/BUILD.md`）。
- **実サイズの実測がない。** `main.cpp:124` のコメントにある 64 万ノードのアカウントを広く閲覧した
  場合にどこまで育つか。§2-4 のサイズ表示が入れば、そこで見える。
- **`CacheLocation` の実パスを実機で確認していない。**
  `%LOCALAPPDATA%\MegaExplorer\MegaExplorer-dev\cache` になる想定（dev プロファイル時）。
  `applicationName` 経由のプロファイル分離が `CacheLocation` でも効くことの確認を含む。
- **属性差し替え（§3-3 の残る窓）を実機で再現する手段がない。** 別クライアントから
  `setThumbnail` 相当を叩く必要があり、`megatool` には口が無い。①の周も単体テスト止まりになる見込み。
- **旧 `%TEMP%/<appName>Thumbnails` の扱い。** 既存ユーザーの機械に残っている。移行はせず放置か、
  初回起動時に消すか。**未決**（捨てても機能が壊れないキャッシュなので移行の義務は無く、
  `CLAUDE.md` の「永続データは負債」には当たらない）。
