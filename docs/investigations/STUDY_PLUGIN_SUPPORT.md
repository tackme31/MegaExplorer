> ただしプロセス数は設計でなくポリシーにする）、§6（着手順。最初の2段はプラグイン抜きでも有益）。

**本書は現在のコードに対する調査である。** 以下の「現状」はすべて `9dc663f` 時点の
`src/core/MenuAction.h` / `MenuActionResolver` / `qml/ActionCatalog.qml` / `src/core/PreviewKind.h` /
`src/qml/PreviewController` / `src/qml/FileMutationController` / `src/platform/WindowsSessionStore` を

想定していたプラグイン像（依頼時点）:

- マニフェストと DLL を特定フォルダに置くと**起動時に読み込まれる**
- コンテキストメニューに項目を追加できる
- 独自プレビューを拡張できる
- 各アクションにハンドラを登録できる（保存時・リネーム時などに処理を差し込む）

全体の見立てとしては、**機能面の下地はかなり揃っている**。「C++ が構造を、QML が文言と実行を持つ」と
いう右クリックメニューの分離、`PreviewKind` + `PreviewController` + `PreviewImageProvider` の3点、
`IMegaClient` のポート境界がそのまま拡張点になる。よって機能面の作業は新しい層を足すことではなく、
**閉じた列挙をレジストリに開くこと**。

一方で**難所は機能ではなくセキュリティと実行環境**にあり、調査時間の大半はそちらに費やした（§3〜§5）。

## 1. 拡張ポイントごとの改修

### 1-1. コンテキストメニュー — 一番きれいに入るが、破壊的変更を1つ含む

現状 `src/core/MenuAction.h` は `enum class` の閉じた語彙で、`MenuActionResolver` がサイト（右クリック
場所）ごとの**メンバーシップ**と**大域固定の表示順**を持つ。実行は `qml/ActionCatalog.qml` の
`entries` にあり、呼び出し側が毎回作る `ctx` オブジェクトを1つ受け取る。

- `MenuAction` を enum → **安定文字列ID**（`"core.download"` / `"acme.convert"`）へ。
  **これが最大の破壊的変更**で、resolver・`src/qml/MenuActions.cpp`・`ActionCatalog.qml`・
  対応するテストに波及する。
- 順序が大域固定なので、**プラグイン項目用のセクション**という概念が要る（末尾に「拡張」区画を作るか、
  マニフェストで `insertAfter: "core.download"` を指定させるか）。
- 実行側は `ActionCatalog.qml` の `entries` にプラグイン由来のエントリをマージするだけ。
  結果として **`ctx` の形がそのままプラグインAPIの公開契約になる**ので、今の `ctx`
  （handle / isRoot / name / pinned / entries / request*() / navController / mutations / canPaste）の
  うち何を契約に含めるかを決める作業が実質の設計になる。`navController` や `mutations` をそのまま
  渡すとコントローラの全 `Q_INVOKABLE` が公開APIになってしまう。
  **なお §4 のプロセス分離を採る場合、`ctx` をそのまま渡すことは原理的にできない**（ポインタは
  境界を越えられない）ので、シリアライズ可能なプロトコルの設計に置き換わる。

### 1-2. 独自プレビュー — 3箇所のハードコードをレジストリ化

現状は拡張子から `previewKindForName()` が `enum PreviewKind{None,Image,Text}` を返し、
`PreviewController` が取得し、`PreviewPane.qml` が `kind` で分岐する、という3箇所ハードコード。

- 拡張子 → プロバイダの**登録テーブル**にする。コア組み込みの Image / Text も同じテーブルに登録して
  ドッグフードする（これをやらないとプラグイン経路だけが二級市民になる）。
- `PreviewKind` に `Custom` を足し、コントローラは「誰が担当か」と生データを持ち、`PreviewPane` は
  `Loader` でプラグインの QML を差す。
- 決めごとが要るのは**データの渡し方**。バイト列を丸ごと QML に渡すか、変換側で PNG にして
  既存の `PreviewImageProvider` 経由にするか。後者のほうが安全で、`kMaxTextPreviewBytes` に相当する
  サイズ上限もそこで効かせられる。
- 3つの用途の中で**唯一、プロセス分離と完全に相性が良い**のがこれ。`バイト列 → PNG/テキスト` は
  純粋関数で、リクエスト/レスポンス1往復に収まる。テキストは50KB上限、画像もせいぜい数MBなので
  共有メモリすら要らずコピーで足りる。

### 1-3. アクションへのフック — ここだけ設計判断が重い

`FileMutationController` の `Q_INVOKABLE` 群（`renameEntry` / `moveHandlesToRubbish` / `createFolder` …）は
すべて fire-and-forget で、結果は SDK スレッド由来のシグナルで返る。ここに素直にフックを刺すと
**プラグインのコードが SDK スレッドで動く**ので、先に整理が要る。

段階を分ける:

1. **after フック（通知のみ）**: `renamed(handle, oldName, newName)` 等を GUI スレッドに載せて配るだけ。
   副作用なし、プラグインが失敗してもコア動作に影響しない。ほぼリスクなしで先に出せる。
2. **before フック（拒否・値の変形）**: 「プラグインが名前を書き換えられる／中止できる」形。同期APIか
   非同期チェーン（プラグイン応答待ち→本処理）が必要で、**プラグインが固まるとアプリが固まる**。
   タイムアウトとフォールバックの設計が要るので2周目に回す。プロセス分離を採ると、この問題は
   in-process より確実に顕在化する（境界を跨ぐ同期待ちになるため）。

置き場所は `src/core/FileOperationService` 側（SDK に近く、テスト可能）に**ディスパッチャを1つ**入れる
のが自然。`src/qml` のコントローラ群に入れると QML 層に業務ロジックが戻ってしまう。

## 2. 他ソフトウェアがセキュリティをどう扱っているか

方針を決める前に有名どころを調べた（出典は §8）。対応は3系統に分かれ、**ネイティブアプリの多くは
1番目、つまり「諦めて信頼を明示する」に落ちている**。

**系統1: サンドボックスせず、信頼を明示的な操作にする。**
VS Code はドキュメントで「ブラウザ拡張や Android アプリと違い、VS Code 拡張はユーザーのシステムに
完全なアクセスを持ち、粒度の制御は一切ない」と明言している。代わりに Workspace Trust / Publisher Trust
（発行者単位の初回同意）/ Verified Publisher（ドメイン所有権証明）/ Marketplace の署名検証を積む。
Obsidian はさらに直球で、「技術的制約によりプラグインを特定の権限に制限することは信頼性をもって
行えない。プラグインは Obsidian の権限を継承する」と help に書き、**Restricted Mode を既定ON**
（サードパーティコードを一切実行しない）にしている。審査は自動スキャン＋人気/報告されたものだけ
手動レビューで、全リリースはレビューできないと明記。
**この系統の本質は技術的防御ではなくガバナンス**（既定オフ・同意・署名・審査・通報）。

**系統2: 別VM／別プロセスに隔離する。**
Figma が教材として良い。当初は Realms shim（同一JS VM内で論理的に隔離）を使ったが、内外のオブジェクトを
取り違えさせる脱出が複数見つかって破られ、現在は **QuickJS を WASM にコンパイルして別VMで実行**する。
教訓は「**同じランタイム内での論理的隔離は失敗しやすく、ランタイムごと分けると成立する**」。
Chrome は別プロセス＋権限マニフェストだが万能ではなく、学術調査では公式ストアの拡張のうち最小権限の
精神に沿うのは 39.8% だけとされ、MV3 でもデータ窃取は防げていないと報告されている。
**権限モデルは開発者が正直に最小申告することを前提にしており、それ自体は防御にならない。**

**系統3: API を絞ることを実質のサンドボックスにする。**
Photoshop の CEP → UXP 移行がこれ。オーディオの VST 等がプロセス外ブリッジをやるのは主に
セキュリティでなく**クラッシュ隔離**が動機、という点も混同しないよう記録しておく。

## 3. ABI を絞ってもセキュリティにはならない（本調査で最も重要な結論）

当初「プラグインに許すのはコンテキストの read と非破壊的操作だけ」という ABI 設計を考えたが、
**in-process の DLL に対してこれは一切の防御にならない。**

**理由1: 順序。** `LoadLibrary` した瞬間、DLL はプロセスのアドレス空間の一部になる。`DllMain` と
静的初期化子は、こちらが `GetProcAddress` でマニフェスト検証関数を引く**前に**走る。つまり検証コードに
到達した時点で任意コードは既に実行済みで、**検証は原理的に間に合わない**。

**理由2: 同一アドレス空間。** その後もプロセス全メモリの読み書き、IAT パッチや Detours による関数
差し替え、自前で `megaapi.h` をリンクして自分のスレッドから MEGA を叩く、`WinHTTP` での外部送信、
プロセス起動、ユーザーのファイル読み取り — どれも止められない。

**理由3（最重要）: 一番楽な経路はメモリ攻撃ですらない。**
`WindowsSessionStore` はセッショントークンを **DPAPI** で保護して保存している。DPAPI のユーザースコープは
「**そのユーザーとして動く任意のコードが復号できる**」という保護なので、悪意あるプラグインは動作中の
アプリのメモリに一切触れずに、(1) 同じ保存場所を読み、(2) `CryptUnprotectData` を自分で呼び、
(3) 自分で `MegaApi` を作ってログインする、で完結する。ABI もプロセス境界も関係ない。
**被害範囲は全アカウント**で、MEGA は E2E なのでセッションは復号鍵も握る＝全ファイルの平文が読めて消せる。

**この DPAPI 経路は、単にプロセスを分けただけでは塞がらない。** 同じユーザートークンで動く子プロセスは
同様に復号できる。実際に塞ぐにはサンドボックスでファイルシステムアクセスごと落とし、セッション保存先に
手が届かない状態を作る必要がある（AppContainer 下で DPAPI がどう振る舞うかは未検証。やるなら実測が要る）。

したがって、**ABI を絞る設計は「バグのあるプラグインに対する事故防止」としては有効だが、悪意に対しては
効果ゼロ**。この区別を曖昧にしたまま権限宣言UIを作ると、守られていない保証をユーザーに約束することになり
かえって有害になる。Obsidian が「権限を継承する」と正直に書いているのは、おそらくこの理由。

### 3-1. QML と DLL の非対称性 — ここが唯一の逃げ道

両方 in-process なのに、**QML/JS プラグインと DLL プラグインでは安全性がまったく違う**。理由は一つで、
**QML から任意のマシンコードを実行する手段がない**こと。`LoadLibrary` 相当がなく生ポインタも作れないので、
JSエンジン自体が境界として機能し、届く範囲は C++ から明示的に生やした API だけになる。

| | 任意コード実行 | セッション到達 |
| --- | --- | --- |
| C++ DLL（in-process） | 可 | **可**（ABI 設計と無関係） |
| C++ exe（別プロセス、非サンドボックス） | 可 | **可**（DPAPI 経由） |
| QML/JS（in-process、API 絞り） | 不可 | 公開した API の範囲のみ |
| 別プロセス + AppContainer | 可 | 不可（にできるはず・要検証） |

**条件が1つある。** `import` でプラグインディレクトリから C++ の QML プラグイン（`.dll`）を読めてしまうと
QML ティアの保証が丸ごと崩れる。QML ティアを作るなら、**エンジンの import パスにプラグインのネイティブ
モジュールを載せないこと**が前提条件。

## 4. 実行環境の分離 — IPC 化と、ホストの粒度

### 4-1. 重いのは transport ではない

プロセス起動と通信そのものは安い。`QLocalServer`/`QLocalSocket`（Windows では名前付きパイプ）か、
子プロセスの stdin/stdout に JSON Lines を流すだけで、数百行の世界。想定3用途のうち**プレビューと
メニューはむしろ IPC 向き**（§1-2, §1-1）。重いのは次の3つ:

1. **API の表面を全部シリアライズ可能にする必要がある。** `ctx` をそのまま渡す案が消え、バージョン付きの
   本物のプロトコル設計になる。コード量でなく設計コストで、一度出すと後方互換の縛りが強い。
2. **before フックが最悪**（§1-3）。GUI スレッドが別プロセスの応答を待ち、タイムアウト・刺さり・
   プロセス落ちを全部扱うことになる。
3. **UI は境界を越えられない。** プラグインが QML でプレビュー画面を提供する、は別プロセスでは成立しない。
   やるならプロセス外レンダリング（共有テクスチャ合成）で、これはブラウザ級の複雑さ。

3 を受け入れると自然にこう割れる: **UI（QML）は in-process、API 絞りで担保。ロジック（デコード・
フック処理）は out-of-process。**

### 4-2. プロセス分離が実際に買うもの

**プロセスを分けただけではセキュリティは得られない**（§3 理由3）。得られるのは別の2つ:

| 得られるもの | プロセス分離だけ | + OS サンドボックス |
| --- | --- | --- |
| ABI 自由（任意言語） | ✅ | ✅ |
| クラッシュ隔離 | ✅ | ✅ |
| セキュリティ | ❌ | ✅（実装重い） |

上2つだけでも元は取れる。特に **ABI 自由**は大きく、どうせプロセスを分けるならプラグインのバイナリは
DLL でなく **`.exe`** でよく、その瞬間 MSVC / Qt / Debug・Release の ABI 縛りが完全に消える
（Rust でも Go でも Python でも書ける）。**IPC 案はセキュリティ対策としてより、ABI 問題の解決策として
評価するほうが正しい。**

### 4-3. ホストの粒度 — プラグインごと vs 集約ホスト

「プラグイン10個でプロセス10個は管理が大変なので、**ホストはこちらで用意し、その中で DLL を動的に
読む**」という案を検討した。これは実在パターンで、Windows の `svchost.exe`（複数サービスを1プロセスに
グループ化）、COM の `dllhost.exe`（サロゲート）、Chrome のプロセス数上限超過時の同居がまさに同じ判断。

**成否はホストをどれだけ痩せさせられるかに全部かかっている。** ホストが Qt をリンクすると、プラグインも
同じ Qt / MSVC / ビルド構成に縛られ、避けたかった ABI 地獄がそのまま戻る。逆に**純C ABI・Qt なし・
STL を境界に出さない**、実質「メッセージポンプ + `LoadLibrary` + ディスパッチ」だけの小さなバイナリに
できれば、縛りは「Windows の DLL で C ABI をエクスポートすること」だけになる（C/C++/Rust/Zig は書ける）。

そしてその前提が満たされるなら、**「10プロセスは管理が大変」という前提自体が弱まる**。ホストが痩せて
いれば1プロセス数MB、ライフサイクル管理のコードは1個でも10個でも同じ、Job object を使えば親が死んだ
ときに子が全部片付く。**N プロセスの本当のコストは、ホストが太っている場合にだけ効く。**

集約で失うもの:

1. **プラグイン相互の隔離。** A が B のメモリを読める・フックできる。1つの侵害が他を踏み台にできる。
2. **クラッシュの巻き添え。** 1つ落ちると全部落ち、**誰のせいか分からなくなる**。「今どのプラグインを
   ディスパッチ中か」を常に記録しておけば犯人は指させる。
3. **ハングの巻き添え。** 避けるならホストがプラグインごとにスレッドを持つ設計になり、「痩せている」の
   維持が怪しくなる。
4. **最小権限の喪失（一番効く）。** サンドボックスはプロセス単位なので、集約すると AppContainer の
   プロファイルが**全プラグインの要求の和集合**になる。ネットワーク不要なプラグインが、ネットワークを
   要求するプラグインと同じ権限のプロセスに同居する。§3 の結論（サンドボックスこそ唯一の実効的防御）
   からすると無視できない。

**結論: 1個か N 個かを設計時に決め打ちせず、「同じホストバイナリを何回起動するか」のポリシーにする。**
既定は共有ホスト1つ、マニフェストに `isolated: true` があるものだけ専用ホスト、権限要求プロファイルが
違うものはプロファイルごとにグループ化（svchost がまさにこれ）。コードパスは1本のまま、同居の有無だけが
設定になる。加えて**遅延起動**（初回使用時に起動、アイドルタイムアウトで終了）を入れると、実際に同時に
生きているホスト数は導入数よりずっと少なくなる。

集約ホストで失う「任意言語」は、**スクリプト用アダプタを1個のプラグインとして自分で書く**ことで回避
できる（Python 埋め込み DLL というプラグインが `.py` を読む）。言語サポート自体がプラグインになるので
コアの設計は綺麗なまま。

## 5. 配布形式と信頼ティア

以上を踏まえると、パッケージは3層のうち必要なものだけ使える形になる:

| 層 | 中身 | 信頼ティア |
| --- | --- | --- |
| `manifest.json` | id / version / 要求API版 / 提供する拡張の宣言 | — |
| `*.qml` | プレビュー描画、メニュー項目の見た目 | **制限付き**（§3-1、本当に制限が効く） |
| ネイティブ（DLL または exe） | 重い処理、独自フォーマットのデコード | **フルトラスト**（制限は不可能） |

**ネイティブコードを含むプラグインは「フルトラスト」と表示する。** 権限を細かく宣言させる UI は作らない
（守られていない保証を約束することになる）。既定オフ＋初回同意（Obsidian の Restricted Mode 相当）は
技術的防御の代わりではなく、**それが唯一できることだから**やる。制限付きの層が欲しいなら、それは
**QML のみ・ネイティブコード無し**というティアとして切る。

## 6. 着手順（もしやるなら）

1. **`MenuAction` を文字列 ID へ** — プラグイン抜きの内部リファクタとして先に済ませる。ここが一番の地雷。
2. **プレビューをレジストリ化**し、既存の Image / Text をその上に載せ替える（ドッグフード）。
3. after フックのイベントバス。
4. ここでようやく `PluginHost` と manifest。まず **QML のみのプラグイン**を1つ書いて検証する。
5. ネイティブ層（プロセス分離）は最後。本当に必要になってから。

1 と 2 は**プラグインをやらないと決めても単体で価値がある**ので、この順序ならいつ中断しても損しない。

## 7. 未解決の懸念

- **AppContainer 下での DPAPI の挙動が未検証**（§3）。ネイティブプラグインを本気で閉じ込めるなら、
  ここが成立するかが前提条件になる。机上では確認していない。
- **`ctx` のどこまでを公開契約にするか**（§1-1）は、決めた瞬間に後方互換の負債になる。プラグインを
  出す前に絞る必要がある。プロセス分離を採るならプロトコル設計そのもの。
- **審査・署名インフラ・リモート kill switch・別プロセスホスト＋IPC の4つは、個人開発では継続的な
  運用コストが本体開発を上回る**可能性が高い。系統1（ガバナンス）の各要素も、VS Code や Obsidian は
  組織規模があって初めて回している点は割り引いて読む必要がある。
- **ライセンス**: アプリは MIT なのでプラグインの二次配布に制約は出ないが、Qt は LGPLv3 なので
  プラグインが Qt にリンクする形にすると、プラグイン作者側に LGPL 条件が波及する。純C ABI + QML なら
  回避できる。
