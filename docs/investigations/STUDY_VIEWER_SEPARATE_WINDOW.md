# ビューアを別ウィンドウにする — 実現可能性調査

> **状態: 調査のみ。コードは 1 行も変えていない。** 対象は `evolve/097`（`9f28915`）で入った
> アプリ内画像ビューア（`qml/components/ImageViewer.qml`、オーバーレイ実装）。
> **結論は §0** —— 「テーマやスタイルの問題」として記憶されていたものは**ポップアップ**
> （`Menu`）の話で、トップレベル `Window` には当てはまらない。実装可能で、難所はテーマではなく
> **キャプションバー（QWindowKit）**と**モデルの寿命**の 2 つ。
> **2026-08-29 追記**: 議論の結果、**前後のファイルへの移動は当面スコープ外**と決まった。
> これで §4-2-1 の「モデルの寿命」問題は消滅し、見積もりが下がったので §0・§4-2・§6 を
> 書き直してある（初版は「動画のときにまとめて判断」を薦めていた）。
> `docs/REQUESTS.md` に「優先度: 高 の先頭」指定で登録済み。

出発点の問い: 画像ビューアを、いまのオーバーレイではなく**独立したウィンドウ**にできるか。
過去に「別ウィンドウはテーマ・スタイルで問題が出る」という話があった記憶があり、それが
本当にこの件に効くのかを確かめる。

---

## 0. 結論

**できる。テーマは障害にならない。** 記録に残っている「別ウィンドウの問題」はすべて
**ポップアップが自前のウィンドウを持つ場合**の話（§1）で、`Theme.qml` は `pragma Singleton` ＝
エンジン単位なので、同じエンジンに作った 2 枚目のウィンドウは**同じトークンを共有する**（§2）。
スタイル（FluentWinUI3）もインポート順の規約を守るだけで済む。

実際のコストは **1 箇所だけ**: **キャプションバー**。本体は QWindowKit でフレームレス化して
あり、`CaptionBar.qml` はタブ帯を内包していて再利用できない（§3）。ネイティブのタイトルバーで
妥協するか、簡素なキャプションをもう 1 つ作るかの二択で、ここが工数のほぼ全部。

もう 1 つの難所だと初版が書いていた **`FileListModel` の寿命は、前後移動をスコープ外に
決めたことで消滅した**（§4-2-1）。**表示に要るのは名前と URL だけ**で、そのどちらもタブにも
モデルにも依存しない。

**推奨は §6** —— **動画より先にやるのが安い**。いま変換すれば器は 1 つで済み、動画・PDF は
最初からウィンドウの中に実装できる。

## 1. 「テーマ・スタイルの問題」の正体

記録に残っているのは 3 件で、**すべて `Menu` が `popupType: Popup.Window` で自前のウィンドウを
持つことに由来する**。トップレベル `Window` の話は 1 件もない。

| 記録 | 中身 | 本件に効くか |
| --- | --- | --- |
| `docs/PROGRESS.md`（アカウントメニュー） | ウィンドウを持つポップアップに `enter` トランジションを付けると、アニメーションの初回 tick より前に未アニメ状態のフレームが提示され、ちらつく。`enter: null` で解決 | **効かない**。トップレベル `Window` は Popup ではなく、開閉トランジションも持たない |
| 同上 | `Popup.Native` に解決されると delegate が描画に使われず、独自ヘッダが黙って消える。`popupType: Popup.Window` を明示して回避 | **効かない**。同じく Popup 固有 |
| 同上 | ポップアップ背景 `popup-background.png` の acrylic グレインが `BorderImage` の引き伸ばしでにじむ | **効かない**。`Dialog` すら無関係（背景が素の `Rectangle`）と明記されている |
| `docs/DESIGN_IMPROVEMENT.md:1177` | メニューが別ウィンドウなのでホバーが外れてシェブロンが消える | **効かない**。同じくメニュー |

つまり **「別ウィンドウ＝テーマが壊れる」という記録は存在しない**。壊れうるのはウィンドウの
**外枠**であって、中身のテーマではない（§3）。

なお `docs/ROADMAP.md` の 見送り にある「タブを引きちぎって別ウィンドウ」は別件 ——
あれは `TabContext` を 2 つの `TabsController` 間で受け渡す話（`docs/PROGRESS.md` Phase 22b の
「Deliberately not done」）で、ビューアには関係しない。

## 2. 2 枚目のウィンドウが共有するもの / しないもの

| もの | 共有されるか | 根拠 |
| --- | --- | --- |
| `Theme.qml` のトークン | **される** | `pragma Singleton`。シングルトンは `QQmlEngine` 単位で 1 インスタンス |
| ライト/ダークの判定 | **される** | `Application.styleHints.colorScheme` を読むだけ。`main.cpp:97/101/113` の `setColorScheme()` はアプリ全体に効く |
| コントロールのスタイル | **される** | FluentWinUI3 はコンパイル時選択。ただし**新しい `.qml` でも `QtQuick.Controls.FluentWinUI3` を他の Controls インポートより先に書く**規約は必要（`Main.qml:4`・`ImageViewer.qml:5` と同じ） |
| `viewerController` | **される** | `engine.rootContext()` のコンテキストプロパティ（`main.cpp:229`）で、子コンテキストが継承する |
| ウィンドウの外枠・キャプション | **されない** | §3 |
| ジオメトリの永続化 | されない | `Settings` のキーをもう 1 組決める必要がある |
| フォーカス | されない | これは**利点**（§4-1） |

## 3. 難所その 1 — キャプションバー

本体は Phase 17a で QWindowKit によるフレームレス化をしてあり、ウィンドウごとに次が要る:

- `WindowAgent` インスタンスと `setup(window)`（`QuickWindowAgent::setup(QQuickWindow*)` は
  **ウィンドウ 1 枚につき 1 エージェント**。`third_party/qwindowkit/src/quick/quickwindowagent.h`）
- `setTitleBar()` ＋ `setSystemButton()` × 3（最小化/最大化/閉じる）。Snap Layout はこの登録が
  無いと出ない
- `applyFrameTheme()` 相当 —— QWindowKit は 1px ネイティブ枠の `dark-mode` を **true 決め打ち**
  するので、ライトテーマでは per-window に打ち消す必要がある（`Main.qml:51-57`）
- 表示時の高さジャンプ対策 —— `WM_NCCALCSIZE` でキャプション分（~31px）がクライアント領域に
  返ってくるので、`visible: false` → `setup()` → サイズ復元、の順序（`Main.qml:71-88`）

そして **`CaptionBar.qml` はそのままでは使えない**: `required property var dragProxy` を持ち、
Phase 17b からタブ帯 (`TabStrip`) を内包していて、`dragReserve` などタブ前提の幅計算がある。
選択肢は 3 つ:

| 案 | 内容 | コスト | 見え方 |
| --- | --- | --- | --- |
| **B** | ネイティブのタイトルバーで妥協（`Window` をそのまま出す） | **小**。`Window` を 1 枚足すだけ | 本体はフレームレス、ビューアだけ Windows 標準の枠。テーマ強制時にキャプションの明暗が本体とずれる可能性あり（§5-1、**要実測**） |
| **C1** | `CaptionBar.qml` をタブ無しでも成立するよう分割し、両方から使う | 中。既存ファイルに手が入るのでリグレッション面積が本体側に及ぶ | 統一 |
| **C2** | ビューア専用の簡素なキャプションを別ファイルで新規に書く | 中。既存に触らない代わりにシステムボタンの見た目が二重定義になる | 統一 |

## 4. 別ウィンドウ化で変わること

### 4-1. 消える問題

- **フォーカス奪取** —— `evolve/097` のレビューで見つかった不具合（ビューア内をクリックすると
  下のファイル一覧に active focus が移り Esc と矢印が死ぬ）は、`Main.qml:305` の
  `enabled: !imageViewer.showing` で塞いである。**別ウィンドウなら構造的に起きない**ので、
  この回避も `closed` シグナルによるフォーカス返却も要らなくなる。
- **ヘッダを覆えない制約** —— いまのオーバーレイはアドレスバー・タブ帯より下にしか置けず、
  そのせいで「開いたままフォルダを移動されうる」前提を抱えている（`ImageViewer.qml` の
  `currentHandle` による引き直しは、まさにその対策）。別ウィンドウならこの前提が消える。
- **タブ切り替えで閉じる仕様** —— `Main.qml:152` の `onCurrentPaneChanged: imageViewer.close()`
  は「ウィンドウに 1 つ」という制約の帰結。別ウィンドウなら不要。

### 4-2. 新しく決めることになるもの

1. ~~**`listModel` の寿命**~~ —— **解消済み（2026-08-29）。前後移動をスコープ外に決めた。**
   表示側が触るのは `source`（`controller.sourceUrl(handle)`）と `currentName` だけで、
   `listModel` は `step()` からしか読まれていない（`rowForHandle` / `count` / `entryAt` の
   3 つ）。前後移動を落とせばモデルへの参照はゼロになり、ウィンドウはタブが閉じようが
   フォルダを移動されようが自立する。**いま「タブ切り替えで閉じて」いる理由は寿命ではなく、
   オーバーレイが `anchors.fill: parent` でタブ領域を物理的に覆っているから** ——
   閉じずに切り替えると、切り替えた先のタブの上に前の画像が乗ったままになる
   （`Main.qml:152` のコメントは前後移動の側だけを理由として書いている）。別ウィンドウでは
   どちらの理由も消える。
   *将来もし前後移動を戻すなら*、モデルを握り続けるのではなく、**開いた時点で「見られる行の
   (handle, name) 列」をスナップショットする**のが素直。`entryAt()` は呼ぶたび
   `QVariantMap` を作るので、QML から N 回回さず `FileListModel` にまとめて返すメソッドを
   1 本足す。代償はスナップショットが古くなることだけで、ビューアウィンドウとしてはむしろ
   自然（そのウィンドウは「この画像たち」であってタブの現在地ではない）。
2. **ウィンドウは 1 枚か複数枚か** —— 画像ごとに開けるようにするかどうか。
3. **ジオメトリの永続化** —— 位置・サイズ・最大化状態のキーを別に持つか、毎回既定に戻すか。
4. **ドロップの扱い** —— レビューで足した `DropArea`（開いたまま外からファイルをドロップすると
   見えないフォルダへアップロードが走る問題への蓋）は、別ウィンドウでは意味が変わる。
5. **QML テスト** —— `tests/qml/tst_ImageViewer.qml` は `ImageViewer` を `Item` として生成して
   いる。`Window` 化すると Qt Quick Test 側の組み立てが変わる（8 件のうち何件かは書き直し）。
6. **CMake** —— `.qml` を足すので `qt_add_qml_module` の `QML_FILES` 追加 ＋ **reconfigure 必須**
   （`CLAUDE.md` の qmlcache_loader の件）。

## 5. 未確認事項

1. **ネイティブキャプションがアプリ側のテーマ強制に追随するか**（案 B の唯一のリスク）——
   設定で「ライト」を選び OS がダークのとき、`QStyleHints::setColorScheme()` が DWM の
   ダークタイトルバー属性まで波及するかは Qt のドキュメントからは読み取れなかった。
   **`Window` を 1 枚出して `MEGAEXPLORER_COLOR_SCHEME=light` と OS ダークの組み合わせを
   撮れば 10 分で分かる。** 追随しないなら案 B は「テーマの問題」を本当に踏む。
2. **同一エンジン内の非ルートウィンドウで QWindowKit が期待どおり動くか** —— API 上は
   ウィンドウ単位なので動くはずだが、実測していない。
3. マルチモニタ / 混在 DPI でのフレームレスウィンドウの挙動。

## 6. 推奨

**動画より先にやる。** 前後移動が外れて残る難所がキャプションバー 1 つになった以上、
先送りする利点がほとんどない。いま変換すれば**器は 1 つ**で済み、動画・PDF は最初から
ウィンドウの中に実装できる。逆に 3 形式そろってから変換すると、オーバーレイ固有の回避
（フォーカス奪取・ヘッダを覆えない前提・タブ切り替えで閉じる・`DropArea`）を 3 つ分作って
から 3 つとも捨てることになる。やり直しの面積は形式の数ではなく**器の数**に比例する。

プレリリースで互換性の縛りが無いので、この順序変更に外部コストは無い（`CLAUDE.md` の
「Pre-release」節）。

**着手する周が最初にやること**は §5-1 の実測 —— `Window` を 1 枚出して
「OS ダーク × `MEGAEXPLORER_COLOR_SCHEME=light`」を撮る。追随するなら案 B
（ネイティブキャプション）で済み、追随しないなら案 C1/C2 のどちらかに倒す。10 分で分かるので、
これを案の選択より先に置く。

**動画に着手する前に別途決めておくこと**（この調査の範囲外だが、ここで見えたので書き残す）:
**動画はフォルダを見ながら再生を続けられるべきか。** 別ウィンドウならできるが、実装方式を
決める要求であって後から足せる装飾ではない。いまの ROADMAP の完了条件（再生・一時停止・
シーク）はこれを求めていない。
