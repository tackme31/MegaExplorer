# 名前衝突の解決 — コピー / 移動

> **状態: 未実装。実装済みのコードは本改訂で撤去対象になる。** `docs/REQUESTS.md` の
> `[バグ] フォルダに入ったファイルが上書き判定されない` を発端に決めた仕様のうち、**コピーと
> 移動**を扱う。**アップロードは別文書** — `SPEC_NAME_CONFLICT_UPLOAD.md`。
>
> **本改訂（2026-08-15）は前 2 版の中心的な判断を覆している。** 覆したのは 3 点:
> (a) **「置き換える」という選択肢を廃止**（API に無い操作だった）、
> (b) 選択肢を種別・経路で変えるのをやめ、**4 セル共通の 4 択**に、
> (c) 混在時の **2 枚出しを 1 枚に戻した**。経緯は §7。
>
> **`evolve/017` / `019` / `024` / `027` が実装した「置き換える」は、この改訂で消える。** ただし
> 撤去対象はそこだけで、**残りは新仕様がそのまま使う** — 現状のコードは §2 が示すとおり、
> 4 択のうち 3 択まで既に出来ている。実装に入る前に §2 と §5-2 を読むこと。積み残しは §6。

2026-08-15。コードは `third_party/sdk` まで読んであり、**本仕様の土台である「移動は同名兄弟を
作る」は同日に実測して確認した**（§1-2）。積み残しは §6。

## 0. 結論（先に要約）

1. **同名のまま発行したときに何が起きるかは API が決めていて、アプリは選べない。** 経路×種別の
   4 セルのうち、**版が積まれるのはコピー×ファイルの 1 セルだけ**で、残り 3 セルでは常に同名が
   2 つ並ぶ（§1-2）。
2. **「置き換える」を選択肢から廃止する。** それは API の操作ではない。コピー×ファイルでは
   「このまま実行」と*たまたま*一致し、移動×ファイルでは `copy` + `moveToRubbish` というアプリ製の
   合成、フォルダでは実現不能 — **同じ言葉が 3 通りの意味を持っていた**のが、前 2 版が説明しにくい
   根本だった。
3. **選択肢は 4 セル共通で「このまま実行 / 名前を変えて実行 / スキップ / キャンセル」。** どれも
   API 呼び出し 1 本に対応する。セルごとに変わるのは**本文の説明文だけ**。
4. **混在ダイアログは 1 枚。** 第 2 版は 2 枚に割ると書いていたが、「置き換える」がフォルダで無意味
   だったことがその理由なので、消える。**実装は最初から 1 枚**なので、ここは仕様が実装に追いついた
   だけで作業は無い（§2-2）。
5. **コピー／移動はゴミ箱を一切使わない。** ゴミ箱に入るのはユーザが明示的に「削除」したものだけ
   になる（§4-1）。
6. **`versions_disabled` はコピー×ファイルの本文にだけ効く**（§1-3）。

## 1. SDK 調査（事実）

### 1-1. 同名の兄弟は MEGA では異常な状態ではない

MEGA のノードツリーは同じ親の下に同名の子を許す。ファイルシステムと違い、名前は識別子ではなく
属性でしかない。**したがって「衝突」はアプリが持ち込んだ概念**で、API 側には衝突という状態も、
それを解決する引数も無い。

### 1-2. 同名のまま発行した結果は、4 セルで決まっている

| 経路 × 種別 | 同名のまま発行した結果 | 版化 | 重複 | 結合 |
|---|---|---|---|---|
| コピー × ファイル | **必ず版になる** | 強制 | **不可能** | — |
| コピー × フォルダ | **必ず同名 2 つ** | 不可能 | 強制 | 不可能 |
| 移動 × ファイル | **必ず同名 2 つ** | 不可能 | 強制 | — |
| 移動 × フォルダ | **必ず同名 2 つ** | 不可能 | 強制 | 不可能 |

根拠:

- **コピー**: `copyTreeFromOwnedNode()` が `getovnode()` で既存を引き `ovhandle` を立て、
  `putnodes(..., UseLocalVersioningFlag, ...)`（`megaapi_impl.cpp:21844,21781`）。判定は
  **「結果の名前が既存ファイルと一致するか」**で、`newName` を明示的に同じ名前にしても版が積まれる。
  したがって**コピーで同名ファイルを 2 つ作ることはできない**。
- **`ov` は `type == FILENODE` のトップレベルにしか付かない。** `proctree()` が作る子ノードには
  入らないので、**フォルダのコピーは常に同名 2 つ**になる。`copyNode()` はサブツリーを 1 リクエストで
  サーバ側コピーするため「既存フォルダへマージ」は書けない（`src/core/IMegaClient.h:247-260`）。
- **移動**: `moveNode()` → `MegaClient::rename()` → `CommandMoveNode`（`m` コマンド）だけで
  `ov` も `vb` も送らない（`megaclient.cpp:10023-10110`）。**衝突を見ていない**ので、ファイルでも
  フォルダでも同名が並ぶ。
- **fingerprint が完全一致ならコピーは通信すらしない。** 既存ハンドルを返して `API_OK` で終わる
  （`megaapi_impl.cpp:21847,21915-21918`）。同一内容のコピーは無害な no-op。

**移動の 2 行は 2026-08-15 に実測した**（`megatool mv`、テストアカウント）:

| 測ったこと | 結果 |
|---|---|
| 3 バイトの `a.txt` を、9 バイトの `a.txt` がある `dst` へ移動 | `dst` に **`a.txt` が 2 行**（`9` と `3`）。版は積まれず、移動元フォルダは空になった |
| `inside.txt` 入りの `photos` を、空の `photos` がある `dst2` へ移動 | `dst2` に **`photos` が 2 行**。結合されない |

エラーも警告も返らず、`moveNode` は素直に成功する。**同名かどうかを移動が一切見ていない**ことの
直接の確認で、本仕様はこの結果の上に立っている。

### 1-3. `versions_disabled` が効くのはコピー×ファイルだけ

`UseLocalVersioningFlag` はアカウント設定で 2 つに分岐する（`commands.cpp:1171-1173`）:

| 設定 | 実際の動作 |
|---|---|
| バージョン管理 **有効**（既定） | `ClaimOldVersion` — 旧ノードが新ノードの第 1 版になる。復元可能 |
| バージョン管理 **無効** | `ReplaceOldVersion` — **旧ノードは完全削除。ゴミ箱にも行かない**（`types.h:1158`、`file.cpp:497`） |

アプリ側で `ClaimOldVersion` に固定はしない。バージョン管理を切るのは容量のためにユーザが意図して
やる設定で、それを無視して版を積むほうが不具合に見える。アプリがやるのは**本文の切り替えと、
既定ボタンの切り替え**だけ（§3-4）。**版化しない 3 セルには一切関係しない。**

読み取りは `MegaApi::getFileVersionsOption()`（非同期、未設定なら `API_ENOENT`＝有効が既定、
`megaapi.h:21447`）。ログイン後にキャッシュする。

### 1-4. 名前は移動・コピーの時点で変えられる

- **移動**: `MegaApiImpl::moveNode(node, newParent, newName, listener)` が存在し
  （`megaapi_impl.cpp:21415`）、`MegaClient::rename()` が `attrUpdates['n']` として先に流すので
  **リネーム込みで 1 リクエスト**（`megaclient.cpp:10092-10107`）。`IMegaClient::moveNode` には
  `newName` が無いので配線が要る（§5-1）。
- **コピー**: `copyNode(src, dst, newName)` は既に配線済み。

つまり「名前を変えて実行」は**どのセルでも API 呼び出し 1 本**で、合成ではない。

### 1-5. 存在チェックにネットワークは要らない

`MegaApi::getChildNodeOfType()` は同期関数で、`NodeManager`（メモリ）→ 未ロードならローカル
SQLite に落ちる（`megaapi_impl.cpp:19410`、`db/sqlite.cpp:4212`）。`fetchNodes()` 済みなら
サーバには行かない。現状のコピー／移動経路は宛先の一覧を読み直しており
（`FileMutationController::DestinationSnapshot::of`）、そのコストはここに収まる。

### 1-6. 件数とサイズは同期・ローカルで取れる

`MegaApi::getSize(node)` はフォルダに対しサブツリー全体の合計を返す同期関数
（`megaapi.h:20241-20250`）。`getNumChildFiles()` も同様。ネットワークに行かない。

## 2. 現状のコードとの差分

### 2-1. 「置き換える」が両経路に実装済み — 撤去対象

| 対象 | 現状 | 本仕様 |
|---|---|---|
| `FileMutationController::copyReplacingExisting` | `copyNode(src, dst, newName="")`。SDK が版を積む | **「このまま実行」に改名**（挙動は同じ） |
| `FileMutationController::moveReplacingExisting` | `copyNode(...)` → 成功したら `moveToRubbish(src)`（`evolve/027`） | **削除** |
| `FileMutationController::moveOne` の `replacing` 分岐 | 上を呼ぶ | **削除**。移動は常に `moveNode` 1 本 |
| `PlannedMove::replacing` | 置き換えかどうかを持つ | **削除** |

`moveReplacingExisting` は `evolve/024`（ゴミ箱先行）→ `evolve/027`（コピー＋移動元をゴミ箱）と
2 周かけて作り替えたばかりだが、**どちらも API に無い操作をアプリで合成していた**という点は同じ。
本改訂はその合成をやめる。ユーザが同じ結果を得る手順は §4-3。

### 2-2. 既に新仕様どおりになっている部分 — 触らないこと

新仕様が要求するもののうち、**次の 2 つは実装済み**。第 2 版の記述に引きずられて作り直さないこと。

| 新仕様の要求 | 現状 |
|---|---|
| 混在しても**ダイアログ 1 枚** | `CopyConflictDialog.qml` が `operation: "copy"\|"move"` を持ち、`conflictingFiles` と `conflictingFolders` を同時に受けて本文を組む。**第 2 版の「2 枚に割る」はコードに入ったことがない** |
| **フォルダも衝突として数える** | `DestinationSnapshot::collidesWith` が `entry.isFolder ? folders.count(...) : files.count(...)` と種別でマッチ済み（`evolve/019`） |

したがってダイアログに足りないのは**「名前を変えて実行」のボタン 1 つ**と、「置き換える」→「この
まま実行」の文言・表示条件だけ（現状は衝突がフォルダだけのとき「置き換える」を隠している）。

`ROADMAP.md` の「名前衝突 3」は `collides()` の `!entry.isFolder` を外す前提で書かれているが、
**その条件はもう無い**。

### 2-3. `uniqueCopyName()` はダイアログの答えではなく既定エンジン

`startCopyBatch()` は衝突が無ければ全エントリを `uniqueCopyName()` に通す。Rename はダイアログの
答えである前に通常のコピー経路そのもので、単純に削除すると壊れる。本仕様では**無確認で使うのは
同一フォルダ複製だけ**に降格する（§3-5）。

### 2-4. ダウンロードは対象外

`COLLISION_RESOLUTION_NEW_WITH_N` で黙って `(1)` が付く（`DownloadController.cpp:132`）。
ブラウザと同じ。本仕様の対象外。

## 3. 仕様

### 3-1. 選択肢 — 4 セル共通の 4 択

| 選択肢 | 発行する API | 衝突したエントリ | 衝突していないエントリ |
|---|---|---|---|
| **このまま実行** | `copyNode(src, dst, "")` / `moveNode(src, dst, "")` | 発行する。結果は §3-2 | 実行する |
| **名前を変えて実行** | `copyNode(src, dst, newName)` / `moveNode(src, dst, newName)` | 空いている名前を付けて発行する | 実行する |
| **スキップ** | — | 発行しない | 実行する |
| **キャンセル** | — | 発行しない | **実行しない**（操作ごと取りやめ） |

**この 4 つは種別でも経路でも変わらない。** 選択肢の数・順序・意味が一定なので、ダイアログの形が
1 つで済む。スキップとキャンセルの差は右列だけなので、本文に「他の N 件はそのまま移動されます」と
書かないと伝わらない。

**既定ボタン**は「このまま実行」。ただし**コピー×ファイルで `versions_disabled` が ON のときだけ
「名前を変えて実行」**にする — 4 セル中そこだけが、選択によって復元不能なデータ喪失を起こす
（§1-3）。

### 3-2. 「このまま実行」の結果 — セルごとの説明文

| 経路 × 種別 | 結果 | 本文に書く説明 |
|---|---|---|
| コピー × ファイル（版管理 有効） | 版が積まれる | 「既存のファイルは以前のバージョンとして残ります」 |
| コピー × ファイル（版管理 無効） | 旧ノード完全削除 | 「既存のファイルは**完全に削除されます**（バージョン管理をオフにしているため）」 |
| コピー × フォルダ | 同名 2 つ | 「同じ名前のフォルダが 2 つ並びます」 |
| 移動 × ファイル | 同名 2 つ | 「同じ名前のファイルが 2 つ並びます」 |
| 移動 × フォルダ | 同名 2 つ | 「同じ名前のフォルダが 2 つ並びます」 |

**「MEGA では同名を許しているので、これはエラーではありません」**を短く添える。Windows Explorer
から来たユーザには、同名が並ぶこと自体が異常に見えるため。

### 3-3. ダイアログの構成 — 1 枚

**種別が混ざっても 1 枚**にする。第 2 版が 2 枚に割ったのは「置き換える」がフォルダで無意味だった
からで、4 択が共通になった今は 1 枚で全部表現できる。**実装は既に 1 枚**（§2-2）なので、ここで
変えるのはボタンと本文だけ。混在時の本文は種別ごとに結果を並べる:

> 移動先に、同じ名前の項目が **5 個**あります。
> 　ファイル 3 個 — `a.txt` `b.png` `c.pdf`
> 　フォルダ 2 個 — `photos` `docs`
> 「このまま移動」を選ぶと、**同じ名前の項目が 2 つずつ並びます**（MEGA では同名を許しているので
> エラーではありません）。他の 12 個はどちらを選んでも移動されます。
> 　[このまま移動] [名前を変えて移動] [スキップ] [キャンセル]

**不変条件: 回答を得てから発行する。** 1 枚になったので自明だが、ダイアログ表示中に API を
1 本も飛ばさないこと。

**既知の制約: 「ファイルはこのまま、フォルダはスキップ」は表現できない。** 1 枚に畳んだ代償。
前版はそのために 2 枚出していたが、そこで分けたかった組み合わせ（ファイルは置き換え／フォルダは
スキップ）は「置き換える」の廃止で消えている。項目ごとに選ばせる UI が要ると分かったら、そのとき
一覧形式にする（§6-2）。

**衝突が 1 件でも選択肢は減らさない。** そのときスキップとキャンセルは結果が同じになるが、件数で
ボタン構成が変わるほうが混乱する。

件数と追加サイズ（§1-6）も添える。

### 3-4. 「名前を変えて実行」で付ける名前

| 経路 | サフィックス | 例 |
|---|---|---|
| コピー | `- Copy`（`uniqueCopyName()`） | `dir - Copy`、既に埋まっていれば `dir - Copy (2)` |
| 移動 | `(2)` | `dir (2)`、埋まっていれば `dir (3)` |

移動は複製ではないので `- Copy` は語感が合わない。**API から見ればどちらも `newName` の文字列
でしかない**ので、これは表示上の判断。**付ける名前は必ずダイアログ本文に出す**（「`dir (2)` という
名前で移動します」）。

### 3-5. 同一フォルダへの貼り付け

| 対象 | 挙動 |
|---|---|
| ファイル / フォルダ / 混在 | **無確認**、`- Copy` 付与 |

同一フォルダへの貼り付けは衝突ではなく**複製の意思表示**なので訊かない。API ファーストでも同じ
結論になる: 同名のまま発行しても、コピー先の既存ノードは**自分自身**で fingerprint が一致するため
**no-op で `API_OK` が返るだけ**（§1-2、未実測）。訊いても意味のある選択肢が無い。

判定に追加 API は不要 — 宛先の一覧は既に読んでいるので、**エントリ自身のハンドルがその一覧に
含まれるか**で分かる（`DestinationSnapshot::of`）。

### 3-6. 名前が同じで種別が違うとき

**衝突扱いしない。** MEGA はファイルとフォルダの同名共存を許し、互いを上書きも結合もしない。
ダイアログは出さず、そのまま発行する。

## 4. この仕様が導く帰結

### 4-1. コピー／移動はゴミ箱を一切使わなくなる

ゴミ箱に入るのは**ユーザが明示的に「削除」したものだけ**になる（`moveHandlesToRubbish`）。
ゴミ箱の自動 purge（無効化は PRO 限定、`megaapi.h:16930`）が、コピー／移動の取り消し可能性に
一切影響しなくなる。

前版は「移動の移動元」も入る二本立てだったが、それが消えて一本になった。

### 4-2. 移動でノードハンドルが変わらなくなる

前版の移動の置き換え（`copy` + `moveToRubbish`）は移動元のハンドルを変えるため、**移動元に張った
公開リンクが切れた**。本仕様の移動は `moveNode` 1 本なのでハンドルが保存され、リンクは生き残る。
Windows Explorer との差異が 1 つ減る。

残る差異は**コピー／移動でフォルダを結合できない**ことだけ（§1-2、SDK の制約）。Explorer は
結合する。アプリでは「このまま（2 つ並ぶ）」か「名前を変える」か「スキップ」になる。
アップロードだけは結合できる（アップロード側 §1-2）。

### 4-3. 「置き換えたい」ユーザがやること

移動元 A を、同名ファイルのある B へ「上書きするように」移したい場合:

1. A を B に**コピー**する → ダイアログで「このまま実行」→ B の既存ファイルが以前のバージョンに
   なる（コピー×ファイルは版化するセル、§1-2）
2. A を**削除**する

**前版の `moveReplacingExisting` はこの 2 手を 1 つのボタンの裏でやっていた**。手数は増えるが、
どちらの手も API の操作そのもので、途中で失敗しても半端な状態の意味がユーザに分かる。この 2 手を
ワンアクションにまとめるべきだと分かったら、そのときは**「置き換える」ではなく「コピーして元を
削除」と、合成であることが読める名前**で足す。

## 5. 実装メモ

### 5-1. `IMegaClient` に足りないもの

| 追加 | 用途 |
|---|---|
| `moveNode` に `newName` | §3-1 の「名前を変えて移動」。SDK 側は 1 リクエストで済む（§1-4） |
| `getFileVersionsOption` 相当 | §3-2 の本文・既定ボタン切り替え。ログイン後にキャッシュ |
| `getSize` / `getNumChildFiles` | §1-6 の件数・追加サイズ表示 |

下 2 つはアップロード側と共通。

### 5-2. 消えるもの

| 対象 | 変更 |
|---|---|
| `FileMutationController::moveReplacingExisting` | **「このまま移動」に作り替え**（§2-1） |
| `moveOne` の `if (replacing)` ブロック | **丸ごと削除**。その下に既にある `mFileOps->move(...)` 1 本が、そのまま「このまま移動」になる |
| `PlannedMove::replacing`、`MoveConflict::Replace` | **削除**。全エントリが同じ 1 本で発行されるので、衝突したかどうかを計画に持つ意味が無くなる |
| `FileMutationController::copyReplacingExisting` | 残すが「このまま実行」に改名（挙動は不変 — 既に `newName` 空で発行している） |
| `uniqueCopyName()` / `CopyConflict::Rename` | 残す。`Rename` は既定エンジンとして生きているので、**ダイアログから呼べる入口（`copyRenamingExisting`）を戻すだけ**（`evolve/019` が消したもの） |
| `CopyConflictDialog.qml` | ボタンを 4 つにし、先頭を常時表示に（現状はフォルダのみの衝突で「置き換える」を隠している）。本文は §3-2。**1 枚構成・`operation` 分岐・キュー処理はそのまま**（§2-2） |

`DestinationSnapshot`・`startCopyBatch`/`startMoveBatch`・`ClipboardController` 連携・
`clearClipboardIfSpentBy` は**すべてそのまま使う**。撤去は移動の置き換えに限る。

**`evolve/027` が入れたテスト**（`MoveReplacingExisting*`）も一緒に消える。`canMove` の事前
チェックは**移動そのものに要る**ので残す（`evolve/027` の判断とは理由が変わる — 破壊的な段が
無くなったので、単に「発行前に通らないと分かる移動を弾く」だけの意味になる）。

### 5-3. 同一操作内の同名も衝突として数える

クリップボードに別フォルダ由来の同名ファイルが 2 つあると、宛先に既存が無くても互いに衝突する。
**宛先の既存だけでなく、同一操作内の同名も数える**こと。数えたうえで「このまま実行」を選ばれた
場合の結果は API どおり（コピー＝版が積み上がる、移動＝同名が並ぶ）だが、コピーは「2 件コピー
したのに 1 行しかない」に見えるため、そこだけ §6-1 に残す。

## 6. 積み残し

### 6-1. コピーで同名が複数積み上がったときの見え方

§5-3。2 件の同名ファイルを 1 箇所へコピーすると、2 件目が 1 件目に版を重ねて 1 行になる。API
どおりではあるが、「このまま実行」の説明文（§3-2）が想定していない結果なので、文面を足すか
2 件目を自動リネームするかを、実測してから決める。

### 6-2. 項目ごとの選択が要るか

§3-3 の既知の制約。1 枚 4 択で足りるか、項目ごとに選ばせる一覧形式が要るかは、実際に混在衝突を
起こしてみないと分からない。**先に 1 枚で出す**（作るものが小さく、要らないと分かれば終わり）。

### 6-3. MEGA がコピーをストレージに二重計上するか（未検証）

MEGA のコピーは物理ブロブを再アップロードせずノードだけ作るため、課金がノード単位か実体単位かで
「大きいフォルダの複製は容量を食う」という懸念の重みが変わる。`megatool` でフォルダをコピーする
前後の `getAccountInfo` を比べれば判定できる。**前版では移動の置き換えが常にコピーを撃つため
優先度が高かったが、それが消えたので通常のコピーの話に戻った**（優先度は下がる）。

## 7. 前 2 版から変えた判断と、その理由

### 7-1. 「置き換える」は API の操作ではなかった

初版・第 2 版とも「置き換える」を選択肢の柱に置いていた。だがその語は 3 つの別物を指していた:

| セル | 「置き換える」の実体 |
|---|---|
| コピー × ファイル | 何もしない（同名で発行すれば SDK が勝手に版を積む） |
| 移動 × ファイル | `copyNode` + `moveToRubbish` の**アプリ製の合成** |
| フォルダ（両経路） | **実現不能**（選択肢から消すしかない） |

同じボタンが「API 任せ」「アプリの合成」「不能」に化けるので、**セルごとに選択肢の集合が変わり、
フォルダには例外の注釈が要り、仕様上は混在時に 2 枚へ割る**必要があった。第 2 版の複雑さはほぼ
全部ここから出ていた。実装は 2 枚化の手前で止まっていて（§2-2）、代わりに「フォルダのみの衝突では
置き換えボタンを隠す」という形で同じ問題を回避していた — その隠しも本改訂で不要になる。

「API が実際にできること」を選択肢に対応させると、4 セルで同じ 4 択になり、変わるのは説明文だけに
なる。**セルごとに変わるものが「結果」から「文言」に移った**のがこの改訂の全部。

### 7-2. 移動の置き換えを落とす判断

撤去するのは `evolve/024`・`evolve/027` が作った**置き換えの実体だけ**で、同じ 2 周が入れた
ダイアログ・宛先スナップショット・バッチ計画は残る（§5-2）。残す理由が弱い:

- API に無い操作で、**ノードハンドルが変わり公開リンクが切れる**（§4-2）
- コピー成功・ゴミ箱失敗の中間状態があり、そのときのトースト文面が別項目として起票されていた
- ストレージ二重計上が未検証のまま（§6-3）で、二重計上なら移動が一時的に容量を食う
- 同じ結果は「コピー→削除」の 2 手でユーザが作れる（§4-3）

**ユーザが自分でやれることを、説明の難しいボタン 1 つに畳んでいた**というのが結論。畳むこと自体を
将来やり直す余地は §4-3 に残してある。

### 7-3. 一貫性は経路の中だけで取る

アップロードの選択肢は「置き換える／スキップ／キャンセル」で、コピー／移動の 4 択と揃っていない。
SDK でできることが経路ごとに違う以上、揃えると全経路を最小公倍数に落とすことになる。**経路の中では
完全に一貫させ、経路をまたいでは揃えない** — 2026-08-15 の文書分割はこの線引きを形にしたもの。
