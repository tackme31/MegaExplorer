# 大規模アカウントでの検索が遅い — SDK 内部の調査

> **状態: 一部着手。`mmap` の設定だけが `develop` に入った（§3）。SDK 本体への修正は
> ローカルブランチにしか存在せず、出荷物には入っていない（§4）。**
> 対象は名前での検索（`MegaApi::search`）。60万ノードの本番アカウントで約6秒かかっていた。
> 結論は §0、内訳は §1、施策ごとの効果は §2、次の一手は §5。
> 2026-09-18 時点のコード（SDK `v10.17.0` = `51954a4`）に対する調査。

---

## 0. 結論

検索時間は**ヒット件数ではなく、検索起点の配下にあるノード数に比例**していた（10件ヒットでも
6秒）。原因は SDK の SQL とその周辺にあり、アプリ側のコードではない。

`MEGAEXPLORER_SQLITE_MMAP_MB` を設定すると SQLite のページをメモリに対応付ける。これだけで
**6秒 → 3秒**。`main.cpp` で完結し、サブモジュールには触れない。

SDK のクエリまで直せば**1.5秒**まで下がるが、そちらはローカルブランチ止まり（§4）。

## 1. 何が時間を食っていたか

`MegaApi::search` → `NodeManager::searchNodes` → `SqliteAccountState::searchNodes`
（`src/db/sqlite.cpp`）。最後の関数が組み立てる1本の再帰 SQL がすべてを行う。

1. **`ancestors` CTE がテーブル全件を走査していた。** 検索起点のハンドル3つと「共有ノードか」の
   判定が1つの OR で繋がっているため、SQLite がインデックスを使えない。`EXPLAIN QUERY PLAN` で
   `SCAN nodes` を確認済み。起点を1件決めるだけのために60万行を読んでいた。
2. **再帰でたどる行が、暗号化ノード本体の BLOB ごと運ばれていた。** CTE の列リストに `node`・
   `counter`・`description`・`tags` が入っていて、`matchFilter` で捨てる行にも付いてくる。
   `description`/`tags` はレコード上で `node` より後ろにあるので、全行でレコード末尾まで読む。
3. **仮想列 `mimetypeVirtual`・`sizeVirtual` が全行で計算されていた。** どちらも SDK 独自の SQL
   関数（拡張子判定、counter BLOB の解析）で、本来はヒットした数件にしか要らない。
4. **名前の部分一致が Unicode 処理を1文字ごとに呼んでいた。** `icuLikeCompare`（`src/utils.cpp`）
   は比較のたびに `foldCaseAccentEqual` を呼び、名前側とパターン側の両方を `utf8proc` で畳み込み
   直す。結果をキャッシュしていない。
5. **SQLite のページキャッシュが既定の約2MB のままだった。** SDK は `cache_size` も `mmap_size`
   も設定していない。60万ノードの DB を散らばった順に引くので、ほぼ毎ページで `ReadFile` と
   メモリコピーが発生する。**これが一番大きかった。**

推測が外れた点：当初「再帰 CTE の結果が一時テーブルに実体化される」と見ていたが、実行計画では
`CO-ROUTINE` で流し読みされていた。

## 2. 施策ごとの効果（Release ビルド、本番60万ノード、同じ検索語）

| 施策 | 単独での効果 |
| --- | --- |
| 名前比較（§1-4）のキャッシュ化 | 6秒 → 約5秒 |
| SQL の作り直し（§1-1〜3） | 6秒 → 3秒弱 |
| `mmap_size=256MB`（§1-5） | 6秒 → 3秒 |
| SQL の作り直し + mmap | 6秒 → 1.5秒 |

## 3. `develop` に入ったもの

`main.cpp` で、環境変数 `MEGAEXPLORER_SQLITE_MMAP_MB`（MB 単位）が設定されているときだけ、
`MegaApi` を作る前に `sqlite3_config(SQLITE_CONFIG_MMAP_SIZE, …)` を呼ぶ。**既定では何もしない。**

- プロセス全体の既定値なので、SDK が開くすべての接続に効く。最初の接続が開く前に呼ぶ必要がある。
- SQLite は vcpkg の triplet で静的リンクされていて exe 内に1つしかないため、アプリ側からの設定が
  SDK にも効く。そのために `CMakeLists.txt` で `unofficial::sqlite3` を `MegaExplorer` にリンク
  している（`SDKlib` 側の `find_package` はディレクトリスコープなので届かない）。
- 効いたかどうかはログの `SQLite default mmap_size … sqlite3_config rc 0` で分かる。

## 4. ローカルにしかない SDK パッチ

SQL と名前比較の修正は `third_party/sdk`（BSD-2-Clause）のソースを書き換える。upstream に出す前提の
変更なので、**どのリモートにも push していないブランチ**に置いてある。

| リポジトリ | ブランチ | 内容 |
| --- | --- | --- |
| `third_party/sdk` | `perf/search-query` | 名前比較のキャッシュ化、SQL の作り直し、`PRAGMA mmap_size` |
| 本体 | `perf/sdk-search-query` | 上を指すサブモジュール参照（**push 禁止**） |

同等性の確認：合成データで旧クエリと新クエリを並べ、起点・共有種別・機密フラグ・名前・種類・説明・
タグ・お気に入り・ページ指定の9216通りで結果が完全一致した（SQLite 3.45 で確認、アプリが使う 3.49
では未確認）。検証スクリプトは残していない。

このブランチを本体の `develop` に merge してはいけない。サブモジュールがローカルにしかない
コミットを指すことになり、他の環境で取得できなくなる。

## 5. 次の一手（未着手）

`parenthandleindex (parenthandle, type, name)` に `flags` と `nodehandle` を足せば、名前だけの検索
なら走査と絞り込みがインデックス内で完結し、テーブル本体を引くのはヒットした行だけになる。先頭の
列は同じなので既存の利用箇所は壊れない。増加は1行16バイト前後（60万件で約10MB）。

ただし `ctime`・`mtime`・`fav` がクエリの文面に出るだけでインデックスだけでは済まなくなるため、
使うフィルタの組み合わせごとに文を作り分ける必要がある。またインデックスは**ユーザーの DB に
書き込まれて、パッチを戻しても残る**ので、試す前にバックアップが要る。

ヒット件数だけに比例させたい場合は FTS5 trigram などの部分一致索引になるが、書き込み経路と DB 移行
に手が入る大改修で、この規模では不要と判断した。
